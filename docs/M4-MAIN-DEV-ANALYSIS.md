`@50 순증 ≥1`과 `@5 총수 비감소`를 모두 만족해 사전 조건을 통과했다. 이는 모든 질문의 비회귀, 통계적 유의성, 완전한 관련성 정답률이나 답변 정확도의 증명이 아니다. 실행 오류는0개였고 품질 실패 질문은 아래처럼 그대로 남겼다.

## 주석의 빈틈과 구조적 한계

**053은 지표 회귀와 답변 가능성을 분리해야 한다.** 고정 hook-order 주석은 영어 `k8s-en-db7d68386819ee82:0`의 `[592,805)` 또는 한국어 대안이다. Terminal은 이를 후보50에서 놓쳤다. 그러나3위의 같은 영어 문서 `:1`, `[842,1835)`에는 hook과 컨테이너 프로세스가 동시에 실행된다는 별도 설명이 있다. 4위 `:4`에도 hook 실행 시점에 프로세스 시작 완료가 보장되지 않는다는 설명이 이어진다. Probe-gate는1위의 한국어 `k8s-ko-ac9fff89924d08ab:1`에 있다.

따라서 주석 기준 @50/@5 실패를 유지하면서도 “terminal은 두 사실에 답할 수 없게 됐다”고 단정하지 않는다. 상위 결과의 대체 설명은 AI 원문 대조로 확인한 정성 관찰이며 사용자 검수나 새로운 정답성 점수가 아니다. 이 대안을 이번 qrels에 소급 추가하지 않는다. 주석상 교차 언어라는 분류도 전체 코퍼스에 같은 언어 답이 없음을 증명하지 않는다.

014의 terminal 상위 결과에는 인증서 기간 flag·회전·CSR 승인과 API 이전 설명이 있었지만, 확인한 top5는 개별 CSR이 더 짧은 기간을 요청할 수 있다는 고정 요청 사실을 직접 회수하지 못했다. TLS bootstrapping 청크에는 발급 기간1년이라는 다른 설명도 있었다. 각 설명의 맥락·적용 조건과 최신성을 판정한 실험이 아니므로, 관련 문서 적중만으로 최신 사실의 정확성까지 주장하지 않는다. 036·039도 같은 문서를 찾은 것과 필요한 문장 구간을 찾은 것이 달랐다.

Terminal의 @5 실패22개 중12개는 후보50부터 모든 주석 근거를 갖추지 못했고,10개는 후보50에는 충분했으나 top5에서 실패했다. 후자는001·006·008·014·017·029·036·039·054·057이다. 후보 부족12개 중011·030·032는 원래 청크 어느 하나도 필수 span 전체를 담지 못하는 구조적 경계 문제이며 그대로 분모에 포함했다.

필수72그룹의 후보50 분류는 회수42→58, 근거 문서 부재24→8, 같은 문서의 다른 청크3→3, 표현 가능한 전체-span 청크 없음3→3이었다. 이는 자동 분류 결과로, 잘림이나 학습 데이터가 각 실패를 일으켰다는 인과 증거는 아니다. 근거 없음12개·조건 불명확8개에도 두 방법 모두 결과를 반환했다. 이 실행은 보류 기준·보류 정확도·생성 답변을 평가하지 않았다.

## 과거 M3 재생, 잘림과 실제 시간

과거 M3 저장 결과의 재생이 통과했고 fresh base의79질문×50후보 구성·순서·raw score와 top10이 저장 dense와 정확히 일치했다. 질문별 지표 차이와 공통 점수 차이는0이었다. 이 관찰은 이번 실행의 일치이며 향후 GPU bitwise 결정성의 보장은 아니다. 새 보고서의 driver·thread 수·tokenizers 버전 등은 옛 보고서에 없던 기록이므로, 그 metadata 차이를 실제 환경 변경으로 단정하지 않는다. 주 비교의 기준선은 끝까지 fresh base다.

두 방법 모두 입력3,671개 중38개가512토큰 한도로 잘렸다. 분모는 문서3,588개·질문79개·warmup4개이며 잘린 질문은0개다. 두 방법의 입력 ID·mask fingerprint와 길이·잘림 기록은 일치했다. 청크 원문 근거 회수와 잘린 모델 입력의 근거 보존은 별개이며 이번에는 새 span-token 가시성 평가를 하지 않았다.

회귀001·006·014·039·040의 주석을 완전히 담는 청크들은 잘리지 않았다. 036과053에는 잘린 한국어 대안 청크가 있지만 잘리지 않은 영어 대안도 있다. 같은 토큰 입력을 받은 두 모델의 순위 차이를 이 관찰만으로 잘림 탓으로 돌리지 않는다.

## 면접에서 설명할 판단

- **왜 dev를 따로 평가했는가:** Fit은 실제 가중치 갱신에 사용했고 calibration은 원래 train 안의 내부 진행 기준이었다. 둘과 문서 계열을 분리한 main-dev에서 같은 checkpoint를 한 번 비교해 학습 데이터 근처의 개선이 기존 개발 평가에서도 관찰되는지 확인했다. 다만 이 dev는 M2/M3에서 이미 사용한 개발 집합이므로 처음 보는 최종 블라인드 test라고 부르지 않는다.
- **왜 @50 개선만으로 충분하지 않은가:** 후보50에 필요한 사실이 있어야 후단이 사용할 수 있지만, 질문에 필요한 여러 사실이 top5에 함께 있어야 하는 조건은 더 엄격하다. 실제054는 근거 순위3·34, 057은6·10이었고 다중 문서 @5는0/7이다. 후보 회수 개선과 최종 근거 조합의 성공을 분리했다.
- **왜053을 자동으로 정답 처리하지 않았는가:** 다른 상위 청크의 동시 실행 설명은 주석의 빈틈을 보여 주는 검토 근거다. 결과를 본 뒤 해당 모델에 유리한 답을 추가하면 원래 비교 기준이 바뀐다. 고정 점수의 회귀를 보존하면서 대체 근거를 별도 정성 기록으로 남겼고, 사용자 검수나 완전한 관련성 판정으로 포장하지 않았다.

## 다음 단계의 경계

이번 결과는 학습 가설인 dense 후보 회수 개선을 별도 dev에서 관찰한 한 번의 예비 비교다. Test는 잠금 상태이고 사용자 검수0·서비스 채택0·이번 비교 중 추가 학습0이다. 실패한 이전 준비·GPU 기록과 calibration 회귀도 보존한다. 이 dev 결과로 epoch·seed·음성·청크·후보 예산·질문을 다시 맞추거나 새 모델을 탐색하지 않는다.

다음은 고정 terminal checkpoint를 대상으로 별도 운영 검증 범위를 먼저 정하는 것이다. 서버 세션·workspace/private ACL의 검색 전 적용, checkpoint와 vector/cache/revision identity, 수정·삭제·재처리 후 이전 근거 제거, 검색/원문/history/feedback, 모델 중단 시 실패와 fallback 거부, 실제 로컬 HTTP·브라우저 및 필수 원격 CI를 확인해야 한다. 기존 모델의 회귀 통과를 terminal 검증으로 대신하지 않는다.

공개 코퍼스 점수는 서비스 권한·문서 생명주기나 사용자 경험의 증명이 아니다. 실행 결과와 모델 없는 replay·로컬 회귀·원격 CI의 상태는 각각 [STATUS](STATUS.md)에 기록한다. 유료 API·GPU 임대·클라우드와 공개 서비스 배포는 별도 사용자 승인 경계를 유지한다.
