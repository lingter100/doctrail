# ADR-0003 · 화면을 React로 전환하고 서비스·근거 계약을 유지한다

- 결정일: 2026-10-12
- 상태: 사용자 요청에 따라 전환 구조 채택. 구현·검증·통합 결과는 [STATUS](../STATUS.md) 참고
- 범위: 프런트엔드 구성, 상태 전환, API·권한·원문 근거의 회귀 조건
- 이전 결정: [ADR-0001](0001-architecture.md)의 초기 화면 구현 기록과 [ADR-0002](0002-java-service.md)의 Java/Python 역할 분리는 유지한다.

## 맥락

기존 화면은 Vite·TypeScript에서 HTML 문자열과 이벤트 연결로 계정, 문서 라이브러리, 검색 결과, 원문 패널과 모달을 관리한다. 상태가 바뀔 때 넓은 DOM 영역을 교체하고 이벤트를 다시 연결하며, 진행 중 요청의 응답과 현재 화면의 관계를 수동으로 검사한다. 사용자의 React 전환 요청을 반영하되 화면 프레임워크 변경을 검색 품질 개선이나 새 서비스 기능으로 소개하지 않는다.

## 결정과 대안

React + TypeScript + 기존 Vite 빌드를 선택한다. React 컴포넌트가 렌더링과 이벤트를 소유하고, 화면 상태와 비동기 요청 검사를 분리한다. 기존 한국어 문구·CSS·반응형 배치·동작 계약을 우선 유지한다. 설치 버전은 실제 `web/package.json`과 잠금 파일에 고정하며, 이 문서가 특정 버전을 최신이라고 보증하지 않는다.

| 선택지 | 판단 |
|---|---|
| 기존 vanilla TypeScript 유지 | 의존성이 적고 이미 동작하지만, 사용자가 요청한 React 전환을 충족하지 않는다. DOM 전체 재생성·이벤트 재연결·입력 포커스 복구 책임도 계속 남는다. |
| React + TypeScript + Vite | 기존 정적 번들 제공과 Java `/api` 경계를 유지하면서 폼·목록·모달·원문 패널을 컴포넌트로 나눌 수 있다. 요청 경합, 오류, 접근성 검증은 직접 책임진다. |
| Next.js 등 전체 프레임워크 | 서버 렌더링·라우팅 등 추가 요구가 생기면 검토할 수 있다. 현재 인증 후 로컬 문서 도구에는 그런 요구가 확정되지 않았고, 이번 전환에 서버 렌더링 계층이나 API 중계 계층을 함께 도입할 필요가 없다. |

React 공식 문서는 일반적인 새 앱에 프레임워크 사용을 검토하도록 권하고, Vite에서 시작하는 경우 라우팅·데이터 요청 등의 설계를 직접 맡는다는 비용을 설명한다. 여기서는 이미 존재하는 Java 서비스와 작은 화면 범위를 보존한다는 프로젝트 조건에 따라 Vite를 유지한다. 모든 React 앱에서 이 구성이 더 낫다는 결론은 아니다. [React 공식 안내](https://react.dev/learn/build-a-react-app-from-scratch)

현재 세 화면은 기존처럼 앱 내부 상태로 전환한다. 새 URL 라우팅, SSR, 서버 컴포넌트, 전역 상태 라이브러리, 영속 클라이언트 캐시는 이번 전환의 필수 범위가 아니다. 화면·데이터 구성이 늘어나면 라우터와 데이터 요청 라이브러리의 도입 비용을 별도로 비교한다.

## 경계와 구성 책임

| 구성 | 책임 |
|---|---|
| 앱 상태·요청 조정 | 현재 인증 사용자, 선택 워크스페이스, 목록·검색·원문, 모달, 진행·실패 상태와 오래된 응답 차단 |
| API 모듈·타입 | `/api` 요청, cookie credentials, FormData/JSON 구분, 안전한 오류 코드·요청 ID, 기존 응답 필드 |
| 화면 컴포넌트 | 계정 폼, 탐색·검색 입력, 라이브러리·이력·검색 결과, 원문 패널, 작업별 모달 |
| 근거 표시 함수 | 검색어와 원문을 텍스트 노드로 표시, 발췌, codepoint 오프셋 검증, 최신 revision 확인 |
| Java 21 + Spring Boot | 인증·ACL, 문서 저장·변경·삭제, 청크 교체, BM25·이력·피드백의 최종 권한과 일관성 |
| Python 3.11 + uv | 데이터 준비·학습·오프라인 평가. 기존 FastAPI는 비교 참조로 보존 |

React는 서버 신원·권한 검사를 대체하지 않는다. 개발 시 Vite의 `/api` 프록시를 유지하고, production 번들은 Java가 같은 출처에서 제공하는 구조를 유지한다. Python 서비스나 subprocess를 Java의 핵심 API 뒤에 다시 넣지 않는다. M2/M3 입력·라벨·동결 결과는 변경하지 않으며 Python 실험 지연을 Java API 또는 React 화면 성능으로 옮겨 적지 않는다.

## 유지할 화면·API 계약

세부 필드와 서버 동작은 [API-CONTRACT](../API-CONTRACT.md)를 기준으로 한다.

- 인증은 서버 cookie 세션과 `credentials: 'include'`를 사용한다. 요청 본문·브라우저 저장소의 사용자 ID를 권한 근거로 보내지 않는다. 로그아웃·현재 세션 만료 시 문서·검색·원문·모달 상태를 비운다.
- 가입·로그인, 워크스페이스 생성·선택, 소유자의 기존 회원 추가를 유지한다. 회원 추가가 초대 이메일 발송인 것처럼 표시하지 않는다.
- 업로드는 multipart와 선택 제목·공개 범위를 유지한다. 최대 5MiB, UTF-8 TXT·MD·텍스트 PDF를 안내하며, HTTP 201의 `status: failed`도 처리 실패 문서로 표시한다. 재처리 버튼과 안전한 오류 설명을 보존한다.
- 목록 필터, 문서 상세, 검색·재검색, 개인 검색 이력, 결과 피드백을 유지한다. 결과는 서버 BM25가 반환한 원문 구절이며 생성 답변으로 표시하지 않는다. 표시하는 `elapsed_ms`는 서버 응답 필드다.
- 문서 소유자에게 편집·삭제·재처리 동작을 노출한다. 워크스페이스 소유자라는 이유로 타인의 private 문서 권한을 확대하지 않는다. 서버가 각 요청에서 ACL을 다시 확인한다.
- 편집은 추출된 텍스트를 수정한다. PDF 파일 자체를 재작성한다고 설명하지 않는다. 성공한 수정·재처리·삭제 후 이전 결과를 새 버전의 근거로 계속 표시하지 않는다.

## 비동기 응답과 상태 전환

응답을 받았다는 사실만으로 현재 화면을 갱신하지 않는다. 요청 시작 때의 세션·워크스페이스·작업 식별자와 완료 때의 현재 값을 비교한다. 취소 신호는 자원 절약 수단이며, 이미 완료된 응답이나 서버에 반영된 변경을 되돌리는 보증이 아니다.

| 경계 | 지켜야 할 조건 |
|---|---|
| 세션 | 시작·종료·새 로그인으로 세션 세대를 바꾼다. 이전 세션 요청의 성공·실패·401이 새 로그인 사용자의 화면을 덮거나 로그아웃시키지 않아야 한다. |
| 워크스페이스 | 선택 즉시 이전 문서·검색·원문·모달을 비우고 범위를 무효화한다. 느린 이전 목록·이력·업로드 응답을 새 공간에 넣지 않는다. |
| 목록·이력 | 같은 공간에서 중복 읽기를 해도 최신 유효 응답만 반영한다. 변경 완료 이전에 시작한 목록 응답이 수정 전 문서나 삭제 문서를 되살리지 않아야 한다. |
| 검색 | 요청별 순서를 검사한다. 검색 A 뒤 검색 B가 완료된 후 A가 돌아와도 결과·이력 표시·오류·로딩을 B 위에 덮지 않는다. |
| 원문 | 새 문서를 열기·원문 닫기·검색·문서 변경 시 이전 detail 요청을 무효화한다. 늦은 응답이 닫힌 패널을 다시 열거나 더 최근 선택을 바꾸지 않는다. |
| 모달 | 모달 종류만이 아니라 열린 인스턴스를 식별한다. A를 닫고 B를 연 뒤 A의 요청이 완료돼도 B를 닫거나 B의 오류 영역에 쓰지 않는다. |
| 변경 | 제출 중인 폼의 중복 요청을 막는다. 같은 문서의 변경 응답 순서가 뒤집혀도 최신 revision이 후퇴하거나 삭제 문서가 되살아나지 않아야 한다. 성공 시 관련 목록·상세·검색 읽기를 무효화하고 서버가 반환한 현재 문서 또는 삭제 상태를 반영한다. |
| 피드백 | 검색 ID·문서 ID와 현재 검색을 묶는다. 이전 검색의 피드백 완료가 새 결과의 버튼·메시지를 바꾸지 않는다. |

모달을 닫았다고 이미 제출한 업로드·편집·삭제가 서버에서 취소되었다고 표시하지 않는다. 서버에서 성공한 변경은 현재 세션·공간이 일치하는 경우 목록·결과를 정리하되 새 모달을 닫거나 새 선택을 강제로 바꾸지 않도록 구분한다. 나중에 돌아온 실패 메시지도 제출했던 모달이 여전히 현재 모달일 때만 그 폼에 표시한다.

문서 응답은 현재 목록과 이미 수락한 응답의 최대 revision을 기준으로 검사하고, 이 세션·워크스페이스에서 삭제가 확인된 ID를 별도로 기억한다. 이전 편집 응답이 최신 revision을 덮거나 삭제 문서를 다시 목록에 추가하지 못하게 하는 화면 정책이다. 서버 쓰기의 실행 순서를 클라이언트가 직렬화한다는 뜻은 아니다. 진행 중인 최초 목록 요청을 변경 완료 시 무효화했다면 새 목록을 다시 읽어 다른 기존 문서를 잃지 않게 한다.

이 구분은 `useRef`의 세대·순서와 컴포넌트 수명 검사, `AbortController` 등으로 구현할 수 있다. 특정 변수 이름이나 숫자 개수가 계약은 아니다. 특히 API 공통 처리에서 401을 받자마자 무조건 전역 상태를 지우면, 호출자 쪽 검사보다 먼저 새 세션을 훼손할 수 있다.

Effect는 세션 초기 확인과 브라우저 이벤트·대화상자 연동처럼 외부 시스템을 연결하는 데 사용하고 정리를 짝으로 둔다. 사용자가 제출한 업로드·편집·삭제·피드백과 검색은 명시적 이벤트에서 실행한다. 이 API의 검색 GET은 개인 이력을 저장하므로 Effect의 개발 모드 재실행으로 검색이 중복 제출되지 않아야 한다. React의 Effect 정리와 응답 순서 경합 안내, Strict Mode의 개발 중 추가 실행을 기준으로 검증한다. [useEffect](https://react.dev/reference/react/useEffect), [StrictMode](https://react.dev/reference/react/StrictMode)

## ACL과 원문 근거 안전성

1. 검색 결과를 선택하면 현재 문서를 API로 다시 읽는다. 현재 문서의 ID·revision과 반환된 chunk ID가 일치해야 정확한 근거로 표시한다. revision 또는 청크가 달라지면 최신 원문과 재검색 안내를 보여준다.
2. 원문 위치는 `Array.from(content)`로 codepoint 기준 구간을 만들고 `chunk.text`와 일치하는지 확인한다. 일치하지 않으면 잘못된 위치를 강조하거나 이동 버튼으로 연결하지 않는다. 이모지·결합문자를 포함한 검증 사례를 둔다.
3. 제목·파일명·본문·질문·회원 이름·오류는 JSX 텍스트로 렌더링한다. 검색어는 정규식 문자를 escape하고 강조 조각도 텍스트 노드로 만든다. 업로드 HTML을 `innerHTML`이나 `dangerouslySetInnerHTML`로 실행하지 않는다.
4. 현재 문서 재조회가 403/404로 실패하면 해당 원문과 로컬 목록·검색 결과를 제거한다. 오래된 읽기가 이를 다시 넣지 못하도록 관련 요청도 무효화한다. API 오류 본문을 그대로 사용자 메시지나 로그에 출력하지 않는다.
5. 브라우저 상태의 캐시는 서버 ACL을 대체하지 않는다. 다른 사용자가 공개 범위를 바꾼 즉시 이미 내려받은 텍스트를 회수하는 실시간 권한 알림은 이번 전환에서 새로 제공하지 않는다. 다음 요청에서 서버 권한과 최신 revision을 확인하는 계약을 유지한다.

## 검증 조건

아래는 필요한 회귀 범위이며 표 자체가 검증 성공의 증거는 아니다. 자동 검사에는 합성 계정·문서를 쓰고 결과와 사용자 검수를 구분한다. 실제 실행 명령·결과·누락은 상태·기여 기록에서 확인한다.

| 검증 | 확인할 결과 |
|---|---|
| 타입 검사·production build | React TSX와 실제 정적 번들 생성, Java의 번들 제공 경로 유지 |
| 실제 Java API 브라우저 흐름 | 가입·로그인·로그아웃·재접속, 공간 생성·전환, 파일 업로드·검색·원문·편집·삭제·이력·피드백이 기존 계약으로 작동 |
| 두 계정 ACL | private 문서 비노출, 공유 멤버 읽기, 타인 편집·삭제 불가, 권한 변경 후 상세 거부와 화면 정리 |
| 원문·입력 안전성 | HTML 태그를 포함한 원문이 텍스트로 남음, 정규식 특수문자 질문, 이모지 offset, 최신 revision 불일치 경고 |
| 느린 응답 경합 | 역순 검색·detail, 원문 닫기, 공간 전환, 초기 목록 중 검색·업로드, 변경 후 구 목록·구 revision, 삭제 후 늦은 편집 응답, 모달 교체, 로그아웃 후 새 로그인과 오래된 401 |
| 실패와 재시도 | 업로드 크기/형식 제한, `failed` 문서와 재처리, 네트워크·401·403·404 오류, 중복 제출 방지 |

Mocked 응답 순서 검사는 브라우저 상태 경합의 자동 증거이며 실제 Java 인증·ACL 검증과 구분한다. 자동 브라우저 동작·화면 확인도 사용자 사용성 검수나 모델 품질 검증으로 부르지 않는다.

## 결과와 재검토 조건

폼과 패널을 명시적 상태로 표현하고 DOM 전체 교체와 이벤트 재연결을 줄일 수 있다. 대신 React 런타임·타입 의존성이 추가되고, 작은 앱이라도 비동기 상태·접근성을 설계해야 한다. 번들 크기나 응답 속도가 좋아졌다는 결론은 별도 측정 없이 내리지 않는다.

공유 가능한 URL 탐색, 많은 서버 데이터의 캐시, 공개 콘텐츠의 검색엔진 노출, 서버 렌더링 요구가 생기면 라우터·데이터 라이브러리·프레임워크 선택을 재검토한다. 이번 전환은 Java 모델 연결·생성 답변·학습·공개 배포를 완료한 것으로 계산하지 않는다.
