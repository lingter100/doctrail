# 회의 Q&A 인용 구조 후속 제안

작성일: 2026-10-13. 상태: **설계 제안만 작성, 구현·모델 실행·채택 없음**.

이 문서는 실패한 9B 후보의 게이트를 통과시킨 기록이 아니다. 1.7B, 4B, evidence-first v2, decoder-only 비교와 9B의 소스·계획·원본 출력·실패를 그대로 보존한다. 현재 자연어 RAG 품질은 완료되지 않았다. 신규 검증 자료는 열지 않았으며, 이 제안서 작성으로 알려진 네 사례나 독립 검증의 재실행을 승인하지 않는다. 후속 구조 구현과 실행 계획은 별도 묶음이다. 유료 API 실행·승인, GPU 임대, 외부 서비스 배포는 모두 0이다.

## 해결하려는 문제와 남는 문제

9B의 알려진 사례에서 모델이 Markdown 표시를 빼거나 곡선 아포스트로피를 바꾸어 정확한 인용 검사를 실패했다. 질문의 한 부분을 놓치거나, 선택한 인용으로 뒷받침되지 않는 이유를 답변에 더한 문제도 남았다. 앞선 4B에서는 JSON 문법을 제한한 뒤에도 잘못된 출처 ID와 서로 떨어진 문장을 합친 인용이 남았다. 이 구분은 부모가 확인한 실행 결과를 바탕으로 하며 이 설계 작업에서 데이터 파일을 다시 읽거나 평가하지 않았다.

제안은 **모델이 원문 인용을 다시 쓰지 않게 하는 것**이다. 생성 모델은 짧은 자연어 주장과 요청 안의 구간 ID만 반환하고, 추론 어댑터가 원문 인용과 위치를 복사한다. 모델의 문장 생성 책임은 유지한다. 발췌 목록을 자연어 답변 성공으로 바꾸지 않는다.

| 실패 종류 | 구조가 직접 바꾸는 것 | 여전히 필요한 판정 |
|---|---|---|
| Markdown·따옴표·공백을 바꾼 인용 | 모델 출력에서 quote를 제거하고 원문에서 복사 | 원문·Unicode 위치의 결정적 일치 검사 |
| 서로 떨어진 문장을 합친 quote | 각 ID가 하나의 연속 원문 구간만 가리킴 | 여러 구간이 필요하면 각각 인용해야 함 |
| 다른 문서·구간의 ID 선택 | 더 좁은 구간을 명시적으로 식별 | 그 구간이 주장을 지지하는지는 의미 검토 필요 |
| 회의일을 사건 발생일로 바꿈 | 자동 해결하지 않음 | 날짜·시제·확정 상태의 의미 검토 |
| 질문 일부 누락, 근거 없는 이유 추가 | 자동 해결하지 않음 | 질문 전체의 완전성과 주장별 지지 검토 |

이미 큰 청크에 정수 ID를 붙이는 방식을 사용했고 의미 오류가 발생했다. 따라서 “ID를 사용하면 해결된다”는 새 주장을 하지 않는다. 이번에 시험할 차이는 **더 좁고 변경할 수 없는 원문 구간 목록과 원문 복사**다. 이 차이만으로 더 나은 의미 품질을 보장할 수 없다.

## 최소 변경안: 추론 어댑터 내부 구간 목록

[Phase 1 설계](MEETINGS-DESIGN.md)의 기존 경계를 유지한다. Java는 세션·ACL·검색·현재 리비전·최종 응답 검증을 맡고, Python은 승인된 컨텍스트의 모델 입력 구성과 모델 출력 해석만 맡는다.

1. Java가 현재 사용자의 권한으로 선택한 기존 `contexts`를 전달한다. 검색 방식·후보 수·순서·문서 필터를 이 제안에서 바꾸지 않는다.
2. Python 추론 어댑터가 요청 안에서만 사용하는 읽기 전용 구간 목록을 만든다. 각 항목은 `span_id`, 기존 `chunk_id`, 원문 문자열, 문서 절대 code point 시작/끝 위치와 현재 리비전에 연결된다.
3. 모델에는 모든 컨텍스트를 원래 순서대로 공급하면서 각 구간에 ID를 붙인다. 제목·회의일·구간 본문은 자료이며 지시가 아니라는 기존 경계를 유지한다.
4. 모델은 기존 `status: answered|abstained`와 `claims` 구조를 유지하고 각 주장의 `evidence_ids`를 먼저, `text`를 다음에 생성한다. answered는 1~6개 주장, abstained는 빈 claims다. 원문 quote, 문서 UUID, offset을 생성하지 않는다. 고정 JSON 문법은 필드·타입·개수와 실제 요청의 인용 가능한 ID 집합만 제한하며 정답 ID를 강제하지 않는다.
5. 어댑터가 각 ID에 연결된 원문·위치를 복사해 **기존 응답의 `chunk_id`, `quote`, `start_offset`, `end_offset`**으로 반환한다.
6. Java가 현재 문서·청크·리비전·접근권한으로 기존 최종 검사를 다시 수행한다. 요청 도중 변경된 결과를 기존 정책대로 폐기한다.

구간 목록은 입력에서 만든 요청별 불변 값이다. 다른 요청의 목록을 재사용하거나, 모델의 응답으로 목록을 수정하거나, 결과를 맞추기 위해 ID를 바꾸지 않는다. 동일한 문장이 여러 곳에 있어도 각 위치는 별도 ID다. 숫자 ID는 요청 안에서만 의미가 있다. 다른 요청의 목록 객체·좌표를 재사용하는 오류는 검사하지만, 두 요청에 같은 숫자가 존재할 때 모델이 잘못 고른 유효한 숫자를 구조 검사로 알아낼 수 있다고 주장하지 않는다. 일부 내용을 조용히 버리는 검색·중복 제거·언어별 제외를 추가하지 않는다.

이는 Java 핵심 기능을 Python으로 옮기는 작업이 아니다. 기존에 모델 입력을 직렬화하고 출처 응답을 구성하던 추론 어댑터의 책임을 좁게 바꾸는 안이다. Python이 문서 접근권한·최신 리비전·결정 변경 관계를 판단하거나 DB를 읽지 않는다.

### Java 신규 DTO를 먼저 만들 필요가 없는 이유

| 구현 위치 | 변경 범위 | 초기 판단 |
|---|---|---|
| Python 어댑터 내부 목록, 기존 인용 응답 유지 | 새 추론 어댑터·parser·문법·테스트·실행기 | **권고**. 기존 Java 최종 검증과 React 인용 표시를 재사용 |
| Java가 구간 목록을 생성하고 worker DTO도 변경 | Java/worker 양쪽 새 계약, 호환 처리와 추가 회귀 | 초기에는 불필요. 저장된 구간 ID를 외부에 영구 제공하는 요구가 생길 때 재검토 |

최종 Java 검사에서 워커가 반환한 구간이 전달된 청크 안에 있고 현재 원문과 일치하는지 확인한다는 기존 계약이 재사용의 전제다. 구현 전에 실제 코드·회귀 검사로 이 전제를 확인해야 한다. 확인되지 않는 검사 공백이 발견되면 그 검사만 보완하고, 편의를 이유로 워커 응답을 신뢰하거나 DTO 전체를 새로 설계하지 않는다. 새로운 DB 테이블·벡터 DB·메시지 브로커·공개 API는 초기안에 포함하지 않는다.

## 구간 생성과 유한 예산

첫 후보의 분할 알고리즘은 모델 응답이나 질문 정답을 보지 않고 미리 고정한다.

- 문서 전체를 다시 정제하지 않고 전달된 청크 문자열의 연속 범위만 사용한다. Unicode code point 위치를 사용하며 Markdown, 따옴표, 공백, 줄바꿈을 정규화하지 않는다.
- Python `splitlines(keepends=True)`의 줄 경계를 사용한다. 한 줄이 480 code points를 넘으면 남은 문자열의 첫 480 code points 안에서 `isspace()`가 참인 마지막 문자 직후에 나누고, 없으면 480 code points에서 나눈다. 남은 문자열에 같은 규칙을 반복한다. 경계의 문자와 공백도 보존하며 빈 문자열 구간은 만들지 않는다. 원문 청크가 문장 중간에서 시작하면 그 사실을 그대로 유지하며 완전한 문장이라고 표시하지 않는다.
- 각 청크의 구간은 겹치거나 빠지는 문자가 없어야 한다. 구간을 순서대로 연결한 결과가 입력 청크와 정확히 같아야 한다. 여러 청크 자체의 중복은 기존 검색 결과 그대로 보존한다.
- ID는 요청의 청크 순서와 구간 순서로 `0..N-1`을 부여한다. 공백·줄바꿈만 있는 비어 있지 않은 구간도 목록과 160개 상한에 포함해 전체 문자 보존을 검사하되, C0의 명시적 nonblank 인용 조건에 따라 인용 가능한 ID에서는 제외한다. 기존 Java는 문자열 길이·원문 좌표를 검사하므로 이 조건은 C0에서 더 엄격하게 적용하는 것이다. 한 주장에 필요한 내용이 경계를 넘으면 여러 ID를 인용할 수 있다. 인접 구간을 모델 출력에 맞춰 사후 병합하지 않는다.
- 최대 10개 청크, 160개 구간, 전체 prompt 4,096 tokens, 출력 768 tokens, 요청 120초, 동시 생성 1개라는 유한 조건을 사전 고정한다. 어떤 상한도 조용한 잘림으로 만족시키지 않는다. 초과하면 모델 호출 전 명시적 오류다.
- 한 답변은 최대 6개 원자적 주장, 각 주장은 1~4개 ID다. 한 주장 안의 중복 ID·알 수 없는 ID·공백 전용 구간 ID는 거부한다. 여러 주장이 같은 근거를 각각 사용하는 것까지 금지하지는 않는다. 유효한 ID를 반환해도 관련성·의미 지지·완전성이 보장된다고 표시하지 않는다.

480과 160은 아직 실측으로 통과한 값이 아니다. 새 독립 자료를 보기 전에 모델 없는 경계·토큰 준비 검사로 적합성을 확인하고 최종 값을 동결해야 한다. 검증 자료의 정답을 보고 구간 크기·개수·토큰 상한을 바꾸지 않는다. 모델 native context6144 안에 입력4096·출력768이 들어간다는 산술 조건과 실제 메모리·지연 통과는 별개다.

## 자연어 주장과 의미 검증

모델이 작성한 주장에는 여전히 잘못된 이유·시제·대상·결정 상태가 섞일 수 있다. 정확한 인용은 필요한 조건이며 충분한 조건이 아니다. 주장에 포함된 모든 사실은 그 주장에 연결된 구간들이 지지해야 한다. 다른 컨텍스트 어딘가에 관련 문장이 있다는 이유로 현재 주장의 잘못된 인용을 인정하지 않는다.

초기안은 생성 요청 한 번만 사용한다. 동일 모델에게 다시 “맞는지” 물어본 결과를 독립된 검증으로 표시하지 않으며, 새로운 의미 검증 모델이나 자동 재작성 루프를 추가하지 않는다. **이 제안의 의미 검증은 동결 후 별도 검토자가 수행하는 평가 게이트다. 요청마다 의미적 참을 보증하는 runtime 검증기를 구현했다는 뜻이 아니다.** 운영 메타데이터에도 문자열 검사를 의미 검증 성공으로 바꾸어 넣지 않는다.

자연어 답변 요구는 유지한다. 질문의 모든 부분을 근거와 함께 답해야 하며, 보류가 필요한 경우도 구분해야 한다. 모든 질문에 보류하거나 원문 목록만 반환하는 방식은 통과하지 못한다. 생성 실패 시 관련 원문을 보여줄 수는 있지만 “관련 원문 발췌”로 분리하고 자연어 답변 성공으로 집계하지 않는다.

## 사전 등록과 봉인 자료 평가 제안

현재 9B 후보는 실패로 종료한 상태이고 원래 계획의 검증 실행은 blocked로 보존한다. 이 문서는 그 모델의 자동 채택, 기존 실패 게이트의 완화 또는 새 검증 실행 명령이 아니다. 후속 구현을 진행하더라도 **구조 후보 C0**를 새 진입점·새 계획·새 결과 경로로 만든다. 완료된 실험의 bound source나 결과를 덮어쓰지 않는다. 부모가 다음 별도 묶음에서 무료 C0 구현을 진행하겠다고 전달했으며, 이 설계 역할은 문서 작성만 수행한다.

### 실행 전에 고정할 것

1. 새 구현의 정확한 Git commit, 모든 바인딩 파일 hash, 구간 알고리즘, 새 모델 출력 계약과 JSON 문법, 인용 복원기, 오류 코드, 위의 개수·토큰·시간 상한을 등록한다.
2. 기존 9B의 실제 가중치·양자화·runtime·GPU 적재 설정을 그대로 식별한다. 이 구조 비교에서 새 모델·새 예시·새 검색 정책·새 샘플링 탐색을 추가하지 않는다. 기존 v2의 의미 제약은 유지하며 출력 계약 변경에 필요한 문장만 변경하고 차이를 기록한다.
3. 근거 부족 보류, 구조/참조 오류, 의미 실패, 시간 초과를 별도 결과로 기록한다. 재시도0이며 JSON·ID·주장을 사후 수정하지 않는다.
4. 모델 없는 검사와 준비 검사를 먼저 통과시킨다. 완료된 4B 회의 분석과 작업 기능을 C0의 생성 품질로 합산하지 않는다. 초기 서비스 분석 경로를 바꾸지 않으며 4B·9B를 GPU에 동시에 적재하지 않는다.

### 이미 준비된 12항목을 사용할 조건

자료 수를 불필요하게 늘리지 않고 **기존 봉인 12항목**을 C0의 별도 계획에 명시적으로 연결할 수 있다. 부모의 현재 확인은 개발 부모·구현자가 계속 자료에 blind이고 모델 호출0이라는 것이다. 이 설계자는 질문·원문·정답·의미 검토 설명을 읽지 않았다. 실제 실행 전에는 격리된 custodian이 다음 조건을 내용 노출 없이 확인해야 한다.

- 원래 9B 계획과 자료 manifest의 hash·작성 시점·자료별 출처·사전 검토가 보존되어 있고, 이후 질문·정답·원문이 바뀌지 않았는지 확인한다. 실제 모델 출력에 맞춘 oracle 수정은 없다.
- 부모·구현자·C0 정책 설계자가 봉인 항목의 내용을 읽거나 그 항목의 모델 결과를 본 적이 없고, 원래 검증의 모델 호출이 0인지 확인한다. 단순 항목 수·언어 구성 같은 내용 없는 metadata 조회와 본문 접근을 구분한다.
- 기존 manifest의 공개/합성, 언어, 답변 가능/보류 필요 항목 수를 내용 없이 보고한다. 이 문서는 실제 pool의 세부 구성을 열람하지 않았으므로 임의의 8/4 같은 숫자를 실제 구성으로 단정하지 않는다. 기존 oracle의 필수 사실·허용 대체 근거·보류 기준을 그대로 연결한다.
- 현재 자료의 공개 URL·revision·라이선스·가공 hash와 의미 검토 기준이 실행 가능한 상태인지 확인한다. 자료 오류나 사전 누출이 있으면 검증 실행을 멈추고 별도 감사 기록을 남긴다. C0에 맞게 조용히 자료를 고쳐 사용하지 않는다.

이는 **자료 작성보다 먼저 C0를 등록한 평가가 아니다.** 봉인 자료는 이전 9B 후보용으로 먼저 작성됐고, C0는 알려진 개발 사례의 후보 실패를 본 뒤 선택했다. 이 정책 변경 시점과 이유를 새 계획에 기록한다. 위 조건이 성립하면 봉인 본문과 출력에 맞춘 튜닝은 없다는 제한된 의미에서 검증용으로 유지할 수 있지만, 무작위 benchmark나 모든 개발 선택으로부터 독립된 평가라고 주장하지 않는다. AI가 만든 과제·oracle와 AI 의미 검토의 공통 편향도 남는다.

### 실행 순서와 한도

1. 모델 없는 구조·호환 검사와 내용에 의존하지 않는 중립 runtime control을 통과시킨다. runtime control은 별도 인위적 입력 최대2회로 한정하고 알려진 네 사례나 봉인 자료에서 가져오지 않는다. 그 입력·목적·통과 기준·횟수 상한은 첫 모델 호출 전에 등록한다. 출력의 사실 선택을 보고 의미 지침을 조정하는 경로가 아니며 구조·자원 확인용으로만 사용하고 품질 성공 건수에 합산하지 않는다.
2. C0의 코드·정책·통과 조건과 봉인 pool manifest를 **새 C0 계획에 바인딩해 동결**한다. 원래 9B 계획의 blocked 상태·실패 결과는 그대로 남긴다. 자료 구성 metadata와 기준을 확인하는 custodian 외에는 봉인 내용을 열지 않는다.
3. 알려진 네 사례를 C0의 개발 회귀 게이트로 각각 한 번 실행한다. 기존 실패 모델의 원본을 재실행하거나 성공으로 바꾸는 작업이 아니다. 하나라도 아래 게이트를 실패하면 C0를 종료하고 봉인 검증 호출은 0으로 남긴다.
4. 네 사례 전체가 통과한 경우에만 봉인 12항목을 각각 한 번 실행한다. 총 품질 호출 상한16회, 중립 control을 포함한 전체 모델 호출 상한18회, 재시도0이다. 이번 문서 작성 중에는 이 순서의 어느 모델 호출도 수행하지 않는다.
5. 의미 검토자는 구현에 참여하지 않은 역할로 원문·질문·선택 구간·주장을 함께 검토한다. 모델 정체·이전 후보 결과·알려진 네 사례의 통과 여부를 검토 입력에서 가능한 한 가리고 기존 oracle로 판정한다. 리뷰가 끝나기 전에 실패 항목을 제외하거나 프롬프트·구간·정답을 수정하지 않는다.

부모가 알려진 후보 실패 결과를 보았다는 사실과 별도 검토자가 후보 출력을 읽고 평가한다는 사실은 숨기지 않는다. 검토자는 새 출력을 볼 수밖에 있지만 판정 규칙과 oracle를 보고 난 뒤 바꿀 수 없다. custodian과 검토자가 같은 역할이면 그 비독립성도 기록하며 인간 검수로 계산하지 않는다. 모델 없는 소프트웨어 결함과 품질 실패를 구분하되, 실제 known4를 본 뒤 수정해 다시 실행하는 경로를 자동으로 열지 않는다.

기존 실패 모델을 봉인 자료에 다시 실행하지 않는 최소안이다. 따라서 12항목 결과로 모델 간 향상률을 주장하지 않는다. 비교 가능한 알려진 네 사례의 회복·퇴보와 C0의 봉인 검증 통과 여부만 구분해서 보고한다. 본문이나 결과가 개발자에게 공개된 뒤 그 자료를 수정에 사용하면 이후에는 개발 자료로 표시하고 독립 평가라고 재사용하지 않는다. M5-B와 최종 test는 이 계획과 무관하게 계속 잠근다.

참조 가능한 원문을 보여줬다는 이유로 관련 없는 주장을 허용하지 않는다. 원문 선택이 정확해도 질문의 일부만 답하면 완전성 실패다. 구조 오류가 의미 검토를 막으면 품질 성공으로 계산하지 않는다. 12건 모두 통과해도 작은 공개/합성 검증에 대한 결과이며 넓은 운영 정확도나 인간 검수를 입증하지 않는다.

첫 C0가 실패하면 known4에 맞춘 예시·문자열 규칙·새 모델 시도를 이어 붙이지 않는다. 실패 유형과 기존에 동작하는 회의 분석·작업·검색 기능을 나누어 보고한다. 자연어 답변은 미완료로 남긴다. 유료 API 비교는 정확한 제공자·모델·전송 자료·요청 수·비용 상한을 갖춘 별도 제안과 사용자 승인 뒤에만 가능하며, 현재 제안서나 로컬 구현 승인이 유료 호출 승인으로 바뀌지 않는다.
