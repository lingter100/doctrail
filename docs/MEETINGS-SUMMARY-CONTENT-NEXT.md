# 회의 요약 내용 개선의 다음 후보와 선행 판단

2026-10-26. **다음 단계는 새 개발 원문4개에서 한정명제 표현이 충분한 요약을 담을 수 있는지 출력 전에 한 번 확인하는 일이다.** 통과할 때만 아래의 작은 생성 후보를 구현 대상으로 삼는다. 원자적 필드를 추가하면 정확해진다는 결론은 아직 근거가 없다. 이 문서는 설계 제안이며 구현·자료 수집·tokenizer·모델·Java 실행 권한을 부여하지 않는다. 부모 수용과 각 단계의 별도 배정이 필요하다.

## 판단 근거

- [유효 초안 독립 판단](../experiments/results/meetings-summary-mode-review-v2.json)은 초안1·주장5·정확 인용20에서 원문전체 지원1/부분4, 선택근거 지원0/부분5, 핵심 불충분1이다. 한국어 가독성은 통과했지만 완전한 요약은0이다. [구조 진단](../experiments/results/meetings-summary-mode-structural-diagnosis-v2.json)은 별도 응답의 유효·고유 ID 순서 위반이며 parser 결함이나 의미 판단이 아니다.
- 잠긴 판단의 안전 taxonomy는 관계·목적 오류3/5, 시점·상태·기간 오류3/5, 선택근거 구성요소 누락2/5다. 중첩8개가 주장5개에 해당하며 합산 오류율이 아니다. 내용1개를 보고 얻은 가설 근거이지 일반 모델 성능이나 전체 오류 빈도가 아니다.
- 잠금 후 자기검토 대조에서 모델은5/5 supported·coverage sufficient였으나 독립 판단은 위와 같았다. 검토 accepted는 의미 품질 보증이 아니다. 유효 쌍이 없으므로 thinking 효과·승자·회복률은 판단할 수 없다.
- [관계 v2](MEETINGS-GROUNDED-SUMMARY-NEXT.md)는 원문 unit 사이의 관계 graph와 자유 문장을 같은 호출에서 만들었다. [재작성 v3](MEETINGS-SUMMARY-CLAIM-ALIGNMENT-PLAN.md)는 전체 원문을 다시 읽고 최종 문장을 고치는 호출을 추가했지만, [후속 분석](MEETINGS-SUMMARY-QUALITY-NEXT.md)의 같은 요청3쌍은 핵심 충분0/3→0/3이었다. 표본이 다른 v1/v2/v3의 숫자를 개선율로 합치지 않는다.
- 현재 생성 지시에는 이미 조건·예외·상태·기간 보존과 충분하지 않으면 abstain이 들어 있다. 따라서 같은 지시를 더 강하게 쓰거나 인용 ID를 정렬하는 것만으로 내용 개선을 설명할 수 없다.

선택은 조건부다. 새 표현도 충분한 내용을 담지 못하면 또 하나의 prompt 실험을 시작하지 않는다. 소스 선택·표현·번역 중 무엇이 제한하는지 확인되지 않은 채 생성 호출을 반복하는 비용을 피한다.

## 먼저 해결할 질문: 충분하고 읽을 만한 내용을 이 표현에 담을 수 있는가

1. 별도 자료 담당이 **새로 수용한 개발 원문4개**를 먼저 고정한다. 기존 mode4·grounded 개발 자료·관측된 초안과 같은 원문/개정판/가족을 재사용하지 않는다. 길이만 짧거나 조건이 단순한 자료로 맞추지 않고, 제안과 결정, 진행/완료, 명시적 기간, 흩어진 조건·예외·후속조치가 포함되는 범위를 출력 전에 정한다. 라이선스·동일/근접 문서·가족·노출 이력과 현재 보호 split을 기존 provenance 경계로 확인한다. 과거 L2 노출의 불명확성을 새 수용으로 지우지 않는다.
2. 원문을 볼 수 있는 지정 담당이 각 원문에서 필요한 핵심과 상태·시간·조건을 source-only로 고정한다. 이어 아래 표현과 기존 flat 표현 각각에 충분한 한국어 요약을 담을 수 있는지 witness를 한 번 작성한다. 이는 로컬 모델 출력이나 학습 정답이 아니라 표현 가능성의 사전 증거다. witness/문서별 기준/원문은 그 담당의 private 영역에 두며 부모·설계자·구현자에게는 hash와 가능/불가능/미확인 집계, 제한 원인만 반환한다. 개발 예시로 prompt에 넣지 않는다.
3. 비교 한도는 양쪽 모두 주장1–6, 각240/합1200 Unicode code point, 주장별 전체 근거 합집합1–4개다. 한정명제의 필드도 최종 문구 예산 안에 포함한다. 기존 flat은 가능한데 새 표현만 불가능하면 새 표현을 버린다. 양쪽 모두 불가능하면 모델 변경의 근거로 삼지 않고 출력 표현력 제한을 부모에게 보고한다. 문서 교체·핵심 삭제·불충분을 충분으로 바꾸는 조정은 없다.
4. 원문4개 모두 충분하고 자연스러운 한국어로 표현 가능하다는 근거가 있어야 작은 구현을 제안한다. 어려운 사례가 미확인이라면 그 이유를 남기고 실제 모델 실행은 보류한다. 새 모델을 돌리기 전에 해결할 질문은 하나이며, 무한 진단·새 validator·대량 checklist를 만들지 않는다.
5. 이 검토는 모델이 그렇게 생성한다는 증거가 아니다. 실제 tokenizer의 template 포함 비용, 생성 능력, 지연·메모리는 아직 미확인으로 남는다. source-only 담당/최종 판단자와 설계·구현 역할을 분리하며, 노출을 기록하고 완전한 blind를 주장하지 않는다. 설계자는 후속 독립 의미 판단자가 아니다.

## 조건부 후보의 원문→출력 계약

후보명은 prospective qualified-summary-v1로 구분한다. 현 서비스의 v1/v2/v3나 닫힌 mode 계약을 고쳐 부르지 않는다. 대상 실패 가설은 “선택한 한정 정보를 자유 문장 합성에서 잃거나 잘못 결합한다”이며, 애초 원문을 잘못 읽는 문제까지 해결한다고 주장하지 않는다.

- 입력은 기존 source_payload의 제목·모든 unit·gap과 정확한 전체 원문이다. 분류 label이나 선택 인용으로 읽을 범위를 제한하지 않는다. 원문과 생성 필드는 모두 untrusted data다.
- 생성은 한 번이다. 각 주장에는 하나의 사건/판단을 나타내는 core와, 필요한 status·time·condition·relation 문구를 순서 있는 parts로 둔다. 각 part는 kind, 최종 한국어 text, 그 문구의 evidence unit ID 목록만 가진다. core는 정확히1개, 다른 kind는 각각0–1개, parts 최대5개이며 빈 placeholder는 없다. relation은 목적·원인 등을 실제로 서술할 때만 쓴다. 조건·예외를 함께 담거나 표현이 더 필요한 경우에도 최종 한도 안에서 충분해야 하며, 필드 슬롯에 맞춰 사실을 버리지 않는다.
- status의 제안/결정/진행/완료와 time의 기간·적용 범위는 최종 독자가 읽는 한국어 문구다. 별도 상태 enum을 자동 사실로 취급하거나 날짜 크기로 현재 상태를 선택하지 않는다. 모호하면 모호함을 문구에 보존한다. 생략된 kind는 “원문에 그 정보가 없다”는 기계 판정이 아니다.
- **최종 text는 parts의 text를 순서대로 공백 하나로 연결한 값만 허용한다.** 별도의 final_text, 마지막 자유 재작성, 새 연결어 삽입, 문장 병합·삭제는 없다. 순서는 한국어 문장이 자연스럽도록 생성하지만 투영 단계는 의미를 바꾸지 않는다. 기계 필드명과 근거 목록을 제품 문장에 노출하지 않는다.
- 모든 part의 evidence는 실제 bound unit의 유효·고유 ID1–4개이며 각 주장의 합집합도1–4개다. 최종 citations는 합집합을 원문 순서로 파생한다. 같은 ID가 서로 다른 part를 지원할 수 있으나 part 내부의 중복은 오류다. 이는 여러 목록의 계약상 합집합이며, 잘못된 입력 중복을 제거해 살리는 복구가 아니다.
- core가 이미 “완료했다”고 잘못 말하고 status가 “제안”이라고 쓰는 모순, 잘못 붙인 조건, 거짓 목적, 없는 time, 중요한 part의 통째 누락은 여전히 발생할 수 있다. kind와 연결 보존만으로 atomicity·지원·충분성을 증명하지 않는다. 단어 blacklist로 이런 의미 오류를 기계 판정하지 않는다.
- 필수 마지막 검토는 전체 원문과 실제 최종 claims/evidence만 받는다. 구조가 잘 갖춰졌다는 설명을 주거나 같은 모델의 계획을 권위로 내세우지 않는다. 기존 REVIEW_PROMPT/REVIEW_GRAMMAR/parse_review의 모든 주장 supported + coverage sufficient 조건을 유지한다. 검토1회 뒤 거부·불확정이면 실패이며 repair0이다.
- 원문/선택근거 지원·핵심 충분성은 이후 독립 판단에서 다시 확인한다. 기계적으로 보장하는 범위는 “출력한 한정 문구와 연결된 근거를 투영 단계가 누락·변경하지 않았다”까지다. v2 graph와의 차이는 관계 목록을 추가하는 것보다 **최종 내용의 단일 표현과 무손실 투영**에 있고, v3와의 차이는 자유 재작성 호출이 없다는 점이다.

이 표현에서 자연스러운 한국어·충분성을 동시에 만족하지 못하면 후보를 선택하지 않는다. labels가 있는 보고서나 적게 말한 답변을 완전한 회의 요약의 대체 성과로 세지 않는다.

## 인용 순서 정규화는 별도 변경

새 계약에서만 strict JSON·정확한 필드·유효 span을 검증한 뒤, flat evidence의 유효하고 고유한 정수 ID 집합을 복사본에서 정렬할 수 있다. bool/float/숫자문자열·중복·범위 밖·공백 unit·모호한 매핑·좌표 불일치는 정렬 전에 거부한다. 원본 생성 bytes와 원래→정규 배열은 보존하고, text·claim 순서·근거 구성원은 바꾸지 않는다. 이후 기존 strict parser와 의미 검토를 거친다. 새 비교의 모든 arm에 같은 사전 규칙을 적용한다. part 합집합의 파생과 flat 목록의 입력 정규화는 각각의 계약대로 검사한다.

이 정규화는 표현상 거부만 줄일 수 있다. 현재 소비된 B를 고치거나 다시 실행하지 않으며, 내용 개선·parser 결함 수정·유효 쌍 확보로 보고하지 않는다. 순서가 의미인 relation 방향이나 parts 문구 순서는 정렬하지 않는다.

## 예산과 가장 작은 구현 경계

- 현재 서비스 전체 분석120초를 유지한다. 새 후보도 생성1회+필수 검토1회, generation768/review128, 실제 template 포함 입력4096, 마지막 EOS와 동일 공유 deadline을 우선 계약으로 삼는다. 분류·관측·준비 시간도 같은 분석 기한에 포함하며 재시작하지 않는다. thinking·모델·GPU layer·cache·sampling을 동시에 바꾸지 않는다.

## 의미 있는 합성 검사

1. 한 사건의 제안/결정·진행/완료·기간·조건이 들어 있는 generic parts를 투영했을 때 모든 문자·순서·근거가 유지되고 최종 claims/legacy projection이 일치하는지 검사한다. 서로 다른 사건/범위와 상충 문구를 섞은 fake 출력은 의미 거부 경로로 끝나는지 확인한다. mock이 정답을 반환했다는 이유로 실제 해석 성공을 주장하지 않는다.
2. repeated quote의 서로 다른 full-span identity, 타 part만 뒷받침하는 unit, 잘못된 ID·중복·bool·float·범위·빈 unit, missing/duplicate core·unknown kind·extra field·invalid Unicode를 검사한다. 한 part의 목록과 전체 합집합의 차이를 검증하고 5 parts/6 claims/4 evidence 경계와 최종240/1200 초과를 실제로 거부한다.
3. 같은 유효 flat ID 집합의 순열은 text·membership·좌표가 같고 정렬은 멱등이어야 한다. 중복이나 잘못된 ID는 정렬로 살아나지 않아야 한다. 새 후보를 쓰지 않는 기존 parser는 unsorted ID를 계속 거부해야 한다. 원본 bytes와 로그가 바뀌지 않는지도 확인한다.
4. source의 모든 unit/gap이 생성·검토 입력에 남고, 실제 최종 투영만 검토된다는 것을 확인한다. coverage insufficient/uncertain 또는 한 주장 unsupported/uncertain에서 저장0·후속 호출0을 검사한다. 연결 단계에서는 입력/EOS/deadline/observer 실패도 동일하게 확인하고 generation→review 외 repair/재작성/fallback이 없음을 검사한다.
