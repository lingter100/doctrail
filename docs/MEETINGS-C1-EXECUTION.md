# C1 실행·독립 검토 절차

2026-10-13. 후보 구현과 자료 가족은 `82b0fff`에서 먼저 고정했다. 이 문서는 이후 작성한 calibration의 실행 준비와 결과 해석 절차다. 실제 실행 상태·수치는 STATUS와 결과 파일을 따른다.

## 실행 전

- `meetings-c1-source-freeze-v1.json`의 46파일은 바꾸지 않는다. 기존 C0와 M5-B, 노출된 12문항도 재실행하지 않는다.
- 자료 작성자는 고정된 네 가족에서 8문항을 작성하고 필수 사실·정확한 대체 인용·금지 추론을 별도 oracle에 저장한다. 별도의 AI가 실행 전에 이를 검토한다. 사용자 검수는 0이다.
- 입력·oracle·검토·새 도구의 해시와 문항 순서를 실행 계획에 고정한다. 중립 2문항과 calibration 8문항이 같은 계획에 들어간 뒤 native 실행을 시작한다.
- 토크나이저 준비 검사는 모델 생성이 아니다. 정해진 입력과 추가 검토·수정 공간을 확인하며 실제 단계별 입력은 native에서 다시 계수한다. 한도 초과를 발견해도 원문을 조용히 잘라 넣지 않는다.
- 출력 디렉터리는 최초 시도에 선점한다. 오류가 나도 삭제하거나 다른 디렉터리로 같은 단계를 다시 실행하지 않는다.

## 답변의 독립 검토

`prepare_meeting_review_audit`는 각 문항의 첫 D0와 최종 C1을 별도 모델 호출 없이 복원한다. 원문의 인용과 위치는 고정된 mapper로 복원하며 C1의 의미 거부는 정상 보류로 바꾸지 않는다.

실행 전에 로컬 무작위 seed의 SHA256을 등록한다. 이 seed로 16개 답변을 섞은 `review-input.json`과 역할을 밝히는 `mapping.json`을 분리한다. 검토자는 전자만 받아 각 답변을 원문과 고정 oracle에 대조하고 판단 파일을 먼저 확정한다. 그 후 역할 대응표를 열어 D0와 C1의 정답·개선·퇴행을 계산한다. 오류 모양이나 같은 답변으로 역할을 추측할 수 있어 완전한 블라인드라고 주장하지 않는다.

입력 report·cases·oracle는 각각 한 번 읽은 바이트로 파싱과 SHA256을 함께 계산한다. 검토 도중 파일이 바뀌어도 실제로 사용한 내용과 영수증의 해시가 달라지지 않게 한다. SHA256은 출처 연결 수단이며 전자서명이나 인간 검수를 뜻하지 않는다.

판정은 원문 일치, 주장 전체의 근거 지지, 모든 질문 부분의 충족, 언어, 시점, 대상, 조건, 올바른 답변·보류를 각각 기록한다. 같은 모델의 V0/V1은 후보의 예측이며 독립 정답이 아니다. AI 사전검토·AI 출력 검토·사용자 검수와 모델 자동 판단을 구분한다.

## 다음 단계 조건

선택 조건은 동결 계획 그대로다. C1의 전체 의미 품질 8/8, 답변 가능 6/6과 근거 부족 2/2, D0 대비 개선 1건 이상·퇴행 0, 자원·보안·인용 검사를 모두 만족해야 새 가족의 validation을 준비한다. D0도 8/8이거나 동률이면 개선 근거가 없으며 자료를 더 만들어 승리를 찾지 않는다.

실패하면 결과와 원인을 보존하고 C1을 종료한다. 프로젝트 목표는 계속 활성 상태로 두고 실패 근거에 맞는 별도 후속 작업으로 이어간다. calibration 성공도 실제 Java/React 연결이나 서비스 운영 검증을 대신하지 않는다.

## 실행 전 확인 기록

공식 Qwen3.5-9B의 고정 revision에서 tokenizer 자산만 받아 별도 임시 폴더에 격리해 검사했다. 모델 가중치 다운로드·native 실행·생성은 0이다. Transformers tokenizer와 native GGUF의 토큰 수가 동일하다고 아직 확인한 것은 아니다.

[calibration 준비 결과](../experiments/results/meetings-c1-calibration-token-readiness-v1.json)는 8항목의 고정/placeholder 입력 최대 2,085 tokens, 동적 초안·검토의 출력 상한과 추가 여유 256 tokens를 더한 계획 추정 최대 3,621이다. [중립 준비 결과](../experiments/results/meetings-c1-neutral-token-readiness-v1.json)의 같은 수치는 602와 2,138이다. 모두 4,096 한도 안이다. 동적 출력의 재직렬화 때문에 이 추정을 수학적 최악 상한으로 쓰지 않으며 실제 단계의 native 검사가 최종 기준이다.

새 도구의 합성 검사 19개와 전체 Python 1,213개, Ruff가 통과했다. 기존 source freeze의 46개 파일과 tokenizer 보고서의 코드 해시가 일치한다. 서비스 코드를 변경하지 않았으므로 Java 125개·React 타입/빌드·회의 브라우저 5개의 `82b0fff` 검증 범위를 유지하며 이 준비 도구의 검사를 새 서비스 운영 결과로 세지 않는다.
