## 문제와 측정

앞선 중립 실행은 답변 생성 전에 실패했으나 원인을 구분할 기록이 부족했다. 같은 Qwen2.5-7B Q4_K_M과 llama.cpp b11429, 문맥 6144·GPU 배치 등 기존 설정을 유지해 자산 준비 → health → 설정 GET 최대 1회 → 정리만 실행했다. 새 모델·시간 제한 변경보다 먼저 실패 구간을 구분하는 것이 목적이었다. 질문·비공개 기준은 사용하지 않았고 생성·요청 출력 토큰은 0이다.

## 해석과 실패 보존

이번 실행에서는 준비 성공 뒤 설정 검증이 실패했다. 따라서 이번 결과를 단순한 시작 시간 초과나 메모리 부족으로 설명하지 않는다. 다만 설정 응답 본문·실제 template는 저장하지 않았으므로, 오류 코드만으로 어느 필드나 바이트가 달랐는지는 알 수 없다. 이전 중립 실행의 정확한 원인은 여전히 미확정이다.

외부 검증에는 두 가지 별도 문제가 남았다.

1. 최초 monitor 종료 시 알려진 5개 신원 중 4개는 없었지만 CLI의 `conhost.exe` 하나는 남아 있었다. 두 실행 세션이 종료된 뒤 별도 1회 확인에서 CLI와 해당 conhost 모두 `NoSuchProcess`였다(04:49:02.908254 UTC). 추가 종료 명령은 없었다. 나중 표본으로 원래 관찰 공백을 소급해 통과시키지 않는다.
2. 부모 AI가 보존 목록에 포함된 계획 문서를 놓치고 CI·설치 설명을 갱신했다. 소스 69개·모델/런타임 파일 신원 67개·설치 통제 2개는 유지됐지만 계획 문서의 일치 검사는 실패했다. Git 원본, 종료 시점 문서의 별도 사본, 부모 변경 귀속을 보존했다. 문서를 되돌리거나 보존 검사를 다시 실행해 성공으로 만들지 않았다.

결과는 `CUSTODY_GAP_NO_ACCEPTANCE`다. 실행 중 파일 고정은 종료 및 알려진 잔여 신원의 후속 부재 확인 뒤 해제했지만, 원래 실패·등록·소비된 once는 유지한다. 이 결과는 QA의 성공 선행 실행으로 사용할 수 없다.

## 재현과 다음 작업

공개 시작 진단 CLI와 관련 합성 검사 명령은 [설계 문서](MEETINGS-FREE-QA-STARTUP-DIAGNOSTIC-PLAN.md)에 있다. 실제 실행에는 설치된 모델·현재 소스·별도 등록과 정확한 once, 직전 충돌 확인과 종료 관찰이 필요하다. 소비된 등록으로 같은 진단을 재실행하지 않는다. 로컬 원본 기록은 공개 JSON에 SHA와 상대 경로로 연결했으며 원본 자료가 공개 저장소에 모두 포함된다는 뜻은 아니다.

다음은 고정 공개 코드와 안전한 메타데이터로 `free_qa_runtime_template`의 조건을 분석하는 일이다. 실제 runtime template를 보지 않은 채 예상값을 바꾸거나 검증을 제거하지 않는다. 필요한 추가 관측은 별도로 설계한다. 향후 실행에서는 보존 목록의 문서도 소스·모델과 함께 고정하고, 진행 설명은 목록 밖의 상태 문서에만 쓴다.

이번 진단은 토큰화·생성·정확성·요약 충분성·제품 전체 완료를 증명하지 않는다. 새 6개 품질 비교는 미실행, 사용자 검수는 0이며 모든 실행·검토·부모 실수 기록은 AI 기여로 구분한다.
