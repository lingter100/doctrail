# 첫 단계 시연과 설명

아래는 M1~M3 당시 시연·설명 기록이다. 이후 구현과 회의 확장 현황은 [회의 설명 자료](MEETINGS-LEARNING.md)와 [현재 상태](STATUS.md)를 함께 읽는다. 과거의 미구현 목록을 현재 상태로 인용하지 않는다.

## 3분 로컬 시연

1. README대로 실행하고 새 계정과 작업공간을 만든다. 기본 공용 계정은 없다.
2. `data/fixtures/onboarding.md`를 등록한다. 파일은 AI가 작성한 합성 시연 자료임을 밝힌다.
3. `운영 서버 접근 권한`을 검색한다. 결과를 눌러 원문 구절과 문서 버전을 확인한다.
4. 문서 편집에서 한 문장을 바꾼다. 같은 문서를 다시 검색해 새 버전 근거를 확인한다.
5. 새로 가입한 다른 테스트 사용자를 작업공간에 추가한다. `나만 보기` 문서는 그 사용자의 목록·검색·직접 조회에 나오지 않는지 확인한다.
6. 자동화된 삭제·재처리·권한 검증과 공개 문서 실험 결과를 설명한다. AI 자동 검증을 실제 사용자 피드백으로 소개하지 않는다.

## M1~M3 시점의 프로젝트 소개

DocTrail은 작은 개발팀의 한·영 문서를 권한에 맞게 검색하고 원문 근거를 확인하는 서비스다. Java 21·Spring Boot로 로그인과 문서 처리를 구현했고, 문서 등록·권한·수정·삭제와 원문 위치를 실제 HTTP로 검증했다. Python은 데이터·학습·오프라인 평가에 사용한다. 공개 문서 313개와 AI 작성 개발 질문으로 비교했을 때 필수 근거를 모두 찾은 질문은 BM25 30/59, 임베딩 29/59, 혼합 검색 27/59, 혼합+리랭커 36/59였다. 사용자 검수와 최종 test 평가가 끝난 정확도는 아니다. 모델의 서비스 연결·학습·생성 답변은 후속 작업이다. 설계·코드·문서·자동 검증에 AI 지원을 받았고 직접 결정·검수한 범위는 별도 기록한다.

## 면접 준비 질문 · M1 범위

M2 데이터·평가까지 포함한 설명과 실제 실패 사례는 [M2-LEARNING](M2-LEARNING.md)을 함께 읽는다. 공개 문서 313개와 활성 AI 후보 239개를 준비했고 dev 양성 59개 중 30개에서 모든 주석 근거를 찾았다. 사용자 검수 0개·test 성능 미측정이므로 이 수치를 확정 정확도로 소개하지 않는다.

**왜 Notion을 그대로 복제하는 데서 멈추지 않았나?** 익숙한 문서 탐색 구조는 사용 흐름을 설명하는 기반이다. AI 직무에서 설명할 핵심은 데이터의 출처와 품질, 검색 기준선, 권한·갱신 오류, 개선 실험이므로 이 부분에 시간을 배분했다. 경쟁 제품에도 유사 기능이 있어 독창적인 제품 발명으로 주장하지 않는다.

**왜 BM25부터 시작했나?** 유료 모델 없이 재현 가능하고, 특정 기술 용어와 오류 코드를 찾는 기준선을 만들 수 있기 때문이다. 현재 한국어는 형태소 분석 없이 2글자 조각을 사용해 동의어·의미 검색에 한계가 있다. 좋은 모델이라는 결론은 정해 놓지 않았다.

**왜 검색 후에 권한을 걸러 내면 안 되나?** 제한 문서가 후보·점수·응답에 영향을 주거나 근거로 넘어갈 수 있다. 서버 세션으로 사용자를 확인한 뒤 작업공간과 문서 공개 범위에 맞는 청크만 점수 계산에 넣고, 원문 조회에도 같은 권한을 적용한다.

**문서를 수정하면 예전 내용이 나오지 않나?** 현재 SQLite 구현에서는 문서 본문과 청크를 한 트랜잭션에서 교체하고 리비전을 올린다. 삭제는 연결된 검색 대상도 제거한다. 벡터 색인과 비동기 워커를 도입하면 같은 보장을 별도로 구현해야 한다.

**점검 질문에서 모두 검색됐는데 성능이 검증된 것 아닌가?** 아니다. 첫 자료는 8문서·4주제의 작고 중복성이 높은 코퍼스이고 질문도 AI 작성이며 사용자 검수가 없다. 기능 연결 확인과 실패 탐색을 위한 smoke 결과다. 최종 성능은 분리된 평가셋에서 다른 방식과 비교해야 한다.

**다음에 무엇을 개선하나?** 첫 비교에서 리랭커 실패 23개 중 22개는 후보 단계부터 모든 필수 근거가 없었다. 후보 회수·청크 경계·입력 잘림을 먼저 구분하고, 학습이 해결할 수 있는 실패를 골라야 한다. 새 모델을 서비스에 연결할 때는 Java의 권한 선필터와 문서 변경·삭제 보장을 다시 검증한다. 근거 없는 질문은 검색 결과 유무만으로 판단할 수 없으므로 답변 보류를 별도 문제로 다룬다.

**왜 Java 전환의 79질문 일치가 모델 성능 개선은 아닌가?** 동일한 313문서·3,588청크에서 Java 검색 결과가 기존 Python BM25의 순위·점수·원문 위치를 보존하는지 검사한 것이다. 알고리즘을 개선한 실험이 아니며 Python GPU 추론 시간을 Java 서비스의 응답 시간으로 옮겨 말하지 않는다.

**리랭커를 학습하면 후보 누락도 해결되나?** 리랭커는 전달받은 후보의 순서를 바꾸므로 후보 밖 근거를 새로 가져올 수 없다. 같은 평가셋에서 후보 단계 회수와 최종 top-5 회수를 나눠 측정해야 어떤 단계의 개선인지 설명할 수 있다. 토큰 한도 때문에 근거가 입력에서 잘리면, 원문 청크에 정답이 있다는 것만으로 모델이 읽었다고 할 수도 없다.

## 사용자가 직접 확인할 부분

시연 흐름이 자연스러운지, 질문과 정답 근거가 실제로 타당한지, 각 구조 결정을 본인의 말로 설명할 수 있는지 확인한다. 아직 확인했다는 기록은 없다. 사용자 검토 결과는 CONTRIBUTIONS와 평가 라벨에 실제 확인 후 반영한다.
