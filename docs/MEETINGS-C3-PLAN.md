## 하나의 메커니즘: 요구사항→근거 계획→필수 슬롯별 자연어

권고 식별자: `meeting-answer-requirement-plan-c3-v1`. 같은 무료 로컬 Qwen3.5-9B Q5_K_M/runtime을 사용한다. 새 모델 다운로드·서비스 API·기존 자료 재생성은 없다. 최대2회의 서로 다른 작업을 수행하며 답변을 만든 뒤 다시 고치는 단계는 없다.

**1회차: 질문의 요구사항과 근거를 먼저 결정한다.** 동일한 권한/리비전 확인된 전체 context, 질문, 별도 요청 언어를 받아 compact JSON plan 하나만 낸다. 질문에서 요구한 하위 항목을1~6개로 적고 각 항목에 `requirement_id`, 짧은 `need`, `supported|missing|uncertain`, 기존 C2 catalog의 `evidence_ids` 0~4개를 붙인다. `need`는 질문/답변에 필요한 하위 요구사항이며 oracle의 사실을 주입한 필드가 아니다. 대상·시점·적용 범위·담당자·조건·순서/중간 경과·제안/확정/실행 상태 중 해당되는 사항을 계획에 드러내도록 지시한다. 제한 때문에 질문을 일부만 계획할 수 있으면 `uncertain`으로 표시한다.

구조적으로 한 항목이라도 `missing|uncertain`이면 서버가 **질문 전체 `abstained/insufficient_evidence`**를 반환하고2회차를 호출하지 않는다. 지원된 부분만 `answered`로 바꾸지 않는다. 사용자에게는 요청 언어의 고정 문장으로 “제공된 근거만으로 질문 전체의 답을 확정할 수 없습니다”를 보여준다. 이를 인용을 단 사실 주장으로 만들거나 “모든 문서에 그 사실이 없다”고 단정하지 않는다. 진단 기록에는 어느 요구사항을 연결하지 못했는지 남기되 운영 로그에는 원문을 넣지 않는다.

**2회차: 모든 항목이 supported일 때만 자연어로 답한다.** 서버는 계획의 ID가 같은 제공 context 안의 유효한 단위인지 확인하고 원문을 정확히 복사한다. 해당 단위를 임의 절단·요약·다른 청크와 좌표 합치기·context 밖으로 확장하지 않는다. 표는 고정된 전체 구조 단위를 유지한다. 새 prompt는 질문, 명시적인 요청 언어, 요구사항별 계획과 선택된 원문 근거만 받는다. 아직 후보자의 claim은 없다.

반환 구조는 요구사항당 정확히 하나의 `requirement_id + text` 슬롯을 가지며, 각 text는1~2개의 완전한 자연어 문장으로 해당 요구와 원문상의 필수 한정 조건을 설명한다. 전체1~6슬롯이다. 인용 ID는 다시 자유롭게 고르게 하지 않고 서버가 **각 요구사항의 계획에 있던 전체 ID 집합**을 그 슬롯에 그대로 붙인다. 미등록 요구/추가 claim, 누락/중복 슬롯, 재선택한 인용은 오류다. 자료가 지지하지 않는 인과 연결·해설·추론을 추가하지 않도록 지시한다.2회차가 불확실성을 발견하면 빈 claims의 전체 보류만 허용하며 부분 answered는 허용하지 않는다.

이는 근거를 먼저 고르는 답변 경로이지 순수 인용문 복사기는 아니다. 한국어 질문/영어 자료와 반대 방향에서도 **요청 언어의 자연어 문장**을 생성한다. 단순 ID/발췌 목록을 자연어 Q&A 완성이라고 하지 않는다. 번역/바꿔쓰기의 지지와 언어 준수는 실제 평가 대상이다. 언어 mismatch는 기존처럼 오류이며 세 번째 번역/수정 호출로 복구하지 않는다.

## 자동으로 보장되는 것과 여전히 가설인 것

서버가 보장할 수 있는 것은 계획 schema, 유효 근거 ID/좌표, plan→answer 슬롯 대응, 부분 불충족 때 보류 분기, 호출/예산/언어 구조 guard다. **plan이 질문의 모든 요구를 올바르게 찾았는지, supported 판단이 맞는지, 자연어가 인용에 함의되는지는 보장하지 못한다.** 계획 자체가 요구를 누락하거나 잘못 지원됐다고 분류하면 C3도 실패한다. 모든 planned ID를 붙이는 방식은 불필요한 인용을 늘릴 수 있어 인용 관련성 기준도 유지한다.

독립 판정은 기존 사실/인용/완전성/언어/시점/대상/조건/상태 기준으로 최종 답변을 먼저 잠근다. 그 뒤 plan을 열어 실패를 `요구 식별 누락 / 근거 판정 오류 / 자연어 실현 누락·추론 / 보류 분기`로만 진단한다. 최초 의미 점수를 plan 설명에 맞춰 바꾸지 않는다. Oracle는 평가에만 쓰며 런타임에 전달하지 않는다.

C2보다 많은 최대2call·최대768출력을 쓰므로 이 실험은 단위 구조만의 공정 비교가 아니다. 이전1/7과 새 비율을 개선율로 계산하지 않는다. 목표는 새 후보 하나가 작은 새 자료의 제품 진행 기준을 충족하는지 확인하는 것이다.

## 고정 예산과 중단

각 단계 입력≤5,120/output≤384, 총 출력≤768, context6,144,24GPU layers, batch512/ubatch128, fit off, greedy/seed0/nonthinking/cache off, 동시성1을 유지한다. **두 단계의 준비·native·후처리 전체가 하나의90초 기한**을 공유한다. 단계마다90초를 새로 주지 않는다. 정리5초·시작부터 정리까지120초 경계, 소유 process 정리와 raw/dispatch 영수증을 유지한다. 기존 자원4회는 C3의2단계 자원 증거로 재사용하지 않는다.

고정 context의1회차 공식 입력은 생성 전에 확인한다.2회차의 실제 길이는 생성된 plan/선택 근거에 의존한다. 이를 사전 tokenizer 통과로 꾸미지 않는다. 모든 native dispatch 직전에 실제 token 수와 request512KiB/response2MiB 제한을 확인하고, 초과 시 context/요구/근거를 잘라 맞추지 않고 해당 실행을 오류로 닫는다. Artifact16MiB·원문 보존도 유지한다. 준비 후 자료를 바꾸거나 cap을 다시 올리지 않는다.

새 neutral plan은 **정상2단계 요청1건 + 기계적 최대 부하2단계 요청1건, 최대 native4**다. 정상은 실제 plan→분기→자연어/인용/EOS를 확인한다. 부하는 미리 봉인한 합성 stage2 입력을 사용하여 각 단계 입력 상한 근처/출력384를 한 요청의90초 안에 연속 처리하는 자원 전용 검사다. 부하의 stage2 입력은 실제1회차의 유효 plan이 아니므로 이 사실을 표시하고 완성된 자연어 pipeline 성공으로 계산하지 않는다. 특수 부하 grammar는 quality 경로에 없고, length 종료는 이 부하에만 허용된다. 부하4회가 아니라 정상2+부하2=4회다.

정상/부하 또는 품질 실행의 OOM/native error/timeout/입력 초과/잘림/언어 guard/설정·hash 불일치/정리 실패는 즉시 중단한다. Retry·warmup·추가 자기검토·자동 fallback은0. 실제 오류가 있으면 남은 dispatch는 미실행으로 남긴다. 오류가 없고 의미상 틀린 답변만 있다면 등록된 calibration을 끝까지 판정하되 실패는 그대로다. 독립 판정 후 틀린 답을 고쳐 같은 pool로 다시 실행하지 않는다.

## 가장 작은 다음 자료와 호출 일정

**새 calibration6 + 격리 validation8, 후보1개**로 제한한다. 과거 C0/C1/C2/M5/M5-B의 질문·원문·oracle·번역·근접 패러프레이즈, 실패 후 미실행/validation pool은 재사용하지 않는다. C2 validation12는 계속 잠근다. 새 family metadata와 C3코드/prompt/예산/판정 계약을 먼저 고정하고 그 뒤 자료를 작성한다. 이미 검증된 출처 처리·청크/좌표·hash·prereview·audit 도구를 재사용하며 새 범용 프레임워크를 만들지 않는다.

- Calibration:6문항=한국어3/영어3, 답변가능4/부분 필수정보 부족2. 보류2는 언어별1개다. 새로운 공개 source 계열1개와 합성 조직1개에 각각3문항을 배정한다.
- Validation:8문항=한국어4/영어4, 답변가능4/부분 필수정보 부족4. 각 언어 답변가능2/보류2다. Calibration과 다른 공개 계열1개/합성 조직1개에 각각4문항을 배정한다. 각 계열은언어별 답변가능1/보류1을 갖는다.
- 출처는 split당 두 계열·각 계열 최대2개의 짧은 문서, 총최대8문서로 제한한다. 별도 폭넓은 코퍼스 수집/검색모델 실험은 없다. 공개 source 개별 이용 조건/NOTICE는 실제 채택 때 확인하며 이 설계는 새 외부 source를 조사하지 않았다.
- 답변가능 항목은3~6개 필수 사실을 요구하고 split마다최소2문항은 복수 문서 근거가 필요하다. 조건/예외, 표의 머리글·적용 범위, 중간 사건·행위자, 계획/실행 상태를 한정된 항목에 분산한다. 각 split에 최소한 한국어 자료→영어 답변1건과 영어 자료→한국어 답변1건을 둔다.
- 보류 문항은 알려진 일부+없는 필수 항목을 함께 물으며, 채택한 계열 원문 전체에서도 그 정보가 없는지 작성자와 별도 사전검토자가 확인한다. 답이 있는 청크를 일부러 빼서 보류를 만들지 않는다. 의미 검토가 끝난 source/문항/전체 context를 token 확인 전에 봉인한다.

순서는 새 코드/합성 검사 동결 → 새 자료의 별도 사전검토·동결·1회차 token 준비 → neutral4 → calibration최대12native → 최종 답변 독립 판정·잠금 → **6/6 완전 적합일 때만** 격리 validation최대16native다. Validation은8/8 완전 적합, 부적절 보류0·근거 없는 추가 사실0·언어/운영 오류0을 요구한다. Calibration의 답변가능4개가 있으므로 전부 보류하는 정책은 통과할 수 없다. 기존 C2 gate를6개로 줄여 통과시키는 것이 아니라 별개 C3의 작은 제품 진행 기준이다.

최대 서비스 호출은4+12+16=**32회**이며 missing/uncertain에서2회차를 건너뛰면 실제 수는 작아진다. 호출별 started 영수증으로 실제 수를 기록한다. 새로운 예시 튜닝, calibration 재선택, 실패 뒤 문항 교체, 추가 후보/threshold 탐색은 이 등록에 없다. 실패하면 C3를 닫고 제한과 다음 제품 결정을 보고한다. 새로운 후보 자동 연쇄를 이 계획이 허용하지 않는다.

## 제품 연결과 남는 한계

통과한 경우에만 부모가 담당하는 Java/React 운영 경로에 명시적인 C3실험 선택을 연결한다. 기존 Java가 세션/ACL/리비전/삭제/인용 범위를 확인하고, 같은 document/meeting retrieval DTO를 넘긴다. Python은 로컬 추론만 맡으며 Java 뒤에서 핵심 서비스를 대신 실행하는 subprocess를 만들지 않는다. 원문/질문/plan은 운영 로그에 남기지 않는다.

사용자는 질문을 입력해 요청 언어의 자연어 답변과 클릭 가능한 정확한 근거를 받거나, 질문 전체를 확정할 수 없다는 보류를 받는다. 내부 plan/상태값을 사용자가 이해해야 하는 흐름으로 만들지 않는다. 실제 Java/React에서 두 단계 취소·busy·공유90초/Java120초·실패/재시도 시 입력 보존·접근 권한·리비전 교체·삭제 후 검색/인용을 확인한다. 기존 추출·결정 이력·담당 작업 편집의 phase1 검증을 함께 완료해야 한다. 후보 품질 통과만으로 phase1 완료/자동 채택이라고 하지 않는다.

작은 목적표집14문항,AI 작성/사전검토/판정·인간0, 공개문서 사전학습 가능성, metadata-exposed reviewer 가능성, 계획 단계의 같은 모델 편향이 남는다. Reviewer의 실제 노출을 다시 기록하고 구현/설계/자료 작성자를 독립 scorer로 쓰지 않는다. 이번 역할은 C3 독립 출력 판정에서 제외한다. 성공은 아직 관측되지 않았으며 무료/로컬 조건과 공개 배포 별도 승인 경계를 유지한다.
