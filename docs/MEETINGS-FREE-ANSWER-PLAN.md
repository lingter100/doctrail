# 무료 로컬 자연어 답변 후속 계획

작성일: 2026-10-13. 상태: **설계만 작성한 단일 후보 C1 제안**. 새 코드·질문·자료 작성, 모델 다운로드·호출은 아직 없다.

사용자는 유료 제안을 보류하고 무료만 사용하도록 결정했다. 이 계획은 이미 실행한 로컬 9B 모델을 재사용한다. 유료 API·크레딧·GPU 임대·클라우드를 사용하거나 유료 승인을 다시 묻지 않는다. 무료라는 이유로 자연어 RAG 또는 Phase 1이 완료된 것은 아니다.

## 출발점과 선택

부모가 전달한 C0 실제 결과는 알려진 개발 사례 4건 중 의미 품질 2건 통과, 반환 인용 9개 중 원문 일치 9개 통과다. 안내 답변과 근거 부족 보류는 통과했지만, 예정 항목을 이미 수행한 사실로 바꾸거나 선택한 인용에 없는 이유를 더하는 문제가 남았다. 이 문서 작성자는 원본 결과·질문을 다시 읽거나 재평가하지 않았다. 정확한 인용 복원과 주장 전체의 근거 지지는 별개라는 실패를 보존한다.

**권고는 기존 C0 초안에 근거 검토를 한 번 추가하고, 필요할 때만 한 번 수정한 뒤 수정본을 다시 검토하는 C1 한 개다.** 새 모델 탐색, 여러 프롬프트 후보 경쟁, 검색 재시도는 포함하지 않는다. 기존 known4와 일부 원문이 노출된 12항목은 이 실험의 개발·검증 입력으로 다시 사용하지 않는다.

| 선택지 | 기대할 수 있는 변화 | 이번 선택 |
|---|---|---|
| 같은 9B의 주장 검토와 수정 최대 1회 | 원문 복원은 유지하고 오류 탐지·수정이 실제 도움이 되는지 분리 측정 | **C1 한 개만 시험**. 개선은 아직 가설 |
| 새 사실 슬롯을 먼저 추출하고 답변 생성 | 사건·상태·조건을 중간 표현으로 드러냄 | 보류. 슬롯 누락·오분류와 최종 문장 오류를 별도로 검증해야 해 이번 묶음에 추가하지 않음 |
| 더 큰 무료 로컬 모델로 교체 | 추론 능력이 달라질 가능성 | 선택하지 않음. 이전 크기 변경만으로 의미 오류가 없어지지 않았고 새 아티팩트·자원·품질 검증이 필요함 |

이는 어떤 새 모델이 더 좋거나 RTX 4050 6GB에 들어간다는 판단이 아니다. 현재 장비는 부모가 확인한 VRAM 약 6GB·RAM 32GB이며, 이미 실행 기록이 있는 동일 9B 가중치·양자화·llama.cpp·적재 설정을 재사용하는 선택이다. 새 모델의 성능·라이선스·적재 가능성을 확인한 것으로 주장하지 않는다.

## 연구가 지지하는 범위와 한계

[Chain-of-Verification](https://aclanthology.org/2024.findings-acl.212/)은 초안 작성 뒤 검증 과정을 분리했을 때 여러 과제에서 환각 감소를 보고했다. 그러나 그 논문의 검증 절차·모델·과제가 여기의 소형 로컬 한국어 회의 RAG와 같지는 않다. 본 계획은 논문 재현이나 그 효과의 이전을 주장하지 않는다.

반대로 [자기 수정 연구 검토](https://aclanthology.org/2024.tacl-1.78/)는 외부의 신뢰할 수 있는 피드백이 없는 자기 수정의 일반적인 성공 근거가 제한됨을 지적한다. [오류 위치 탐지 연구](https://aclanthology.org/2024.findings-acl.826/)는 오류를 고치는 능력과 오류를 찾는 능력을 나누어 보아야 하며 후자가 어려울 수 있음을 보여준다. 따라서 같은 9B의 검토 결과는 **독립된 정답 oracle가 아닌 또 하나의 모델 예측**이다.

[CoV-RAG](https://aclanthology.org/2024.findings-emnlp.607/)의 결과에는 질의 재작성·새 검색과 학습 단계가 포함된다. 여기에서는 그런 구성이나 추가 학습을 도입하지 않으므로 그 성능을 근거로 C1의 성공을 예상하지 않는다. 이번 선택은 새 모델 설치 없이 검증할 수 있는 작은 가설이라는 설계 판단이다. 모든 링크는 이 문서 작성 시 일차 논문 페이지에서 확인했다.

## 변경 범위와 실행 흐름

새 진입점·새 adapter·새 계획·새 결과 경로만 추가한다. 기존 C0와 이전 실패 후보의 bound source·prompt·fixture·결과를 수정하지 않는다. `meeting_answer_spans.py`의 불변 구간 생성·원문 복원과 기존 v2/C0의 의미 지침을 그대로 재사용한다. 구간 480 code points, 최대 160구간·10청크, 주장 최대 6개·주장당 인용 ID 최대 4개를 바꾸지 않는다.

한 요청의 모든 단계는 같은 snapshot과 span catalog를 사용한다. Java가 전달한 자료의 순서·권한 범위·리비전을 유지하며 새 검색·외부 조회·후보 누락·원문 요약으로 입력을 줄이지 않는다.

1. **초안 D0, 1회:** 기존 C0와 같은 입력·prompt·decoder·생성 설정으로 자연어 주장과 span ID를 만든다. 이 원본 출력이 같은 새 질문에 대한 비교 baseline이다. baseline을 따로 호출하지 않는다.
2. **검토 V0, 1회:** 새 모델 요청으로 질문·동일 자료·D0의 주장과 인용 ID를 준다. 주장마다 선택한 인용만으로 지지되는지, 질문 각 부분이 답변됐는지, 주어진 자료로 완전한 답이 가능한지를 구분해 반환한다. 이전 대화나 정답 oracle는 전달하지 않는다.
3. **조건부 수정 D1, 최대 1회:** V0가 최종 수용 조건을 만족하지 못하면 원 질문·동일 자료·D0·V0를 사용해 전체 답변을 한 번 다시 생성한다. 다른 인용 ID를 고를 수 있지만 새 자료를 검색하거나 질문을 축소하지 않는다. 실패 주장만 삭제하고 답변 전체가 완료됐다고 처리하지 않는다.
4. **수정본 검토 V1, 최대 1회:** 질문·동일 자료·D1만 넣어 V0와 동일한 검토를 수행한다. V0의 결론·수정 이력은 보여주지 않는다. V1까지 수용되지 않으면 종료한다. 두 번째 수정, 투표, 여러 모델 judge, 사람 대신 모델에게 최종 평가를 맡기는 경로는 없다.

입력·schema·ID·언어 형식·출력 잘림 오류는 수정 단계로 보내 숨기지 않고 해당 요청의 실패로 기록한다. 불완전한 JSON을 고치는 재시도도 없다. D0와 D1은 같은 C0 answer 계약이며, 변경은 검토·조건부 수정의 유한 제어 흐름과 새 내부 검토 계약이다.

### 검토 계약

검토 출력은 다음 필드만 갖는 고정 JSON으로 제한한다. 새 few-shot·도메인 단어 규칙·known4의 표현을 넣지 않는다. 정확한 prompt·schema·grammar 문자열은 구현 완료 후 모델 실행 전에 hash로 동결한다.

| 필드 | 범위 | 의미와 검사 한계 |
|---|---|---|
| `claim_checks` | 각 기존 claim index를 정확히 한 번, `entailed / not_entailed / uncertain` | 해당 claim의 선택 근거만 검사. 다른 문단이 관련 있다는 이유로 수용하지 않음 |
| `question_parts` | 1~6개, 질문 요구의 짧은 설명·연결 claim index·`covered / missing / uncertain` | 질문 전체의 분해와 완전성도 모델 예측. 요구를 빠뜨렸는지는 별도 oracle로 평가 |
| `source_sufficiency` | `sufficient / insufficient / uncertain` | 전체 제공 자료로 질문 전체를 답할 수 있는지. 선택 인용 실패와 자료 부족을 구분 |
| `language_ok` | boolean | 요구 언어가 맞는지에 대한 예측. 기존 형식 검사와 별도 의미 검토를 대신하지 않음 |

`question_parts`의 설명은 항목당 최대 120 code points이며 사실·수정 답변·긴 추론을 쓰는 필드가 아니다. 검토자는 원문 quote나 새 span을 만들지 않는다. 각 claim의 지지는 그 claim에 연결된 ID로만, 자료 충분성과 질문 완전성은 전체 자료로 판단한다. 이 경계를 모델이 실제로 지켰는지는 평가자가 판정한다. 문법 검사는 index의 범위·누락·중복을 확인할 수 있지만 의미적 참이나 질문 분해의 완전성을 보장하지 않는다.

### 반환 상태

- **답변 수용:** draft가 answered이고 모든 claim이 entailed, 모든 질문 부분이 covered, 자료가 sufficient, 언어가 적합하며 기존 구조·원문 검사를 통과한 경우만 자연어 답변을 반환한다. 수용은 C1 내부 정책의 판단이며 실제 정답 판정은 아니다.
- **근거 부족 보류:** draft가 abstained이고 검토가 insufficient를 반환하며 적어도 하나의 질문 요구에 답할 근거가 없다고 판단한 경우 기존 `insufficient_evidence` 보류를 반환할 수 있다. 실제로 옳은 보류인지는 고정 oracle가 판정한다.
- **의미 수용 실패:** 한 번 수정한 뒤에도 불일치·불확실·누락이 남으면 원문을 꾸며 보내지 않고 새 안전 오류 코드, 예를 들어 `generation_semantic_rejected`로 종료한다. 이것을 자료가 부족한 보류로 바꾸지 않는다. 구현 시 기존 error envelope와 호환되는 코드를 고정한다.
- **운영 실패:** timeout·입력 초과·잘림·잘못된 ID·파싱·OOM은 각 운영 실패로 기록한다. 오류를 보류 성공에 합산하지 않는다.

답할 수 있는 질문에서 abstained 또는 semantic_rejected가 나오면 모두 답변 실패다. 정답 자료가 실제로 없는 질문의 올바른 abstained만 보류 성공이다. 위험한 문장을 줄이면서 질문에 답하지 못하는 결과는 자연어 RAG 완료가 아니다.

외부 `AnswerResponse`의 status·reason·claims·citations 구조와 Java 최종 원문·ACL·revision 검사를 유지한다. 새 검토 결과는 내부 값이다. `semantic_support_verified: true` 같은 확정적 운영 표시를 넣지 않는다. Java·React 계약을 새로 설계하지 않으며, 새로운 안전 오류가 기존 실패 표시로 처리되는지는 통합 전에 검사한다.

## 자원·호출 예산

동일 9B 인스턴스 하나를 직렬로 사용한다. 기존 4B 회의 분석 경로와 추출·작업 기능은 변경하지 않으며 4B와 9B를 GPU에 동시에 적재하지 않는다. 새로운 모델 다운로드·학습·동시 worker를 추가하지 않는다.

| 항목 | 고정 상한 |
|---|---|
| 한 질문의 native 생성 호출 | 2회 또는 4회. D0/V0/D1/V1 각각 최대 1회 |
| 입력 | 모든 단계마다 전체 prompt 4,096 tokens 이하 |
| 출력 | D0/D1 각각 768, V0/V1 각각 512 tokens 이하. 한 질문 합계 최대 2,560 |
| 시간 | 한 질문의 모든 단계를 합해 기존 120초. 단계마다 deadline 재설정 금지 |
| 동시 실행 | 1개. 재시도·자동 fallback·두 번째 수정 0 |
| 중립 readiness | 질문·자료가 별도인 인위적 요청 최대 2개, native 호출 최대 8회 |
| 새 calibration | 8개 × 최대 4회 = 최대 32회 |
| 새 validation | calibration 게이트 통과 때만 8개 × 최대 4회 = 최대 32회 |
| 전체 실험 | native 모델 호출 최대 72회. 요청 deadline 합계 최대 36분, 모델 적재·정리 포함 실제 실행 작업 상한 45분 |

위 숫자는 허용 상한이며 완료 예측이 아니다. **72회는 계획상 최대 호출 수이고 이 설계 작업의 실제 호출은 0회다.** 추가 검토의 GPU 시간·전력·지연은 무료 호출에서도 비용이다. 현재 C1의 실제 지연·메모리는 미측정이며 2배 또는 4배로 선형 증가한다고 단정하지 않는다. 기존 C0의 실제 시간과 새 단계별 native 시간·전체 worker 시간을 별도 기록한다. Python worker 시간을 Java/브라우저 체감 성능이라고 보고하지 않는다.

부모가 전달한 C0의 기존 4건 실측은 다음과 같다. 새 검토·수정의 성능 측정이나 재실행은 아니다.

| 기존 개발 사례 | 전체 Python 요청 ms | completion wrapper ms | 입력/출력 tokens | 모델 보고 경과 초 |
|---|---:|---:|---:|---:|
| cross-public | 12,351.047 | 12,225.680 | 2,590 / 99 | 12.219 |
| budget | 6,281.082 | 6,070.455 | 2,314 / 11 | 6.063 |
| host | 8,807.748 | 8,675.147 | 2,276 / 57 | 8.672 |
| KO | 9,222.360 | 9,050.914 | 1,208 / 97 | 9.046 |

이는 다른 CPU/GPU 부하가 없는 제한된 네 요청의 기록이다. 모델 경과 시간에는 prompt 처리가 포함되므로 출력 tokens를 나눈 값을 순수 decode 처리량이라고 쓰지 않는다. 이 수치는 최대 네 단계가 120초 안에 들어갈 가능성을 검토하는 참고일 뿐이며, 더 긴 검토 입력·출력의 실제 통과를 보장하지 않는다.

자료를 모두 포함한 검토·수정 prompt가 4,096 tokens를 넘으면 잘라 넣지 않고 입력 초과로 실패시킨다. 모델 없는 준비 검사에서 일반 경계와 추가 출력 공간을 점검하되 실제 후속 단계도 호출 직전 token 검사를 수행한다. 초안이 맞더라도 이후 단계가 timeout이면 최종 성공이 아니다. 120초 안에 유의미한 검토·수정이 불가능하면 이 구조는 현재 자원에서 탈락하며 사후에 timeout을 늘리지 않는다.

중립 readiness는 연결·문법·원문 복원·deadline 확인용이다. 입력·기대 구조·횟수는 첫 호출 전에 등록하고 실제 출력으로 의미 지침을 조정하지 않는다. 분기·종료 동작은 모델 없는 scripted generator 검사로 먼저 확인한다. 중립 실제 요청에서 수정 분기가 발생하지 않더라도 수정 경로·호출 수·전체 deadline·거부 처리는 그 합성 테스트로 검증하며, 분기를 강제로 얻으려고 중립 모델 호출을 추가하지 않는다. 추가 모델 warm-up도 native 생성 호출이면 위 72회 안에 포함하며 별도 숨은 호출은 없다.

## 새 자료와 역할 분리

새 자료는 known4, 일부 출처가 노출된 기존 12항목, 기존 calibration의 문구·수치·인명만 바꾼 변형이어서는 안 된다. M5-B와 기존 최종 test는 계속 잠그고 읽거나 재사용하지 않는다. 기존 12항목의 노출 상태와 원래 9B/C0 실패 게이트도 그대로 보존한다. 이 계획의 새 가족은 과거 검증 실패를 지우는 교체본이 아니다.

이번 단계에서는 아래 수량과 역할만 등록한다. 문서 작성자가 새로운 질문·정답·출처를 만들거나 고르지 않는다.

| 구분 | 고정 크기·구성 | 공개 시점과 목적 |
|---|---|---|
| calibration | 8항목, 답변 가능 6·근거 부족 2, 한국어 4·영어 4. 공개 원문 4·명시적 합성 원문 4 | 한 후보의 선택용 개발 자료. 코드·정책·oracle 동결 후 한 번 비교 |
| validation | 다른 source family의 8항목, 동일 구성 | calibration 통과 후 별도 custodian이 작성·봉인. 최종 후보에 한 번만 사용 |

각 split은 최소 4개 source family, 가족당 최대 2항목으로 한다. 같은 문서의 다른 날짜·동일 회의 시리즈·한 합성 템플릿의 인명 교체를 별개 가족이라고 세지 않는다. 양 split은 서로 다른 원문·가족을 사용한다. 공개 원문과 합성 원문은 각각 한국어 질문 2·영어 질문 2가 되게 하고, 두 보류 필요 질문은 언어별 1개로 한다. 공개 원문의 언어와 질문의 언어는 별도 필드다.

답변 가능 항목은 단일 근거 질문만으로 채우지 않는다. 질문 여러 부분, 여러 출처의 관계, 명시된 상태·조건과 근거에 없는 정보의 구분, 문서 변경을 포함하는 공통 품질 범주를 사전에 배분한다. known4에서 본 문장이나 개별 사실을 본뜬 함정은 만들지 않는다. 각 항목의 필수 사실·허용 대체 인용·답변 가능성·금지 추론·언어·출처 revision과 가공 hash를 모델 출력 전에 고정한다.

역할은 다음과 같이 나눈다.

1. **정책/구현 역할:** 새 코드·검토 계약·수정 조건·예산·게이트를 고정한다. validation의 원문·질문·oracle·의미 검토 설명은 읽지 않는다. calibration 결과를 보고 C1 prompt나 조건을 바꾸지 않는다.
2. **자료 custodian:** 먼저 가족 등록을 남기고 그 뒤 질문·oracle를 작성한다. 내용 없는 기존 가족 식별 정보로 중복을 검사한다. 과거 잠긴 데이터를 열어 비교하지 않는다. 기존 12항목의 격리 역할은 원래 자료를 변경하지 않고 새 가족의 분리 여부를 확인할 수 있다. 확인할 수 없는 독립성은 완료됐다고 쓰지 않는다.
3. **별도 의미 검토 역할:** 생성 prompt 구현에 참여하지 않고 oracle를 사전 검토한다. 모델 실행 뒤에는 답변과 해당 원문으로 판정하되 후보 이름·단계·다른 출력의 점수는 가능한 한 숨긴다. 모든 판정을 잠근 뒤 비교한다. 평가 모델의 판정도 AI 검토이며 인간0이다.

역할 분리는 서로 다른 사람·기반 모델의 독립성을 뜻하지 않는다. custodian과 의미 검토자가 같다면 이를 공개하고 AI의 공통 편향을 기록한다. 실제 C1 검토 출력은 평가 oracle나 정답 라벨에 사용하지 않는다. 모델 출력 뒤 oracle를 바꾸거나 일부 사례를 제외하지 않는다.

validation은 원문 접근도 봉인한다. staged 전체 diff·공백 진단을 부모 화면에 출력하지 않는다. 전체 검사 결과는 격리된 로컬 파일로 보내고 허용된 종료 코드·hash·개수만 전달한다. 새 노출이 발생하면 실행을 멈추고 별도 사고를 기록하며 이름만 바꾸어 blind라고 부르지 않는다. [기존 노출 기록](MEETINGS-VALIDATION-EXPOSURE.md)의 조건 완화를 통해 자료를 재활용하지 않는다.

## 세 가지 가설과 선택 게이트

추가 프롬프트·샘플링·구간 크기를 탐색하지 않고 C0 baseline과 C1 한 개만 비교한다. D0를 저장해 baseline으로 사용하므로 같은 질문에서 별도 baseline 호출이 필요 없다. 이는 새 자료에 등록한 비교이며 known4 재실행이 아니다.

**H1 — 오류 탐지:** V0가 D0의 잘못된 주장 지지·누락을 실제로 구분하는가. 독립 oracle와 비교해 오류를 수용한 수, 맞는 주장을 잘못 거부한 수, 빠뜨린 질문 요구 수를 각각 기록한다. 오류가 없는 분모에 100% 탐지라고 쓰지 않는다. JSON 유효율·원문 일치율은 별도로 보고한다.

**H2 — 유용한 수정:** C1의 완전 정답·올바른 보류 항목 수가 D0보다 늘고 기존 정답을 망가뜨리지 않는가. calibration에서 C1은 **8/8**, 즉 답변 가능한 6건을 모두 완전하게 답하고 실제 근거 부족 2건을 모두 올바르게 보류해야 한다. 모든 주장은 자신의 인용이 지지해야 하며 언어·시점·대상·조건·질문 완전성을 통과해야 한다. D0 대비 최소 1건 개선, D0 정답의 퇴보 0을 요구한다.

D0가 이미 8/8이거나 C1이 동점이면 더 많은 비용의 구조를 선택할 개선 근거가 없다. 비개선 또는 미식별로 남기고 자료를 더 만들어 우위가 나올 때까지 찾지 않는다. 이것이 C0의 기존 실패를 성공으로 바꾸거나 C0를 자동 채택한다는 뜻은 아니다. 올바른 답변 대신 보류·semantic_rejected가 늘어도 H2 통과가 아니다.

**H3 — 현재 자원에서 실행 가능:** calibration 8건 모두 전체 120초와 입력·출력 상한 안에서 끝나고 OOM·잘림·원문/질문 로그 노출·조용한 fallback이 없어야 한다. 지연 분포와 각 단계 토큰·시간을 원본 기록으로 남긴다. H2가 좋아도 H3 실패면 선택하지 않는다.

세 가설 중 H1은 탐지/수정 원인을 설명하는 진단이고, 선택에는 H2·H3와 구조·보안 게이트를 모두 적용한다. H1이 좋아 보여도 완전한 최종 답변이 실패하면 선택하지 않는다. 후보가 수용한 근거 없는 주장 하나도 성공 항목에 포함하지 않는다.

calibration을 통과해야만 동일한 코드·prompt·정책으로 새 validation 8건을 각각 한 번 실행한다. validation의 수용 조건도 **8/8, 답변 가능 6/6·올바른 보류 2/2, 원문 일치·주장 지지·완전성·언어·자원·보안 전부 통과**다. validation의 D0 중간 출력은 보존하지만 그 결과로 C0/C1을 다시 선택하거나 정책을 바꾸지 않는다. 이는 작은 AI/공개·합성 자료에서의 후보 선택·검증 게이트이며 최종 제품 품질, 일반 운영 정확도나 인간 검수를 입증하지 않는다.

## 구현 수용 조건과 종료

실제 모델 호출 전에 새 구현 묶음은 다음을 통과해야 한다.

- 원문·구간 알고리즘과 C0 prompt/decoder가 그대로임을 확인하고 새 파일과 모든 의존 파일의 commit/hash를 등록한다. 기존 파일 수정이 필요하면 실행 전에 범위를 재검토하며 frozen 파일을 직접 고치지 않는다.
- scripted generator로 2회 수용 경로, 최대 4회 수정 경로, 실제 보류 후보, 잘못된 보류 후보, 검토 누락·중복·불일치, 수정 후 실패, deadline 소진을 확인한다. oracle와 겉보기 verifier success를 혼동하지 않는 집계 검사를 포함한다.
- 단일 runtime lock와 한 번의 요청 deadline 아래에서 모든 호출을 수행한다. 단계마다 기존 `answer()`를 중첩 호출해 lock/deadline을 다시 만드는 구현은 허용하지 않는다. 오류·중단 때 catalog와 요청 상태가 정리되어야 한다.
- 기존 AnswerResponse 인용·안전 오류 envelope와 호환되고 Java 최종 ACL·revision·원문 검사를 통과하는지 확인한다. 원문·질문·raw 모델 출력은 일반 운영 로그에 남기지 않는다. 실험 원본은 공개/명시적 합성 자료만 별도 결과 파일로 보존한다.
- 모델 없는 검사를 마친 뒤 중립 readiness 최대 2요청과 calibration 계획을 각각 등록한다. 계획된 호출과 실제 native 호출을 구분해 집계하고 예산은 예외 경로에도 적용한다.

한 번의 calibration 결과가 선택 게이트를 통과하지 못하면 **C1을 비개선·실패로 보존하고 종료**, validation 작성·호출은 0으로 남긴다. semantic 오류는 고정된 calibration 묶음에서 기록하되 prompt·oracle·항목을 중간 수정하지 않는다. 자원·보안·격리 오류는 즉시 중단하고 완료하지 못한 항목을 실행한 것으로 세지 않는다. validation이 실패해도 같은 자료로 다시 고쳐 돌리지 않는다. known4·노출된12·기존 M5-B로 되돌아가 성공 사례를 찾지 않는다.

모델 없는 코드 결함은 최초 freeze 전에 수정할 수 있지만, calibration 출력에 노출된 뒤의 변경을 같은 후보 재시도로 숨기지 않는다. 별도 후속 작업이 필요하면 실패와 새 가설을 먼저 기록한다. 이번 묶음에는 자동 다음 모델·다음 프롬프트·추가 자료 탐색이 없다.

품질 검증을 모두 통과해도 서비스 기본값을 즉시 바꾸지 않는다. 실제 Java/브라우저에서 새 자료의 자연어 답변, 인용 열기, 문서 수정·삭제·권한 변경과 관련 Java/Python/React 검사를 확인해야 한다. 회의 분석·결정·작업 기능의 기존 성공과 자연어 답변의 현재 한계는 별도 상태로 보고한다. 실패하면 무료 범위 안에서 그 한계를 유지하며 유료 선택지를 다시 요청하지 않는다.
