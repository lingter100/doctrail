# M2 코퍼스·질문 후보·검색 평가 계약

기준일: 2026-10-12. 이 문서는 M2의 데이터 경계, 질문 계약과 측정 방법을 정한다. 수집 수량과 질문 수량은 실행 결과로 확인하며, 아래 목표 수량을 달성 수량으로 인용하지 않는다. 실제 결과와 한계는 [STATUS.md](STATUS.md), 실행 보고서와 함께 읽는다. 상위 설계는 [data-evaluation.md](data-evaluation.md)를 따른다.

M2의 산출물은 재현 가능한 공개 문서 코퍼스, 분할 누출 검사, AI 작성 질문 후보, 사람 검토 도구와 BM25 개발 평가다. 임베딩, 생성 답변, 파인튜닝, 사용자 연구 또는 공개 서비스 배포를 구현·검증한 단계로 소개하지 않는다. `train`은 향후 학습에 사용할 수 있도록 예약한 문서 분할 이름이며 학습 실행 증거가 아니다.

## 1. 코퍼스 범위와 집계

고정 커밋의 Kubernetes 영어·한국어 문서를 정제 후 약 1,000개 레코드 확보하는 것이 초기 목표다. 지원하지 않는 Hugo 구문이나 빈 본문을 통과시켜 수량을 채우지 않는다. 실제 적격 문서 수가 적으면 부족한 수와 제외 이유를 공개한다.

2026-10-12의 고정 manifest와 품질 보고서에는 **313개 문서**가 있다. 영어 235개·한국어 78개이며 train 180개, dev 65개, test 66개, smoke 2개다. canonical 계열은 255개, 분할 연결 그룹은 212개이며 최대 그룹은 23개 문서다. 검사 목록 2,287개 중 1,974개가 범위·정제 기준으로 제외됐다. 1,000문서 목표는 미달이며, 이 수량을 “1,000문서 확보”라고 소개하지 않는다. 자동 파싱·분할 확인과 별개로 사람 검토는 대기 중이다.

| 산출물 | 역할 |
|---|---|
| `data/manifests/kubernetes-v1.json` | 원본 경로·커밋·해시, 정규화 해시, 언어, 계열, 분할과 출처 계약 |
| `data/manifests/kubernetes-v1-quality.json` | 후보·선택·제외·검역 수량, 정제 결함과 중복 검사 정보 |
| 로컬 원문·정규화 본문 | manifest로 재수집·재검증하는 평가 입력; 대량 본문은 Git에 넣지 않음 |
| 질문 JSONL | 질문·관련 문서·근거 후보·작성 출처; 원문 코퍼스와 구분 |
| 검토 이벤트 파일 | 사람이 실제 내린 판단; AI 작성 원본 질문 파일과 구분 |

원본 파일 수, 정제 문서 레코드 수, 언어별 수, canonical 문서 계열 수, 분할 연결 그룹 수, 청크 수를 각각 센다. 영어·한국어 번역 두 레코드를 두 개의 독립 주제로 소개하지 않는다. 긴 문서를 여러 청크로 나눈 수도 문서 수에 합산하지 않는다. 원본 저장소 전체 파일 수와 선택 범위의 파일 수도 구분한다.

문서 로더는 원본 `sha256`, `normalized_sha256`와 현재 정규화 도구로 다시 변환한 결과를 모두 확인해야 한다. 근거 오프셋은 해시가 맞는 **정규화 본문**에 대한 것이다. 수집 시각은 원문 작성·갱신 시각을 의미하지 않는다. 원문 갱신 시각을 확인하지 못하면 `source_updated_at=null`을 유지한다.

## 2. 계열·중복·분할 경계

분할은 질문 생성보다 먼저 문서 단위에서 수행한다. 다음 연결을 합친 연결 요소를 하나의 분할 그룹으로 취급한다.

1. 같은 canonical docs 상대 경로의 영어·한국어 문서 계열.
2. 정규화 본문의 완전 동일 SHA-256.
3. 고정 토큰화로 만든 5-token shingle의 Jaccard 유사도가 0.85 이상인 문서 쌍.

유사 중복 후보는 역색인으로 열거하며 길이 상한 조건으로 불가능한 쌍을 제외한다. 이 방식의 전수성은 **선택한 토큰화·shingle·임계값 조건 안에서**의 후보 탐지에 한정된다. 알고리즘, 버전, 임계값, 토큰화, 탐지한 쌍 수, 그룹 수와 최대 그룹 크기를 품질 보고서에 남긴다. A–B, B–C가 연결되면 A–C 유사도가 낮아도 세 문서를 같은 그룹으로 분할한다.

현재 manifest의 `canonical_path`가 영어·한국어 대응 경로 계열을 나타내고, `family_id`는 유사 중복 연결까지 합친 **분할 연결 그룹**이다. 따라서 같은 `family_id`에 서로 다른 canonical 문서가 들어갈 수 있다. `family_id` 개수를 독립 주제 수로 소개하지 않고 canonical 계열 수와 함께 보고한다.

연결 그룹의 결정적 해시로 train/dev/test를 약 60/20/20으로 배정한다. 이는 정확한 개수나 언어·주제 균형을 보장하는 층화 추출이 아니다. 실제 분포와 편차를 보고한다. 기존 파일럿 4개 canonical 계열이 포함되면 연결된 그룹 전체는 `smoke`로 보존하여 새 holdout으로 재사용하지 않는다. 정제 기준을 통과하지 못한 파일럿 계열은 제외하며, 이런 경우 M2에 smoke 문서가 없을 수도 있다.

검증기는 `family_id`, 정규화 완전 중복, 유사 중복 연결 그룹이 분할을 가로지르면 실패해야 한다. 질문의 모든 관련 문서·근거는 질문과 같은 분할이어야 한다. 여러 문서 질문은 근거 문서가 이미 같은 분할에 있는 경우에만 만들거나, 분할을 고정하기 전에 연결 관계를 다시 정한다. 결과를 보고 질문만 다른 분할로 옮기지 않는다.

**검출 한계:** 0.85 미만의 파생 문서, 짧은 공통 절, 단어 순서가 크게 바뀐 개정판, 의미만 같은 문서와 canonical 경로가 다른 번역은 누락될 수 있다. 경로 대응도 번역의 최신성·의미 동등성을 보증하지 않는다. 자동 누출 검사를 통과했다는 이유로 의미 중복이 없다고 주장하지 않는다. 자동 후보와 사람 확인 상태를 분리해 기록한다.

## 3. 질문 후보의 범위

초기 목표는 dev 80개와 test 160개, 총 240개 **AI 작성 후보**다. 모든 후보의 사람 검토는 `pending`에서 시작한다. 적격 근거와 충분한 질문 다양성을 확보하지 못하면 실제 수량을 낮춰 보고한다. 같은 질문에 표현만 조금 바꿔 목표를 채우지 않는다.

실제 최초 후보 240개를 보존했다. 검색 평가 전에 별도 AI 검토에서 `m2-dev-055`의 두 문서 필요성이 불확실하다고 판단해 [리비전 계약](../data/evaluation/revisions/m2-dev-v1.1.json)으로 제외했다. 현재 활성 dev는 79개, test 후보는 160개다. 아래 표의 240개 배분은 최초 목표/초안 기준이며 활성 집계는 [데이터 카드](DATA-CARD.md)를 따른다. 사람 검수는 여전히 0개다.

| 분포 축 | 목표와 처리 |
|---|---|
| 질문 언어 | 한국어 약 2/3, 영어 약 1/3; 실제 분할별 수를 보고 |
| 응답 가능성 | 근거 있음 180, 근거 없음 36, 조건 불명확 24를 초기 설계값으로 사용 |
| 언어 교차 | 최소 60개를 초기 목표로 하되 아래의 `required`와 `allowed`를 구분 |
| 질문 유형 | 오류명·명령어, 절차, 조건, 개념 구분, 여러 문서 비교; 중복 태그 허용 |
| 근거 계열 | 질문당·계열당 분포와 최대 반복 수를 보고; 같은 계열의 표현 변형을 독립 표본처럼 취급하지 않음 |

`single_document`는 한 문서 계열의 충분한 근거로 해결되는 질문이다. 영어·한국어 대체 정답 두 개가 있다고 `multi_document`로 바꾸지 않는다. `multi_document`는 서로 다른 문서의 사실을 함께 확인해야 해결되는 질문으로, 적어도 두 개의 독립 필수 근거 그룹을 가진다. 단순히 관련 문서 두 개를 붙여 만들지 않는다.

`no_evidence`는 해당 코퍼스의 범위에서 근거가 없는 그럴듯한 요청이다. Kubernetes 사용자가 물을 법한 버전·환경·기능 질문을 사용하고, 의미 없는 임의 문자열의 낮은 검색 점수를 보류 성능으로 소개하지 않는다. `ambiguous`는 환경·버전·목표 등 필수 조건이 빠진 질문으로, 근거 없음과 별도 분류한다. BM25가 결과를 반환하거나 반환하지 않은 사실만으로 두 범주를 판정하지 않는다.

## 4. 질문 JSON 계약

M1 파일럿과 호환되는 `id`, `query`, `language`, `split`, `category`, `relevant_document_ids`, `evidence`를 유지하고 M2는 `schema_version=2`를 사용한다. 의미가 같은 중복 키를 새로 만들지 않는다. 예를 들어 `query_id`/`text`를 기존 `id`/`query`와 동시에 관리하지 않는다.

| 필드 | 계약 |
|---|---|
| `id`, `question_family_id` | 안정적인 질문 ID와 의미·표현 변형 계열 ID; 질문 계열도 분할을 넘지 않음 |
| `query`, `language` | 공백 제외 3자 이상인 질문, `ko` 또는 `en`; 실제 API의 최대 500 codepoint 제한을 만족 |
| `split` | `dev` 또는 `test`; M1 파일럿은 별도 schema의 `smoke`로 유지 |
| `category` | `single_document`, `multi_document`, `no_evidence`, `ambiguous` 중 명시된 값 |
| `answerability` | `answerable`, `unanswerable`, `ambiguous`; category와 모순되면 거부 |
| `relevant_document_ids` | 직접 충분한 grade 2 근거가 있는 문서 ID의 중복 없는 집합 |
| `evidence` | 아래의 정규화 본문 구간과 필수 근거 그룹 |
| `reference_answer` | 질문·근거 적합성 검토를 돕는 AI 참고 답안; 서비스의 생성 답변이나 검증된 정답으로 소개하지 않음 |
| `negative_reason` | 근거 없음 후보의 그럴듯한 요청 의도와 코퍼스에서 빠진 정보 설명; 단순 “검색 결과 없음”은 불충분 |
| `intended_corpus_scope` | 근거 없음·조건 불명확 판단의 대상 코퍼스 manifest 해시와 범위 |
| `created_by`, `generator_model`, `generator_reasoning_effort` | AI 작성 여부와 도구가 실제 수락한 개발 보조 모델 설정; 미확인 값은 명시 |
| `generation_prompt_sha256`, `generation_job_id` | 질문 작성 프로토콜의 해시와 위임 작업 ID; 컴파일 단계에서 실제 프로토콜·작업 등록 정보와 대조 |
| `human_review`, `human_reviewer`, `human_reviewed_at` | 후보 원본은 `pending`, `null`, `null`; 실제 사람 판단은 별도 이벤트에서 관리 |

자동 검사 결과와 교차언어 분류는 질문 작성자가 임의로 채우는 레코드 필드가 아니다. 자동 검사 보고서가 검사 범위·결과를 기록하고, 평가기가 질문 언어와 실제 grade 2 근거 문서 언어로 교차언어 분류를 계산한다. 생성 작업의 날짜와 출처는 `data/evaluation/generation/jobs.json`에 별도로 보존한다. 검사 결과를 의미 검증이나 사람 승인으로 승격하지 않는다.

필수 필드 누락, 알 수 없는 enum, 중복 ID, 빈 query, 잘못된 분할, 중복 근거 ID와 정합성 실패는 조용히 보정하지 않고 거부한다. 계약 확장은 버전을 바꾸고 기존 파일럿과 M2 검증 경로를 명시적으로 나눈다. AI 검토자는 사람 검토자 필드에 들어갈 수 없다.

### 근거 구간과 그룹

각 근거 항목은 `document_id`, `quote`, `start_offset`, `end_offset`, `evidence_group_id`, `grade`를 가진다. `grade=2`는 질문 해결에 직접 필요한 근거, `grade=1`은 부분 조건·배경이다. M2 최초 후보는 grade 2만 사용한다. 검증기는 grade 1 배경 근거가 `relevant_document_ids`에 없어도 같은 분할의 유효 span이면 허용하지만, grade 1을 직접 관련 문서나 필수 근거 회수의 정답에 섞지 않는다.

- 오프셋은 Python Unicode codepoint 기준의 반개구간 `[start_offset, end_offset)`이다. UTF-8 byte 또는 JavaScript UTF-16 code unit과 혼동하지 않는다.
- `0 <= start_offset < end_offset <= len(content)`와 `content[start_offset:end_offset] == quote`가 정확히 성립해야 한다. 같은 문장이 여러 번 나올 때 `find()`의 첫 위치를 무조건 정답으로 쓰지 않는다.
- 근거는 조건·단위·부정을 포함한 충분한 구간이어야 한다. “지원한다” 같은 짧은 조각만으로 질문 전체가 해결된다고 가정하지 않는다.
- 같은 `evidence_group_id`의 여러 구간은 하나의 필수 사실에 대한 대체 근거로 **OR** 처리한다. 다른 그룹은 모두 필요한 사실로 **AND** 처리한다.
- 같은 사실의 영어·한국어 번역은 각각 정확한 span을 확인한 경우에만 같은 그룹의 대체 근거가 될 수 있다. 문서 계열이 같다는 이유만으로 관련 문서에 자동 추가하지 않는다.
- 어떤 필수 사실을 설명하려면 두 구간을 반드시 함께 봐야 한다면 두 구간을 한 OR 그룹에 넣지 않는다. 각각의 필수 그룹으로 나누거나 전체 조건이 포함되는 단일 충분한 구간을 쓴다.
- `relevant_document_ids`와 grade 2 evidence의 문서 ID 집합은 일치해야 한다. grade 1 배경 문서가 binary recall의 정답 분모에 섞이지 않게 한다.

긴 구간이 현재 청크 경계에 걸려 하나의 청크에 온전히 들어가지 않을 수 있다. 이는 데이터 결함 또는 청킹 한계로 분류하되, 점수를 올리려고 핵심 조건을 빼지 않는다. 청크 ID를 정답으로 고정하지 않으므로 다른 청크 설정을 비교할 수 있다.

### 언어 교차의 의미

질문 언어가 한국어이고 직접 충분한 영어 근거만 존재하면 교차언어 근거가 필요하다. 충분한 한국어 대체 근거도 있으면 영어 답을 허용하는 경우다. 영어 답을 허용하는 질문을 한국어 문서만으로 맞힌 결과를 교차언어 검색 성공으로 세지 않는다.

현재 평가기의 `cross_language` 집계값은 `same_language_only`, `cross_language_only`, `same_language_sufficient_with_cross_language_alternatives`, `mixed_language_required_or_alternative`, `not_applicable`다. 필수 그룹별 직접 근거 언어 집합에서 계산하며, 근거 없는 질문은 `not_applicable`이다. 언어가 섞인 다중 근거를 모두 단순 교차언어 성공으로 합치지 않는다.

언어 교차 지표는 질문 언어와 유효 번역 대체 근거 유무별로 분리한다. 교차언어 필요 여부는 현재 **라벨된** 근거 범위에 따른 후보 판단이며, 코퍼스 전체에 대체 근거가 없다는 확정은 사람 검토 전에는 하지 않는다. 번역의 조건·버전·기능 설명이 다르면 언어가 같아도 대체 정답으로 허용하지 않는다. 회수된 실제 근거 언어별 성공률을 추가하면 후보 언어 분류와 구분해서 보고한다.

### 근거 없음의 코퍼스 범위

실험 인덱스는 고정 manifest에 포함된 train/dev/test/smoke 문서 전체를 사용할 수 있다. 검색할 정답 문서가 인덱스에 있는 것은 질문·정답 라벨을 학습이나 튜닝에 사용한 것과 다르다. 문서 분할은 질문·라벨의 사용 경계를 통제한다.

근거 없음 후보가 dev 문서 안에서는 답이 없어도 train/test 문서에 답이 있으면 전체 코퍼스 음성이 아니다. `intended_corpus_scope`는 실제 검색한 전체 manifest 해시와 일치해야 한다. 후보 탐색 경로·그럴듯한 근접 문서와 제외 이유를 보존한다. 자동 어휘 검색에서 찾지 못한 것은 근거 부재의 의미 검증이 아니므로 모두 사람 검토 대기로 남긴다.

## 5. 검토 도구와 사람 판단 기록

검토 화면은 외부 호스팅 없이 여는 로컬 정적 HTML이다. 작성된 질문마다 고정 커밋의 원문 링크, 정확한 인용·오프셋, 근거 앞뒤 문맥, 언어·분할·카테고리, 필수 근거 그룹과 대체 구간을 보여준다. 여러 문서 질문의 모든 근거를 한 화면에서 확인할 수 있다. 전체 corpus manifest 해시와 제목·경로로 검색하는 원문 목록을 제공한다. 근거 없음은 이유와 전체 corpus 범위를 제시하지만 제목 검색만으로 근거 부재를 확정할 수는 없다.

화면에서 문서·질문은 text node로 렌더링한다. 업로드 HTML이나 원문 문자열을 실행 가능한 HTML로 삽입하지 않는다. 원문 링크의 HTTPS scheme을 검사한다. 현재 인용과 문맥을 각각 보여주며, 문맥 내부 강조와 개별 정규화 문서 해시의 화면 표시는 후속 보강 사항이다. 강조를 추가할 때는 Python codepoint 오프셋을 JavaScript UTF-16 offset으로 혼동하지 않도록 변환해야 한다. 이 검토 화면은 실제 검색 제품의 일반 사용자 기능과 구분한다.

사람은 각 질문에 대해 승인, 수정 필요 또는 거절을 선택한다. 승인에는 질문이 명확한지, 근거가 질문을 실제로 해결하는지, 모든 필수 근거가 있는지, 대체 번역이 동등한지 확인한 기록이 필요하다. 음성 후보에는 전체 코퍼스 범위의 근거 부재 판단과 이유를 남긴다. 기본 선택은 미검토이며 일괄 기본 승인으로 검토 수를 늘리지 않는다.

`scripts/review_questions.py`는 화면 생성과 **실제 사람이 만든 결정 파일**의 검증·가져오기를 담당한다. 이벤트는 질문 전체 레코드 해시, 질문셋·코퍼스 해시, 결정, 검토 항목, 검토자가 입력한 식별자, 시각과 이유에 연결한다. 작성 원본 JSONL을 덮어써 과거 후보를 지우지 않는다. 질문·근거가 수정되면 기존 승인은 새 레코드에 자동 승계되지 않는다. 과거 이벤트는 감사 기록으로 남고 새 버전은 다시 검토한다.

명령의 `--manifest`, `--questions`, `--output`은 필수다. `--review`를 생략하면 HTML을 만들고, 실제 다운로드한 결정 JSON 경로를 `--review`로 넘기면 별도 검토 영수증을 기록한다. 출력이 이미 있으면 덮어쓰지 않는다. 질문 계약은 `scripts/question_dataset.py --manifest <manifest> --questions <dev.jsonl> <test.jsonl>`로 함께 검사한다. `--metadata-only`는 CI에서 메타데이터 경계를 확인하는 용도이며, 실제 본문 quote·span 검사를 했다고 표시하지 않는다. 저장소의 고정 Python 환경에서 `uv run python -m scripts.<module>` 형태로 실행한다.

AI가 HTML을 생성·열람하거나 가져오기 명령을 시험한 것은 사용자 검토가 아니다. AI는 사용자의 실제 결정을 받지 않은 채 사람 이름으로 승인 이벤트를 만들지 않는다. 해시 연결은 대상 자료의 무결성을 검사하며 검토자의 독립성·전문성을 증명하지 않는다. 로컬의 자기 기입 검토자 ID는 인증된 독립 전문가 검토라는 표현의 근거가 될 수 없다.

## 6. 개발 평가와 테스트 격리

`scripts/question_dataset.py`는 M2 질문 계약과 corpus 연결을 검증한다. `scripts/evaluate_dataset.py`의 M2 평가 대상은 dev뿐이며 **test 실행을 항상 거부한다**. `human_reviewer` 문자열을 넣거나 임의 승인 이벤트를 만들거나 단순 확인 옵션을 넘겨 test 제한을 해제할 수 없다. test 후보는 생성·구조 검증·사람 검토 준비까지 허용하며 검색 점수, 모델 비교, 오류별 튜닝에는 사용하지 않는다.

dev의 자동 평가는 `AI-authored / automatically checked / human review pending`으로 표시한다. 질문 수, 검토 상태, 근거 있음·없음·불명확 수와 제외 수를 보고한다. 자동 통과한 후보를 전문가 gold set 또는 실제 사용자의 질문이라고 소개하지 않는다.

나중에 최종 평가를 열려면 별도 변경과 다음 자료가 필요하다.

1. 사용할 test 레코드 각각에 연결된 실제 사람 검토 이벤트와 반영된 수정 내역.
2. 확정 코퍼스·질문·qrels·분할 해시, 포함·제외 ID와 이유.
3. dev에서 고른 검색 설정, 기준선, 지표 정의와 실행 계획의 고정 해시.
4. test 결과를 보기 전에 기록한 동결 시각과 이후 결과 접근·수정 이력.

전체 160개 중 일부만 검토했다면 검토된 별도 부분집합의 이름·버전·분모로 평가할 수 있게 설계한다. 한 질문 승인으로 전체 test를 여는 방식은 허용하지 않는다. 아직 M2에서는 그 부분집합도 평가하지 않는다. 공개 질문 후보는 완전한 블라인드 시험이 아니며, AI 작성·열람 이력도 보존한다. test 결과를 보고 방법을 고치면 해당 셋은 이후 개발에 노출된 데이터로 표시한다.

## 7. 실제 서비스와 같은 검색 기준선

M2의 BM25 기준선은 [retrieval.py](../src/doctrail/retrieval.py)의 실제 `chunk_content`와 `rank_chunks`를 재사용한다. 별도 라이브러리의 기본 BM25를 같은 서비스 기준선이라고 부르지 않는다. 정규화 이후 서비스 ingestion이 본문을 바꾸는지도 해시와 span으로 확인한다.

오프라인 품질 평가는 모든 선택 문서를 가시적 문서로 취급하는 고정 corpus snapshot을 사용한다. 같은 본문·청크·토큰화·BM25 설정·동점 정렬 키를 넣어 서비스와 동일한 순위를 만들고, 경로·문서명·청크 ID의 차이가 동점 순서에 미치는 영향도 기록한다. 점수는 소수점 반올림과 동점 정렬 규칙까지 서비스 구현을 따른다. 알고리즘을 재사용했다고 인증·ACL·DB·HTTP 경로까지 검증된 것은 아니다.

| 측정 | 의미 |
|---|---|
| 오프라인 dev 품질 | 서비스와 같은 chunker/ranker로 고정 corpus의 관련 근거 회수 측정 |
| API 경로 품질·일치 점검 | 실제 업로드·인덱싱·검색·원문 구간을 제한된 질의로 확인 |
| 권한·삭제·수정 자동 테스트 | 통제된 계정·문서에서 해당 시나리오의 운영 정확성 확인 |
| 실제 로컬 API 지연 | 로컬 서버·인증 세션·HTTP 요청의 왕복 지연; 전용 실험으로 분리 |

토큰화, `k1=1.5`, `b=0.75`, 1,000 codepoint 청크, 150 codepoint 겹침, 정규화 버전과 검색 코드 해시를 실행 보고서에 남긴다. 설정을 바꾸면 기존 보고서를 덮어쓰지 않고 새 run을 만든다. M2의 미래 기본값은 실제 코드·실행 설정을 우선하며 이 표의 값과 달라지면 이유를 기록한다.

## 8. 지표 정의와 한계

API의 `limit=10`은 **10개 청크**를 반환한다. 같은 문서의 청크가 여러 개면 포함된 고유 문서는 10개보다 적다. 이 결과를 문서별 전체 순위의 `Recall@10 documents`라고 부르지 않는다. 기본 metric key와 보고 제목에도 `within_top_10_chunks` 등 단위를 드러낸다.

질문 q의 상위 10개 청크에서 처음 등장한 순서를 보존해 고유 문서 순위 `U(q,10)`을 만든다. 알려진 grade 2 문서 집합은 `R(q)`다. 현재 문서 지표는 `U(q,10)`의 첫 5개를 사용하며, 근거 지표는 **원래 청크 순위의 첫 5개**를 사용한다. 필수 근거 그룹마다 어느 하나의 대체 span이 올바른 문서의 반환 청크 안에 완전히 포함되면 해당 그룹을 찾은 것으로 센다.

| 지표 | 계산·분모 |
|---|---|
| `document_recall_at_5_within_10_chunks` | `U(q,10)`의 첫 5개 문서와 `R(q)`의 교집합 크기 / `len(R(q))`를 근거 있음 질문에서 평균 |
| `document_hit_at_5_within_10_chunks` | 위의 첫 5개 고유 문서 안에 알려진 직접 근거 문서가 하나 이상 있는 질문 비율 |
| `document_reciprocal_rank_within_10_chunks` | `U(q,10)`에서 첫 grade 2 관련 문서의 역순위; 상위 10개 청크 안에 없으면 0 |
| `evidence_group_recall_at_5_chunks` | 상위 5개 청크가 찾은 필수 근거 그룹 수 / 전체 필수 그룹 수를 질문별 평균 |
| `evidence_any_at_5_chunks` | 상위 5개 청크가 필수 그룹을 하나 이상 찾은 질문 비율 |
| `evidence_all_at_5_chunks` | 상위 5개 청크가 필수 그룹을 모두 찾은 질문 비율; 여러 문서 질문을 별도 집계 |
| Source offset fidelity | 모든 검사 결과에서 반환 `text == content[start:end]`가 성립하는지 boolean으로 기록; 불일치하면 평가 실패 |
| Empty result rate | 근거 없음 후보의 결과 비어 있음 비율; 보류 정확도·답변 가능성 정확도로 해석하지 않음 |

문서 recall은 대체 정답을 많이 라벨한 질문에서 낮아질 수 있다. 한 가지 충분한 번역만 찾았어도 필수 근거 그룹을 해결한 경우는 all-required 지표로 구분한다. 문서 hit가 높아도 실제 질문을 해결하는 span을 놓칠 수 있어 문서 지표와 근거 지표를 함께 보고한다.

기본 근거 적중은 한 청크가 span 전체를 포함하는 엄격한 규칙이다. 여러 청크의 합집합 coverage를 추가하면 별도 지표 이름으로 계산한다. 넓은 겹침을 완전 적중으로 바꾸려면 dev에서 기준을 정하고 버전을 고정해야 한다. score를 보고 즉석에서 span 길이나 overlap 임계값을 바꾸지 않는다.

모든 qrels는 **현재 주석한 불완전 관련성 집합**이다. 미라벨 문서가 관련 없다고 확정하지 않는다. M2 점수는 known-annotation 회수 지표이며 전체 corpus의 완전한 정답 집합 회수율이 아니다. 후보 방법을 추가할 때는 dev의 여러 검색기 상위 결과를 모아 판정하고 라벨셋 버전 변화도 보고한다. 최신 라벨로 이전 기준선을 다시 계산할 때 과거 보고서를 남긴다.

M2 최초 grade 2 후보만으로 graded relevance가 검증됐다고 주장하지 않는다. nDCG를 추가하면 불완전 qrels, grade 1 판정 여부, gain과 ranking unit을 명시한다. 선택된 결과 안에서만 문서 중복을 제거해 만든 순위는 `deduplicated documents within top k chunks`로 이름 붙인다. 진짜 top k document 지표는 충분한 청크 후보 또는 문서 순위 산출 방법을 따로 정의한 뒤 계산한다.

현재 평가는 단일/다중 문서 등 category, 질문 언어, 계산된 cross-language 분류별 표본 수와 점수를 공개한다. 절차·오류 코드 등 추가 태그별 집계는 후속 범위다. 근거 없음·불명확 질문은 관련 문서 recall의 분모에서 제외하되 제외 이유와 수를 남긴다. 분모가 0인 지표는 0%가 아니라 `null`로 표시한다. 현재 보고서는 신뢰구간을 계산하지 않는다. 이후에는 같은 계열 질문을 독립 표본으로 가정한 과도하게 좁은 구간을 피하고, 공유 근거 계열·질문 계열의 의존 관계를 고려한 그룹 단위를 사용한다.

## 9. 지연시간과 재현 정보

오프라인 ranker 시간, 서버의 `elapsed_ms`, 클라이언트 HTTP 왕복 시간은 각각 다른 측정값이다. TestClient는 프로세스 내부 통합 검사이며 실제 HTTP 네트워크 측정을 대신하지 않는다. UI 렌더링까지 재지 않았다면 사용자 대기시간이라고 표현하지 않는다.

실제 로컬 API 실험은 유한한 범위로 실행한다. 코퍼스·청크 수, 업로드 완료 여부, DB 크기, 질의 선정 규칙, 워밍업 수, 측정 요청 수, 동시성, 캐시·전원 조건을 미리 정하고 보고한다. 표본이 작으면 p95가 소수의 느린 요청에 좌우되는 점을 명시하며 부하 시험이나 운영 SLO 달성으로 소개하지 않는다. 실패·timeout을 제외한 성공 요청만으로 빠른 지연을 주장하지 않는다.

각 실행은 덮어쓰지 않는 `run_id` 아래 다음을 보존한다.

```text
git_commit, git_dirty, source hashes, uv.lock hash, exact command
corpus manifest hash, normalized corpus hashes, query set hash, split version
question provenance counts, human-reviewed count, included/excluded IDs
chunker/tokenizer/ranker versions, actual ranking config, output unit and k
metric definition version, group counts, per-query outcomes, subgroup metrics
runtime/environment, warmups, measured requests, concurrency, latency samples
errors/timeouts, measured scope, limitations, started/finished timestamps
```

학습하지 않은 실행의 train/model/optimizer 정보는 `null` 또는 해당 없음으로 기록한다. 개발 보조에 사용한 모델과 서비스 추론 모델을 구분한다. 이 설계 작업은 도구에서 수락한 `gpt-6-astra / xhigh` AI 설계·검토 기여이며 사람이 평가한 결과가 아니다. 부모 채팅 모델이 바뀌었다는 주장도 하지 않는다.

## 10. M2 완료와 이후 작업의 경계

M2의 완료 증거는 실제 corpus 수와 해시, 완전한 제외 집계, 자동 누출·span 검사, AI 후보 수와 검토 상태, test 거부 동작, dev 기준선 보고서 및 제한된 API 측정이다. 기능·데이터 수량만으로 검색 품질이 좋다고 결론내리지 않는다. 이 문서의 설계 항목 중 구현하지 않은 부분은 상태 문서에서 계획·미구현으로 남긴다.

사람 검토가 대기 중이어도 corpus 준비, 검증 도구, dev 실패 분석과 실제 서비스 측정은 진행할 수 있다. 이후 사람 검토·라벨 개선·설정 동결을 거쳐 최종 평가를 연다. 임베딩·하이브리드·리랭킹·학습은 그 이후 독립 실험이며, M2에서는 해당 성과를 미리 기록하지 않는다.
