# M4 · 내부 calibration 개선과 남은 회귀

기준일: 2026-10-13. **마지막 E5 저장본은 내부 calibration의 주석 근거 회수 @50을 13→15/16, @5를 8→11/16으로 높였다.** 사전 진행 조건을 통과했지만 @5 회귀 3개와 계속 누락 1개가 남았다. 별도로 고정할 main-dev 비교의 후보가 됐으며 서비스 채택이나 일반 검색 품질 향상을 확정한 결과는 아니다.

이 문서는 [저장된 결과](../experiments/results/m4-calibration-v1.json), [고정 평가 계획](../data/training/m4-calibration-evaluation-v1.1.json), [공개 질문](../data/training/m4-pilot-v2/questions.jsonl)과 원래 train 원문을 대조한 사후 분석이다. 새 모델 실행·학습·평가는 하지 않았다. `prepare_training.load_inputs`와 `chunks_for`로 기존 캐시의 해시를 검증하고 train 청크만 분석에 사용했다. 기존 검증 로더의 전체 코퍼스 무결성 검사와 dev/test 질문을 여는 행위는 구분하며, 이 분석에서 main-dev/test 질문은 열지 않았다.

## 비교 범위와 결과

Fit64·calibration16은 문서 계열로 분리했다. Calibration은 원래 train 안의 5개 계열에 AI가 작성한 질문16개이며, 사용자 검수는 **0개**다. 검색 대상은 원래 train180문서·2,196청크다. E5 base와 고정 배율1024에서 실제16회 갱신한 마지막 checkpoint를 동일 tokenizer·512토큰·FP32·후보50 조건으로 한 번씩 비교했다. 준비 v1 실패와 GPU v1.1 실패는 [실행 기록](M4-READINESS-RESULTS.md)에 보존했다.

| 고정 지표 | Base | Terminal | 해석 |
|---|---:|---:|---|
| 전체 주석 근거 @50 | 13/16 (81.25%) | 15/16 (93.75%) | 001·005 회복, 추가 회귀0 |
| 전체 주석 근거 @5 | 8/16 (50.00%) | 11/16 (68.75%) | 회복6·회귀3, 순증3 |
| 근거 청크 MRR@10 | 0.30156 | 0.60129 | @5 회귀 외에003의 순위도 하락 |
| 문서 hit@5, 상위10청크 안 | 10/16 | 15/16 | 중복 제거한 문서 순위이며 근거 청크 지표와 다름 |

@50은 주석 근거 전체를 포함하는 청크가 후보50에 있는지를 센다. @5와 MRR도 고정된 근거 span을 대상으로 하며, 답변 생성·정확도나 모든 대체 정답의 회수를 측정하지 않는다. `@50 순증 ≥1`과 `@5 총수 비감소`가 사전 조건이므로 이번 결과는 통과다. 조건 통과가 모든 질문의 비회귀를 뜻하지 않는다.

| 세부 집단 | 질문 수 | @50 Base→Terminal | @5 Base→Terminal |
|---|---:|---:|---:|
| 질문과 주석 근거 언어가 다름 | 10 | 7→9 | 2→8 |
| 질문과 주석 근거 언어가 같음 | 6 | 6→6 | 6→3 |
| 한국어 질문 | 10 | 8→10 | 3→8 |
| 영어 질문 | 6 | 5→5 | 5→3 |

집계상 이득이 교차 언어 주석군에 집중됐고 같은 언어 주석군은 퇴보했다. 번역·대체 근거의 미주석과 작은 표본 때문에 이를 언어 능력의 일반적 개선·악화나 학습 원인으로 단정하지 않는다.

## 001·002: 주석 회수와 답변 가능성의 차이

**001**의 고정 영어 양성 `k8s-en-03468ff4ebcb29fe:0`은 후보50 밖에서1위로 올랐다. 그러나 base의1위 `k8s-ko-d5181b0c9cee25ab:0`은 같은 계열의 한국어 번역이고, 권장 레이블이 관리에는 도움이 되지만 코어 도구에는 필수가 아니라는 내용을 담는다. 원문과 청크 해시를 확인했다. 따라서 영어 주석 회수의 성공을 “이전에는 답할 수 없던 질문을 새로 해결했다”로 표현하면 과장이다.

**002**의 주석은 영어 표 행 `[1336,1460)`이고 양성 `k8s-en-03468ff4ebcb29fe:1`은36→9위다. Terminal5위의 같은 문서 `:3`에는 `app.kubernetes.io/instance`로 개별 WordPress 설치를 식별하고 인스턴스마다 고유 이름이 필요하다는 별도 설명이 있다. Base1위의 한국어 번역 `k8s-ko-d5181b0c9cee25ab:2`도 이 사실을 설명한다. 두 모델 모두 top5에서 대체 답변 근거를 찾았다고 정성적으로 볼 수 있지만, 고정 표 행은 top5 밖이므로 주석 @5 실패를 그대로 유지한다.

이 사례는 고정 주석이 모든 관련 근거를 망라하지 않음을 보여 준다. 번역·대체 설명을 이번 실행의 정답에 소급 추가하거나 점수를 재계산하지 않는다. 위 해석은 원문에 대한 AI 사후 분석이며 사용자 검수나 별도 정답성 평가가 아니다.

## 회귀와 남은 실패의 원문 대조

Offset은 정제 원문 기준 0부터 시작하는 반열린 구간이다. 같은 문서의 상위 청크가 있다는 사실만으로 해당 근거를 포함한다고 판정하지 않는다.

| ID | 주석·양성 청크 | Terminal 상위 후보에서 관찰한 사실 |
|---|---|---|
| 010 | `[1525,1616)`, `k8s-en-7375d5fe28a8752e:1`, 4→7위 | 같은 문서 `:3`이1위, `:0`이2위지만 둘 다 해당 span과 겹치지 않는다. 별칭·Homebrew 스크립트와 Bash 요구 조건이 앞섰다. 설치 후 동일 명령으로 검증하는 대체 설명 `:2`도5→6위여서 top5 밖이다. |
| 014 | `[1342,1512)`, `k8s-en-3161ebe6b588b5f0:1`, 2→6위 | 같은 문서의 도입·FAQ 목록 `:0`이1위를 유지하지만 주석과 겹치지 않는다. 요청한 피드백 이슈106917은6위 청크에 남고, 그 앞에는 폐기 정책·RBAC·보안 공개 문서가 있다. |
| 015 | `[5629,5682)`, `k8s-ko-05261080c1ab2828:6`, 1→6위 | Top5에 해당 한국어 문서가 없다. 영어 Service DNS 설명3개와 Linux 보안·namespace 설명이 앞섰으며 `.spec.os.name`을 스케줄러가 사용하지 않는다는 요청 사실을 제공하지 않는다. |
| 003 | `[1869,1990)`, `k8s-en-03468ff4ebcb29fe:2`, 4→5위 | 요청한 `managed-by` 표 행은 top5에 남아 MRR만0.25→0.20으로 줄었다. 같은 문서 도입 `:0`은1위지만 해당 행을 포함하지 않는다. 이 회귀를 @5 실패로 세지 않는다. |

010·014의 같은 문서 상위 청크는 근거의 일부만 포함한 상태도 아니다. 각각의 주석 span과 겹치는 문자가0개다. 이는 가까운 주제·문서를 찾는 것과 요청한 사실을 담은 청크를 상위에 놓는 것이 다르다는 관찰이다. 단일 학습 전후 비교만으로 특정 음성쌍·토큰·언어 편향이 회귀를 일으켰다고 결론 내리지 않는다.

015의 양성은537→512토큰으로 잘렸다. 다만 [저장된 tokenizer 영수증](../data/training/m4-tokenizer-receipt-v1.json)에서 근거와 겹치는32토큰이 모두 보존됐고 잘림으로 사라진 근거 토큰은0이다. 문자 offset `[5648,5649)`가 tokenizer offset 합집합에 포함되지 않는 현상은 잘림 전후 동일하다. 이를 잘림으로 잃은 근거나 완전한 문자 span 가시성 증명으로 해석하지 않는다. 두 모델이 같은 tokenizer·입력을 사용했으므로 이 기록만으로015의 순위 하락을 잘림 탓으로 돌릴 수 없다.

**016**은 주석 `[4309,4417)`을 담은 `k8s-ko-05261080c1ab2828:5`가 두 모델 모두 후보50 밖이다. 원문은 LogMonitor가 ETW 공급자 등을 감시해 STDOUT으로 보내는 내용을 명시한다. 해당 청크는466토큰으로 잘리지 않았다. Base 상위에는 kubectl 명령 참조의 공통 말미가, terminal 상위에는 명령 참조·도구 설치·Windows 자원 관리가 있다. 요청 도구를 담은 고정 근거를 회수하지 못한 후보 단계 실패가 남았으며, 질문 자체에 답이 없거나 토큰 잘림이 원인이라고 판정하지 않는다. 후보50을 받는 후단은 이 주석 청크를 새로 만들어낼 수 없지만, 모든 대체 정답의 부재까지 조사한 결과는 아니다.

## 시간·자원과 측정 한계

로컬 NVIDIA RTX4050 Laptop GPU에서 CUDA FP32로 base 다음 terminal을 측정했다. 각 모델에 warmup2회, 실제 질문16개 한 순회다. 다음 수치는 저장 보고서의 서로 다른 구간이며 합쳐서 서비스 지연으로 부르지 않는다.

| 측정 구간 | Base | Terminal |
|---|---:|---:|
| 모델 로드 | 5,088.358ms | 1,618.149ms |
| Warmup | 237.016ms | 38.216ms |
| 문서2,196청크 임베딩 준비 | 27,340.805ms | 27,937.632ms |
| Query encode+dense rank p50/p95 | 12.419/15.861ms | 13.513/18.907ms |
| 위 질문별 측정16개 합계 | 203.900ms | 239.890ms |
| 계측을 포함한 질문 단계 wall time | 247.306ms | 281.831ms |

문서 임베딩은 질문 측정 전에 준비했다. 로드 경로·순서·캐시·전원·다른 부하를 통제한 반복 비교가 아니므로 로드 단축이나 질문 지연 차이를 모델의 일반적 속도 특성으로 주장하지 않는다. Python 오프라인 dense 검색 시간이며 Java HTTP, ACL·DB·네트워크·BGE reranking·생성 답변·동시 사용자 지연은 포함하지 않는다.

두 모델 모두 전체 토큰화 입력2,216개 중23개가 잘렸다. 이는 문서2,196개·질문16개·warmup4개를 합친 분모이며 질문은 모두 잘리지 않았다. 청크 원문 기준 회수 지표와 실제 모델 입력의 토큰 보존은 서로 다른 진단이다. GPU 자원 수치는 해당 프로세스의 CUDA allocator, CPU 메모리는50ms 간격 RSS 샘플 범위다. 전체 장치 VRAM이나 배포 환경의 최대 메모리를 보장하지 않는다. 유료 API·임대 GPU·클라우드는 사용하지 않았고 공개 서비스 배포도 하지 않았다.

## 다음 판단의 고정 경계

현재 terminal 하나와 tokenizer·청크·후보 예산·평가 지표를 유지한다. 별도 main-dev 계획에서 입력·코드·checkpoint hash, 한 번의 비교 범위와 판정 기준을 **실행 전에** 고정한 후 비교한다. 이 문서 작성 시점에는 그 비교를 실행하지 않았다. 이번 calibration을 보고 epoch·seed·음성·질문 삭제·청크 설정을 다시 조정하지 않는다. Test는 잠금 상태를 유지한다.

Main-dev에서 불리한 결과가 나와도 함께 보존하며 이 실행을 재튜닝하지 않는다. Java/React 서비스는 기존 검증 모델을 유지한다. 실제 채택에는 별도 ACL·revision/delete·검색/근거/history/feedback·HTTP·브라우저 회귀와 원격 CI 확인이 필요하다. 데이터 준비 통과, 실제 가중치 갱신, 내부 주석 회수 개선, 서비스 채택을 각각 구분한다.
