# M3 첫 개발 비교: 결과와 다음 판단

2026-10-12의 로컬 CUDA 실측에서 **혼합 검색 뒤 BGE 재순위화를 적용한 HR이 필수 근거 top-5 회수를 30/59에서 36/59로 높였다.** E5 단독은 29/59, RRF 혼합만으로는 27/59였다. 따라서 이번 결과는 사전학습 임베딩을 붙이면 자동으로 개선된다는 설명을 뒷받침하지 않는다. 같은 H50 후보의 재순위화는 9문항을 회복했고 퇴보는 없었지만, BM25와 비교하면 7문항 회복·1문항 퇴보다.

이것은 **AI 작성·사용자 검토 0개의 dev 라벨에 대한 예비 회수 실험**이다. test 160개는 실행하지 않았다. 생성 답변·학습·실서비스 품질·공개 배포의 성과가 아니며, 추가 검색 경로의 서비스 ACL·수정·삭제 통합이 남아 있어 M3 전체 완료로 표시하지 않는다.

## 1. 분석 근거와 변경하지 않은 것

주 근거는 [M3 실행 보고서](../experiments/results/m3-retrieval-dev-v1.json), [원래 M2 기준선](../experiments/results/m2-bm25-dev-v1.1.json), [dev v1.1 질문](../data/evaluation/m2-dev-v1.1.jsonl), [고정 corpus manifest](../data/manifests/kubernetes-v1.json), [실행 전 설계](M3-DESIGN.md)다. 이 분석은 저장된 결과를 읽고 원문 hash·span·순위를 대조했다. 모델 추론을 다시 실행하거나 라벨·코드·모델·test를 변경하지 않았다.

| 재현 식별자 | 값 |
|---|---|
| 실행 코드 커밋 | `a8fb5a99b0445366970c4ae63026fb1d51d02fe5` |
| 보고된 작업 상태 | `git_dirty=true`; 실행 당시 상태를 그대로 보존 |
| 실행 설정 SHA-256 | `fba1add80bd305a3e64b194cde80c164a3d3c9a9545335515ddc85d69c7ce09b` |
| 결과 파일 SHA-256 | `76aa4bbc0f827fc4022dbab289eb730072ded56122b8ed8107f72f67ee32a63f` |
| 실제 입력 | 313문서·3,588청크·dev 79질문; 양성 59, 근거 없음 12, 조건 불명확 8 |
| 모델/장치 | E5-small FP32, passage batch 8/query 1; BGE v2 m3 FP16 batch 1; RTX 4050 Laptop GPU |

원래 M2와 이번 BM25의 79개 질문별 top-10 청크·점수·지표 및 전체 지표가 정확히 같음을 보고서의 parity 결과와 별도로 재확인했다. 실행기는 source/input·corpus·model의 실행 전후 drift 검사도 통과했다고 기록한다. 지연은 순위 재현과 별개이므로 예전 M2 지연과 이번 지연을 같은 조건으로 직접 비교하지 않는다.

분석 AI 위임 설정은 `gpt-6-astra / xhigh`다. 아래 원문 확인은 AI의 분석이며 사람의 의미 검수나 라벨 승인으로 계상하지 않는다.

## 2. 같은 분모에서의 결과

B는 BM25 50후보, D는 E5 50후보, H는 두 결과를 RRF로 합친 뒤 50개를 남긴 방법이다. HR은 **그 H50 후보를 그대로** 재순위화했다. H25는 B25·D25 합집합을 사용하는 사전 지정 후보 예산 진단이다. 모든 최종 근거 지표는 같은 원문 청크의 첫 5개를 사용한다.

| 방법 | 모든 필수 근거 @5 /59 | 주석상 교차언어 전용 /23 | 다중 문서 /7 | 후보 안 모든 필수 근거 /59 |
|---|---:|---:|---:|---:|
| B | 30 (50.85%) | 1 (4.35%) | 1 (14.29%) | 35 (59.32%) |
| D | 29 (49.15%) | 1 (4.35%) | 1 (14.29%) | 34 (57.63%) |
| H | 27 (45.76%) | 0 | 0 | 37 (62.71%) |
| HR | 36 (61.02%) | 6 (26.09%) | 1 (14.29%) | 37 (62.71%) |
| H25 | 30 (50.85%) | 0 | 1 (14.29%) | 36 (61.02%) |

H25의 실제 후보는 질문별 31~49개, 전체 79질문 평균 41.99개다. H는 두 검색기에서 최대 100개를 받아 50개를 유지하므로 B/D와 후보 생성 비용이 같지 않다. 이 표의 마지막 열은 후보에 모든 주석 span이 존재하는지 보는 필요조건이다. 5청크로 모든 근거를 덮는 최적 조합을 계산한 oracle@5나 재랭커의 의미 이해 정확도는 아니다.

HR의 한국어 양성 회수는 20/39, 영어는 16/20이다. B의 14/39·16/20과 비교하면 이번 순증 6문항은 한국어 집합에서 생겼다. 그러나 두 언어의 질문·주제·난이도 분포가 달라 언어만의 인과 효과로 해석할 수 없다. 모든 방법은 근거 없음 12문항에도 결과를 반환했다. 답변 보류를 구현·평가한 결과는 아니다.

문서 Hit@5도 B 35/59에서 HR 45/59로 올랐지만, 이 순위는 **상위 10청크에서 중복 제거한 문서**의 첫 5개다. 전체 문서 순위의 Hit@5라고 부르지 않는다. source offset 검사는 각 방법 79질문 모두 통과했다. 이는 반환 문자열의 무결성이며 의미상 정답 보장은 아니다.

다중 문서의 1/7은 같은 질문을 계속 맞혔다는 뜻도 아니다. B와 H25는 `060`, D와 HR은 `053`을 맞혔다. 교차언어 1/23 역시 B는 `027`, D는 `050`이다. 집계 점수가 같아도 실패 구성이 바뀐다.

## 3. 원문을 대조한 다섯 사례

아래 5질문에 연결된 10개 annotation을 8개 정규화 문서와 대조했다. 문서 bytes의 SHA-256이 manifest와 같고 각 `[start_offset,end_offset)`가 저장된 quote와 정확히 일치함을 확인했다. 원문 링크는 동일한 Kubernetes 고정 커밋을 가리키며, 문서 번호와 offset은 정규화 본문 기준이다. 사례는 결과를 본 뒤 설명 목적으로 골랐으므로 독립적인 추가 평가 표본이 아니다.

### `m2-dev-003`: 같은 문서의 필요한 절을 더 위로 올림

질문은 lifecycle hook이 이벤트당 한 번만 호출된다고 가정해도 되는지 묻는다. [Container Lifecycle Hooks](https://github.com/kubernetes/website/blob/4b10551a8c6f0a3f100356d8fc3c6fb5cfde1448/content/en/docs/concepts/containers/container-lifecycle-hooks.md)의 정규화 구간 `[4744,4966)`는 같은 이벤트에 반복 호출될 수 있으며 구현이 이를 처리해야 한다는 내용을 담는다.

이 span을 포함하는 `k8s-en-db7d68386819ee82:5`는 B에서 6위, D에서 1위, H에서 4위, HR에서 1위였다. B도 후보 50개에는 이미 이 근거를 갖고 있었다. **관찰된 개선은 원문 발견 여부가 아니라 top-5 안으로의 순위 이동**이다. HR의 해당 쌍은 271토큰이며 잘리지 않았다. 이 한 사례로 E5의 전반적인 의미 검색 우위를 주장할 수는 없다.

### `m2-dev-009`: 교차언어 근거를 재순위화로 회복

한국어 질문은 `kubectl`로 삭제한 mirror Pod가 왜 다시 나타나는지 묻는다. [Static Pods](https://github.com/kubernetes/website/blob/4b10551a8c6f0a3f100356d8fc3c6fb5cfde1448/content/en/docs/concepts/workloads/pods/static-pods.md)의 영어 span `[1383,1544)`는 mirror Pod를 삭제해도 static Pod는 제거되지 않고 kubelet이 mirror Pod를 다시 만든다고 설명한다.

근거 청크 `k8s-en-5b28d26f42e3ae09:1`의 순위는 B20 → D30 → H6 → HR1이었다. 두 첫 검색기의 후보 안에 있던 영어 근거가 H의 top-5를 한 자리 놓쳤고, 재순위화 후 회수됐다. 해당 HR 쌍은 305토큰, 잘림 없음이다. **새 근거를 생성하거나 후보 밖에서 찾은 효과가 아니라 동일 후보의 순위 개선**이다.

### `m2-dev-027`: 명령어 근거에서 dense가 놓친 결과를 BM25 후보가 보존

한국어 질문은 `kubectl get nodes -o wide`를 `getn` 별칭으로 만들 때 리소스 이름을 어디에 넣는지 묻는다. [kubectl kuberc set](https://github.com/kubernetes/website/blob/4b10551a8c6f0a3f100356d8fc3c6fb5cfde1448/content/en/docs/reference/kubectl/generated/kubectl_kuberc/kubectl_kuberc_set.md)의 영어 예시 `[800,979)`에 `--prependarg nodes`가 있다.

근거 청크 `k8s-en-f224aebec3f75421:0`는 B3, D의 top-50 밖, H18, HR1이었다. H25에서도 7위라 실패했다. 해당 HR 쌍은 301토큰, 잘림 없음이다. 이번 질문에서는 BM25 후보가 없었다면 고정 D50 경로가 이 근거를 제공하지 못한다. 다만 이것이 오류 코드·명령어 질문 전체의 보편적 성질인지는 따로 태그와 분모를 정해 확인해야 한다.

### `m2-dev-053`: 다중 문서 성공과 잘림 미측정의 경계

질문은 PostStart가 메인 프로세스보다 먼저 끝나는지와 startup probe 성공 전 다른 probe의 상태를 함께 묻는다. [한국어 lifecycle hook 문서](https://github.com/kubernetes/website/blob/4b10551a8c6f0a3f100356d8fc3c6fb5cfde1448/content/ko/docs/concepts/containers/container-lifecycle-hooks.md)의 `[327,390)`와 [probe 문서](https://github.com/kubernetes/website/blob/4b10551a8c6f0a3f100356d8fc3c6fb5cfde1448/content/ko/docs/concepts/configuration/liveness-readiness-startup-probes.md)의 `[801,846)`가 각각 필요한 사실이다.

B는 probe 근거를 1·2위에 반환했지만 hook 순서 근거는 top-10에 없었다. D는 hook 근거를 4위, H는 7위, HR은 3위에 뒀다. HR에서 probe 근거도 1·2위에 남아 두 그룹을 모두 충족했다. 한 사실의 여러 청크가 올라온다는 것과 서로 다른 필수 사실을 확보한다는 것을 구분해야 하는 사례다.

하지만 HR의 hook 청크 쌍은 615토큰에서 잘렸고, probe 청크 한 개도 567토큰에서 잘렸다. probe의 다른 대체 청크는 177토큰으로 잘리지 않았다. 이 성공은 **반환된 원문 전체 청크의 span 포함**에 대한 것이다. 잘림 후 정확한 model-visible span coverage는 측정하지 않았으므로 hook 근거의 모든 글자를 모델이 실제 읽었다고 확정하지 않는다.

### `m2-dev-060`: 후보는 충분했지만 두 번째 사실이 6위에 머묾

영어 질문은 Windows workload에서 `wincat not found`가 발생한 경우와, 이를 고친 뒤 선택한 Pod 종료로 포워딩이 끊긴 경우를 함께 묻는다. [Windows debugging tips](https://github.com/kubernetes/website/blob/4b10551a8c6f0a3f100356d8fc3c6fb5cfde1448/content/en/docs/tasks/debug/debug-cluster/windows.md)의 `[4668,4873)`는 pause 이미지의 `wincat.exe` 포함을, [kubectl port-forward](https://github.com/kubernetes/website/blob/4b10551a8c6f0a3f100356d8fc3c6fb5cfde1448/content/en/docs/reference/kubectl/generated/kubectl_port-forward/_index.md)의 `[175,383)`는 선택 Pod 종료 시 명령을 재실행해야 함을 설명한다.

| 근거 청크 | B 순위 | D50 내 순위 | H50 순위 | HR 최종 순위 |
|---|---:|---:|---:|---:|
| Windows 설명 EN `k8s-en-44bfbf890126fa84:5` | 1 | 26 | 3 | 2 |
| 같은 Windows 사실 KO `k8s-ko-3a31a7af2aaf3467:3` | 25 | 없음 | 50 | 1 |
| 세션 종료 `k8s-en-24608d068e5a4828:0` | 2 | 없음 | 11 | 6 |

HR의 50후보에는 두 필수 그룹이 모두 있었다. 첫 두 결과는 같은 Windows 사실의 번역 대안이고, 3~5위는 Pod/image/lifecycle 문제의 다른 구간이었다. 두 번째 필수 사실이 6위여서 top-5 성공을 놓쳤다. **이 질문의 HR 퇴보는 후보 부족이나 청크 경계 문제가 아니라 최종 순위 배치의 실패**로 관찰된다. 사실 다양성을 보장하지 않는 개별 쌍 점수화가 관련 있을 수 있다는 해석은 후속 통제 실험 전까지 가설이다.

위 세 근거 쌍은 각각 321·453·336토큰이며 모두 `truncated=false`였다. 따라서 이 사례를 512토큰 잘림 때문이라고 설명할 근거는 없다. 전체 평가의 정확한 model-visible 지표가 없는 한계와, 이 세 입력에 잘림이 없었다는 관찰은 구분한다. H25에서는 세션 종료 근거가 5위여서 성공했다. 이를 보고 기존 top-5 지표를 top-6으로 바꿔 퇴보를 지우지 않는다.

## 4. 후보 단계가 다음 품질 개선의 우선순위인 이유

H의 B50·D50 합집합에는 59개 양성 중 40개 질문의 모든 필수 근거가 있었다. 이를 50개로 줄이면서 `013`, `017`, `040`이 빠져 37개가 남았다. 아래는 저장된 후보 순위로 재계산한 진단이며 모델을 재실행한 결과가 아니다.

| 질문 | 합집합에 있었던 근거 | H50에서의 손실 |
|---|---|---|
| `013` | D49의 `k8s-en-a74613f9005a7ab1:48` | 필수 사실 청크 탈락 |
| `017` | B28의 변경 저장 근거와 B14의 재시도 근거 | 저장 근거 탈락; 재시도만 유지 |
| `040` | 양쪽 1위의 권한 설명과 D48의 구체 규칙 | 구체 규칙 청크 탈락 |

HR은 H50가 모든 필수 근거를 가진 37문항 중 36개를 최종 top-5에서 회수했다. 남은 하나는 `060`이다. **현재 주석·고정 후보에 한정하면 재순위화가 회수할 수 있는 후보 조건에 근접했다**는 뜻이지 재랭커가 거의 완벽하거나 97% 정답이라는 뜻이 아니다. 실패 23개 중 22개는 H50부터 필수 근거가 부족했고, 그중 3개는 위처럼 합집합→50 축소에서 잃었다. 나머지 19개는 합집합 단계부터 불충분하다. 기존 청크 안에 span 전체가 들어갈 수 없는 질문도 이 실패에 포함된다.

품질 측면의 다음 권고는 다음 순서다. 아직 수행한 개선 결과로 읽지 않는다.

1. **추론 없는 후보 진단을 먼저 확장한다.** 저장된 B/D/합집합/H50에 대해 근거 문서 미포함, 같은 문서의 다른 청크, 주석 span 경계, 겹치는 청크와 번역 대안이 차지한 수를 구분한다. `013/017/040`의 후보 보존과 `060`의 사실 중복을 별도 문제로 다룬다.
2. **모델·청크·라벨을 그대로 두고 후보 선택 하나만 바꾼다.** 현 H50과, 각 분기의 상위 후보를 일정 수 보존한 뒤 나머지를 RRF로 채우는 최대 50후보 방식을 사전 고정해 비교하는 것이 후보안이다. 이미 측정한 H25가 30/59이고 후보 조건은 36/59라는 사실만으로 그 뒤 재랭킹 결과까지 예측하지 않는다. 후보 보존을 바꾼 뒤의 최종 성능은 새 dev 실험으로 확인한다.
3. **후보 확대와 다양성 통제를 분리한다.** 전체 합집합 최대 100개 재랭킹은 추가 연산 예산을 쓰는 별도 상한 탐색으로 표시한다. 겹침 기반 중복 억제는 원문 offset 기준을 먼저 고정하고, 번역 대안/같은 문서의 서로 다른 필수 사실을 무작정 제거하지 않는 별도 실험으로 한다. 두 변경을 동시에 넣어 원인을 혼동하지 않는다.
4. **잘림 진단을 완성한 뒤 청킹·학습을 결정한다.** exact model-visible span과 전체 청크의 근거 회수를 구분하고, 현재 3개 경계 실패는 별도 청크 설정 비교로 다룬다. Train 계열만으로 학습할 수 있는 실패가 반복적으로 남는지 확인하기 전에는 파인튜닝을 첫 해법으로 확정하지 않는다.

이 모든 후속 선택은 dev에서만 한다. test는 계속 잠근다. 후보 생성 변경으로 새 미라벨 결과가 나오면 AI 라벨을 자동 정답으로 늘리지 않고 검토 대상으로 모아 새 버전의 절차를 따른다.

## 5. 시간·메모리·잘림의 실제 범위

합성 질문·passage 한 종류를 2회 반복해 준비한 뒤 dev 79개를 한 번 측정했다. 아래 값은 각 질문에서 **따로 측정한 구성 요소 시간을 더한 뒤** 계산한 분위수다. 서버 요청의 실제 end-to-end 측정이나 각 단계 p50끼리의 합이 아니다.

| 방법 | 구성 요소 합 p50 / p95 (ms) |
|---|---:|
| B | 424.157 / 515.826 |
| D | 25.480 / 35.346 |
| H | 456.547 / 542.107 |
| HR | 2,556.104 / 2,924.512 |
| H25 | 456.251 / 541.562 |

재랭킹 단계만의 p50/p95는 2,119.564/2,458.314ms였다. E5의 전체 3,588청크 사전 인코딩에는 45,078.132ms가 걸렸고, 모델 로드는 E5 8,844.956ms·BGE 5,495.654ms였다. 이 준비 비용은 위 query 합계에서 빠져 있다. D는 문서를 사전 인코딩했고 B는 질의마다 tokenization을 수행하므로, 위 숫자만으로 같은 캐시·전처리 비용의 효율 비교라고 말하지 않는다. H25 시간도 이미 계산한 top-50 분기 시간을 재사용했으며 최적화한 top-25 실행을 측정한 수치가 아니다.

E5 passage는 38/3,588개(1.06%)가 잘렸고 query 79개는 모두 잘리지 않았다. BGE는 803/3,950쌍(20.33%)이 잘렸다. 이는 79질문×50후보의 **쌍 수**로, 고유 문서·청크 비율과 다르다. 준비 입력의 잘림 집계는 별도다. `max_tokens_before_truncation_since_model_load`는 모델 로드 이후 누적 최대이므로 E5 query 단계의 565를 query 최대 길이라고 읽으면 안 된다. 질문별 저장 기록의 실제 query 최대는 61토큰이다.

| 단계 | CUDA allocated peak | CUDA reserved peak | sampled process RSS peak |
|---|---:|---:|---:|
| E5 passage 사전 인코딩 | 0.776GiB | 1.766GiB | 1.384GiB |
| BGE 모델 로드 | 1.067GiB | 1.084GiB | 4.251GiB |
| BGE 79질문 재순위화 | 1.097GiB | 1.111GiB | 2.089GiB |

E5 단계를 닫은 뒤 BGE를 로드하는 순차 실행이었다. 따라서 두 모델이 동시에 상주하는 서비스의 peak를 확인한 것이 아니다. GPU 값은 PyTorch allocator 범위이며 전체 드라이버·디스플레이 VRAM이 아니다. CPU RSS는 50ms 간격 샘플이라 짧은 peak를 놓칠 수 있다. 단계별 peak를 더해 동시 메모리로 보고하지 않는다.

이 설정의 로컬 CUDA 오프라인 실행은 완료됐다. 외부 추론 API 요청·요금은 0건·$0이며 로컬 전력·장비 비용은 재지 않았다. 단일 순회·동시성 1이고 OS cache·전원·백그라운드 부하는 통제하지 않았다. 반복 지연 분산·부하 안정성·실제 HTTP·ACL·동시 수정의 비용은 이 실행에서 검증하지 않았다.

## 6. 현재 선택과 남은 작업

BM25 기본 서비스를 유지하면서 HR을 추가 검색 경로의 유력 후보로 검토할 근거는 생겼다. 그러나 E5 단독·혼합만의 품질 우위는 확인하지 못했고, HR도 근거 회수 36/59·교차언어 6/23·다중 문서 1/7에 그친다. 사용자 검수 0개와 새 퇴보 `060`을 포함해 공개해야 한다.

다음 구현 의무는 별도 서비스 통합에서 권한 선필터·revision 교체·삭제·cache 무효화·history/feedback 회귀를 실제 확인하는 것이다. 그 작업과 후속 후보 품질 실험을 구분한다. 이번 분석만으로 서비스 기본값을 교체하거나 M3 전체·학습·생성 답변을 완료했다고 표시하지 않는다.
