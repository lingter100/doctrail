# DocTrail 데이터·평가 설계

설계 기준일: 2026-10-12. 아래 수량과 통과 기준은 수집·실험 계획이며 실측 성과가 아니다. 현재 확보한 데이터와 실행 결과는 [STATUS.md](STATUS.md)에 따로 기록한다. 아직 없는 점수는 `미측정`으로 표시한다.

## 현재 파일로 확인한 파일럿 범위

2026-10-12에 [파일럿 manifest](../data/manifests/kubernetes-pilot.json)에서 Kubernetes의 Pods·ConfigMap·Namespaces·Secrets를 한국어·영어 각각 포함한 8개 레코드, 4개 문서 계열을 확인했다. 원본은 `4b10551a8c6f0a3f100356d8fc3c6fb5cfde1448` 커밋과 SHA-256으로 고정하며 분할은 `smoke`다. 이 파일럿은 아래의 1,000문서 목표나 독립 최종 평가셋을 달성한 상태가 아니다.

정규화 도구의 현재 식별자는 `hugo-light-v2`다. 도구는 glossary tooltip의 표시 문자열을 보존하고 일부 미해결 include·정의 shortcodes를 provenance에 기록한다. 모든 렌더링 문맥이 보존됐다고 가정하지 않으며 사람 검토 상태는 `pending`이다. [파일럿 질문](../data/evaluation/pilot-smoke.jsonl)은 파이프라인 점검용이고, 점수를 보고 수정에 사용한 질문을 최종 평가로 다시 소개하지 않는다. 실행 결과 수치는 상태 문서와 실제 실행 결과에서만 인용한다.

## 평가 질문

“한국어·영어 기술문서에서 사용자의 권한과 문서 버전을 지키면서, 작업에 필요한 원문 근거를 빠르게 찾을 수 있는가?”를 평가한다. 다음을 서로 구분한다.

1. **검색 품질:** 필요한 문서와 근거 구간이 상위 결과에 있는가?
2. **답변 품질:** 이후 생성한 주장이 반환한 근거로 뒷받침되는가?
3. **운영 정확성:** 숨긴 문서, 삭제된 내용, 이전 버전이 노출되는가?
4. **실행 비용:** 같은 장비에서 지연시간, 메모리, 인덱싱 시간이 얼마인가?
5. **사용 가치:** 실제 사용자가 더 정확히 과제를 수행하는가? 별도 사용자 검증이 필요하다.

자동 테스트 통과는 3번의 제한된 시나리오 증거다. 1번의 정답 라벨이나 5번의 인간 사용성 증거를 대신하지 않는다.

## 코퍼스 계획

첫 공개 원천은 Kubernetes 공식 문서 저장소의 한국어·영어 본문이다. [공식 LICENSE](https://github.com/kubernetes/website/blob/main/LICENSE)는 CC BY 4.0이다. 저작권·라이선스·출처·변경 표시를 보존하고 자료에 별도 조건이 있으면 수집 전에 확인한다. 저장소 전체 코드를 문서 라이선스로 일괄 분류하지 않는다.

목표는 정제 후 **약 1,000개의 문서 레코드**다. 실제 확보 수는 수집 후 센다. 하나의 긴 문서를 청크 100개로 나눠 100문서라고 세거나 동일 문서 버전·번역을 서로 독립된 내용 1,000개로 소개하지 않는다. 보고서에는 원본 파일 수, 정제 문서 수, 문서 계열 수, 언어별 수, 청크 수, 제외 수를 모두 표시한다.

| 데이터 층 | 내용 | 공개·집계 원칙 |
|---|---|---|
| 공개 원문 | 특정 커밋의 운영·개념·문제 해결 문서 | 커밋·경로·라이선스와 해시를 보존한다. |
| 정규화 문서 | 본문, 제목 구조, 원문 위치 | 변환 규칙과 버전을 남긴다. |
| 서비스 청크 | 검색용 본문 조각 | 문서 수와 구분하며 생성 설정을 기록한다. |
| 가상 런북 | 직접 작성한 온보딩·사고 대응 문서 | `synthetic=true`; 실제 사고·회사 기록으로 소개하지 않는다. |
| 권한·변경 시험 자료 | 접근 차단·수정·삭제를 확인하는 통제 자료 | 일반 검색 품질셋과 별도 집계한다. |

원문은 고정한 저장소 커밋에서 재수집할 수 있게 한다. 기본 공개 산출물은 다운로드·변환 스크립트와 manifest, 출처 고지다. 대량 원문·모델 가중치·사용자가 올린 문서를 Git에 포함하지 않는다. 재배포 여부는 원천 조건과 크기를 확인해 별도 결정한다.

## 문서 manifest

다음은 M2용 데이터 계약이다. M1 데이터베이스에 이미 모두 구현된 필드 목록이 아니다.

| 필드 | 의미 |
|---|---|
| `document_id`, `document_family_id` | 언어·버전별 레코드와 동일 내용 계열 식별자 |
| `source_repo`, `source_revision`, `source_path`, `canonical_url` | 원본을 다시 얻을 위치와 고정 버전 |
| `source_sha256`, `normalized_sha256` | 원본·정규화 결과의 내용 해시 |
| `title`, `language`, `topic`, `document_type` | 문서 분포와 세부 평가에 쓰는 메타데이터 |
| `license_id`, `license_url`, `attribution`, `modified` | 재사용 조건과 변경 표시 |
| `collected_at`, `source_updated_at` | 수집 시간과 원문 변경 시간; 모르면 `null` |
| `parser_version`, `normalizer_version`, `chunker_version` | 변환 재현 정보 |
| `synthetic`, `exclusion_reason` | 생성 자료 여부와 제외 근거 |
| `split`, `split_version`, `dedup_group` | 학습·개발·최종 평가 경계 |

`collected_at`을 문서가 작성되거나 최신 상태가 된 시간으로 사용하지 않는다. 번역 문서의 최근 커밋 시각만으로 원문과 내용이 동기화됐다고 판단하지 않는다.

## 정제와 분할 순서

1. HTML·템플릿·내비게이션·중복 머리말 처리 규칙을 정하고 원본을 보존한다. 코드·명령어와 경고 문구는 무작정 제거하지 않는다.
2. 빈 본문, 깨진 인코딩, 추출 실패, 지원하지 않는 자료를 분류한다. 제외한 이유와 수를 남긴다.
3. 정규화 해시로 완전 중복을 찾는다. 제목·경로 대응, 본문 유사도와 표본 검토로 유사 중복을 찾는다.
4. 같은 페이지의 번역·버전·이동 경로·짧은 파생 문서를 하나의 `document_family_id`로 묶는다. 유사도 도구의 판정과 사람 확인 상태를 분리한다.
5. 이 계열의 연결 관계를 기준으로 **문서부터** train/dev/test에 나눈다. 처음부터 질문이나 청크를 무작위 분할하지 않는다.
6. 문서 계열 기준 60/20/20을 초기 목표로 삼되 언어·주제·크기를 확인한다. 실제 개수와 편차를 기록한 뒤 고정한다.
7. 질문은 해당 분할의 문서만 근거로 만든다. 여러 문서가 필요한 질문은 모든 근거 문서가 같은 분할이 되도록 계열을 연결하거나 질문을 제외한다.
8. 질문 표현·정답 근거도 완전 중복과 유사 중복을 검사한다. 수정 후 manifest와 파일 해시로 분할 버전을 잠근다.

검색 인덱스에는 평가 대상 문서가 들어가야 정답을 찾을 수 있다. **평가 문서를 검색 인덱스에 넣는 것**과 **그 문서에서 만든 질문·정답을 모델 학습이나 튜닝에 쓰는 것**은 다르다. 후자는 금지한다. test 문서 계열은 학습의 정답·음성 예시·질문 생성 원천에서도 제외한다.

공개 기술문서가 사전학습 모델에 이미 포함됐는지는 완전히 확인할 수 없다. 이 한계를 명시하고, 반환 근거·권한·수정 반영을 평가한다. 이후 작성한 가상 문서의 평가도 별도 보조 결과로 제시하며 일반화 성능으로 과장하지 않는다.

## 질문 계획과 근거 라벨

검색·답변 평가 질문은 200~300개 범위에서 **240개를 초기 설계값**으로 잡는다. 개발 80개, 최종 평가 160개를 목표로 한다. 이 수량은 학습용 질문 수와 별개다. 품질 검토로 제외된 질문을 메우려고 낮은 품질의 질문을 그대로 넣지 않는다.

| 축 | 초기 설계 | 해석 |
|---|---|---|
| 질문 언어 | 한국어 160, 영어 80 | 양쪽 분할에도 비율을 유지하는 목표이며 실제 분포를 공개한다. |
| 응답 가능성 | 근거 있음 180, 근거 없음 36, 조건 불명확 24 | 근거 없음과 질문 명확화 필요를 구분한다. |
| 언어 교차 | 한국어 질문→영어 근거 등을 최소 60개 포함 | 별도 집계 축이며 위 수량에 더하는 추가 질문 수가 아니다. |
| 질의 유형 | 오류명·명령어, 절차, 동의어, 조건·버전, 여러 문서 비교 | 각 유형의 실제 수와 중복 태그를 공개한다. |

위 수는 분할 잠금 전 조정할 수 있다. 조정 이유와 최종 수를 기록하고 잠근 후 모델 성능에 맞춰 바꾸지 않는다. ACL과 변경 시험은 아래 별도 시나리오 집합으로 관리한다.

질문 레코드는 `query_id`, `text`, `language`, `intent`, `answerability`, `split`, `document_family_ids`, `relevant_spans`, `reference_answer`, `label_provenance`, `review_status`를 가진다. 근거 구간은 원본 버전의 문서 ID·정규화 본문 오프셋·짧은 확인용 인용으로 표시한다. 청크 설정이 바뀌어도 정답이 유지되도록 **청크 ID만 정답으로 저장하지 않는다**.

관련도는 `2=질문 해결에 직접 필요한 근거`, `1=일부 조건 또는 배경만 제공`, `0=관련 근거 없음`으로 정의한다. 같은 정답을 충분히 뒷받침하는 여러 구간은 모두 기록한다. 정답 근거를 한 구간으로 임의 고정해 다른 유효 문서를 오답 처리하지 않는다.

## 라벨의 출처와 검토

| 상태 | 허용하는 표현 | 허용하지 않는 표현 |
|---|---|---|
| `ai_authored` | AI가 초안 질문과 근거 후보를 만들었다. | 사람이 작성한 실제 질문이다. |
| `auto_checked` | 스키마·오프셋·중복·존재 여부를 자동 검사했다. | 질문과 정답의 의미가 검증됐다. |
| `human_reviewed` | 기록된 검토자가 원문과 질문·정답 적합성을 확인했다. | 독립 전문가 다수 검토가 있었다. |
| `adjudicated` | 여러 판단의 차이를 기록하고 해결했다. | 검토자 정보나 판단 기록 없이 합의했다고 주장한다. |

각 질문에는 작성 주체, 사용 모델·버전 또는 작성 방식, 프롬프트 해시, 자동 검사 버전, 사람 검토자와 시각을 분리한다. 실제 사람이 확인하지 않았으면 `reviewer=null`을 유지한다. AI가 다른 AI의 질문을 검토한 것은 사람 검토가 아니다.

최종 평가의 핵심 결과는 사람이 근거를 확인한 부분집합으로 보고하는 것을 목표로 한다. 검토가 없는 단계에서는 `자동 생성·자동 검증 예비 평가`라고 표시한다. 사용자 검토가 필요해도 데이터 수집·기준선 구축 등 독립적으로 가능한 작업은 먼저 진행한다.

검색 결과의 좋아요·싫어요는 노출된 결과에만 반응하는 편향이 있다. 이를 qrels 또는 학습 정답으로 바로 사용하지 않고 근거 검토 대기 자료로 저장한다.

## 비교 실험 순서

| 실험 | 바꾸는 것 | 반드시 고정하거나 기록할 것 |
|---|---|---|
| E0 | M1 BM25 기준선 | 토큰화, 문서·청크 버전, `k1`, `b`, IDF, 후보 수 |
| E1 | 토큰화 또는 청크 방식 중 하나 | 나머지 검색 설정; 두 변경을 한 번에 공로로 묶지 않는다. |
| E2 | 사전학습 임베딩을 이용한 밀집 검색 | 모델 리비전·접두사·정규화·정확 유사도 검색 |
| E3 | BM25 + 밀집 검색 결합 | 양쪽 후보 수·RRF 상수·중복 제거 규칙 |
| E4 | 상위 후보 재순위화 | 후보 집합·수, 최대 토큰·배치·정밀도 |
| E5 | 학습한 임베딩 또는 재순위화 모델 | 학습 전후의 같은 입력·코퍼스·평가·비용 조건 |
| E6 | 근거 기반 답변과 보류 | 동일 검색 결과를 이용한 생성 모델·프롬프트·판단 기준 |

Dense 또는 RRF가 BM25보다 반드시 좋다고 가정하지 않는다. 재순위화는 후보에 없는 정답을 새로 찾지 못하므로 재순위화 전 Recall도 기록한다. 모델 비교의 방향은 [BEIR 연구](https://arxiv.org/abs/2104.08663)를 참고하되 그 논문의 점수를 프로젝트 점수로 사용하지 않는다.

`multilingual-e5-small`은 첫 임베딩 후보다. 모델 카드의 검색 접두사와 정규화 방법을 따르고, 최대 512 토큰에 의해 잘린 근거 비율을 측정한다. [공식 모델 카드](https://huggingface.co/intfloat/multilingual-e5-small)

`bge-reranker-v2-m3`는 재순위화 후보다. 실제 사용 전에 라이선스와 고정 리비전을 기록하며 긴 입력·배치에 따른 GPU 메모리와 지연시간을 측정한다. [공식 모델 카드](https://huggingface.co/BAAI/bge-reranker-v2-m3)

## 측정 지표

| 영역 | 지표와 분모 |
|---|---|
| 문서 회수 | Recall@5/@10: 근거 있음 질문별로 상위 고유 문서가 알려진 관련 문서 중 얼마나 포함하는지 평균. 불완전 qrels라는 한계를 함께 기록한다. |
| 첫 유효 결과 | MRR@10: 근거 있음 질문의 첫 관련 문서 역순위 평균. 못 찾으면 0. 관련도 2를 기본으로 사용하고 다른 기준이면 표기한다. |
| 순위 품질 | nDCG@10: 관련도 0/1/2와 `2^rel-1` gain을 고정. 정답 집합과 문서 중복 제거 규칙을 기록한다. |
| 근거 회수 | Evidence Hit@k: 최소 하나의 정답 구간을 충분히 포함한 청크가 있는 질문 비율. span 포함·겹침 기준을 개발셋에서 정의하고 고정한다. |
| 다중 근거 | All-evidence Recall@k: 필요한 모든 근거 집합이 반환된 질문 비율. 하나만 찾은 경우와 구분한다. |
| 응답 가능성 | 근거 있음/없음/명확화 필요의 혼동행렬. 보류 정확도만으로 모든 질문에 보류하는 모델을 높게 평가하지 않는다. |
| 생성 단계 | 주장별 근거 지지율, 인용 구간 정확도, 사실 오류율. 자동 판정과 사람 판정 결과를 분리한다. |
| 답변 범위 | Coverage: 답변한 질문/전체 질문. 답변한 질문 중 근거 없는 답변 비율과 함께 보고한다. |
| 보안·변경 | 권한 없는 결과 수, 삭제·이전 버전 노출 수, 직접 조회 차단 결과. 평균 검색 지표에 섞지 않는다. |
| 성능 | 검색·재순위화·생성 각각 p50/p95, 전체 요청 시간, 인덱싱 시간, RAM·GPU peak, 디스크 크기 |

문서 순위는 중복 청크를 제거하고 최초 최고 순위를 보존해 만든다. 청크 순위의 지표도 별도로 남긴다. 번역을 정답으로 허용하는 질문에서는 어떤 언어의 근거가 유효한지 qrels에 명시한다. 필요한 언어를 충족하지 못한 번역을 자동 정답 처리하지 않는다.

지표에는 분할·검토 상태·질문 수·평가 제외 수를 같이 적는다. 한국어/영어/언어 교차/오류 코드/절차/근거 없음으로 나누어 성능 하락이 평균에 가려지지 않도록 한다. 여러 표현의 같은 질문과 같은 문서 계열이 묶여 있으므로 95% 부트스트랩 신뢰구간은 가능하면 독립 문서 계열 단위로 계산하고 표본이 작은 세부 집단의 불확실성을 설명한다.

## 권한·최신성 시험

통제된 계정 A·B·C와 두 워크스페이스를 사용한다. 예제 속 이름과 비밀 문구는 실제 개인정보가 아닌 시험 데이터다. 다음은 계획한 필수 시나리오이며 실행 완료 목록이 아니다.

- A의 개인 문서: A는 검색·조회 가능, 같은 공간의 B는 목록·검색·직접 조회 불가.
- 다른 워크스페이스의 C: 알려진 문서 ID, 검색 이력 ID, 피드백 대상 ID를 사용해도 접근 불가.
- 공개 문서를 개인 문서로 변경: B의 새 검색과 예전 링크 조회에서 내용 비노출.
- 내용 수정: 옛 문구 검색은 사라지고 새 문구가 나타나며 `revision`과 근거 본문이 일치.
- 삭제: 목록·검색·직접 조회에서 내용 제거. 피드백으로 삭제된 문서를 다시 읽을 수 없음.
- 반복 재처리: 청크가 늘어나지 않고 동일 버전의 근거가 중복되지 않음.
- 실패한 수정·재처리: 반쪽 본문이나 다른 버전 청크가 보이지 않음.
- 검색 후 원문 열기 전에 수정·삭제·비공개 전환: 최신 상태를 확인하고 오래된 근거로 답변하지 않음.
- 임베딩·캐시 도입 후: 재시작, 인덱스 지연, 캐시 적중에서도 같은 ACL·버전 조건 적용.
- 문서 안의 “규칙을 무시하라” 같은 문자열: 데이터로만 취급. 생성 기능에서는 지침으로 실행하지 않음.

M1에서 멤버 제거 API, 외부 커넥터 동기화 또는 캐시를 구현하지 않았다면 관련 시험은 `미구현`으로 표시한다. 존재하지 않는 경로의 성공을 기록하지 않는다. 결과가 0건 누출이어도 유한한 시험 범위의 결과이며 모든 공격에 안전하다는 증명은 아니다.

## 학습 데이터와 음성 예시

파인튜닝은 데이터 품질, 기준선 실패 유형과 실제 하드웨어 측정 이후 고른다. 작은 평가셋 240개를 학습셋으로 돌려 쓰지 않는다. 학습 질문은 train 문서 계열에서 별도로 작성하고, 생성·검토 여부를 기록한다.

우선 후보는 작은 임베딩 모델의 대조 학습 또는 재순위화 모델의 순위 학습이다. 대형 생성 모델 학습은 필수가 아니다. 학습 표본 수별 학습 곡선과 과적합을 먼저 보고 모델 크기·학습 방식·배치를 정한다. LoRA·양자화를 쓰면 무조건 6GB에 들어간다고 가정하지 않는다.

- Hard negative는 **train의** BM25·밀집 검색 후보에서 채굴한다. test 질문·근거를 후보 선정과 오류 분석에 쓰지 않는다.
- 미라벨 문서는 정답일 수도 있다. 관련성 미확인 후보는 자동 오답으로 간주하지 않고 검토하거나 제외한다.
- 정답의 번역·이전 버전·거의 같은 청크가 음성 예시가 되지 않도록 계열과 중복 그룹을 검사한다.
- In-batch negative에서도 같은 근거 계열·복수 정답 충돌을 제거한다.
- Train에서 만든 질문의 단순 표현 변경을 dev/test로 보내지 않는다.
- 사람 검토한 학습쌍과 AI 생성쌍의 결과를 분리하고, 생성쌍 추가 효과를 ablation으로 확인한다.
- Seed를 바꾼 실행과 학습 전 모델을 같은 평가 조건에서 비교한다. 모든 실패한 실행과 OOM도 기록한다.
- 성능이 개선되지 않으면 “학습 완료”와 “품질 개선”을 구분하고 원인을 보고한다.

## 실행 결과의 필수 메타데이터

모든 실험은 하나의 `run_id` 아래 설정·요약·질문별 결과·로그를 연결한다. 질문별 원문 출력은 공개 가능한 평가 자료에만 한정한다.

```text
run_id, started_at_utc, finished_at_utc, status
git_commit, git_dirty, dependency_lock_sha256, command
corpus_manifest_sha256, query_set_sha256, qrels_sha256, split_version
model_id, model_revision, model_license, tokenizer_revision
parser_version, chunker_version, lexical_tokenizer_version
retrieval_method, candidate_k, output_k, rrf_constant, bm25_parameters
max_tokens, truncated_fraction, precision, batch_size, seed
train_data_hash, negatives_hash, optimizer, learning_rate, epochs
cpu, ram, gpu, driver, cuda, framework_versions, os
warmup_count, measured_request_count, concurrency, cache_state
metric_definition_version, aggregate_metrics, subgroup_metrics
latency_samples, memory_peak, error_count, excluded_query_ids
label_provenance_counts, human_reviewed_count, limitations
```

실행하지 않은 필드를 가상의 값으로 채우지 않는다. 저장소 수정 상태에서 실행했다면 `git_dirty=true`와 diff 식별 정보를 남긴다. 학습 없는 실험의 학습 설정은 `null`로 표시한다.

지연시간은 워밍업과 실제 측정을 구분하고, 후보 수와 문서 길이, 동시 요청 수를 고정한다. GPU 작업은 동기화 후 시간을 잰다. API의 `elapsed_ms`만으로 네트워크·화면 렌더링을 포함한 사용자 대기시간이라고 하지 않는다. 배터리/전원과 전력 모드 등 노트북 조건도 가능하면 기록한다.

## 최종 평가를 잠그는 규칙

개발셋에서 토큰화·청크·모델·후보 수·보류 임계값을 선택한 후 설정 파일과 해시를 고정한다. 최종셋은 후보를 고르는 과정에서 반복 조회하지 않는다. 결과를 본 뒤 수정하면 다음 평가 버전 또는 추가 독립 최종셋이 필요하다. 기존 점수도 폐기하지 않고 왜 개발 판단에 사용됐는지 남긴다.

공개 저장소의 최종셋은 타인이 볼 수 있으므로 완전히 비공개인 블라인드 시험이라고 부르지 않는다. 이 프로젝트에서 변경·튜닝에 사용하지 않은 고정된 holdout이라는 의미다. 배포 후 회귀 점검에 반복 사용하는 순간 개발에 노출된 셋이므로 새로운 일반화 주장은 별도 데이터로 확인한다.

## 채택 판단

숫자 목표를 실험 전에 기록할 수 있지만 성능을 이미 달성한 것처럼 쓰지 않는다. 첫 측정 전 임의로 95% 정확도 같은 목표를 약속하지 않는다. 기본 판단 순서는 다음과 같다.

1. 누출·이전 버전 노출·잘못된 근거 매핑이 발견되면 평균 점수가 높아도 수정한다.
2. 주요 세부 집단의 회수율과 오류 유형을 확인한다.
3. 개발셋 품질 변화와 불확실성, p95·메모리 비용을 함께 보고 후보를 고른다.
4. 잠근 최종셋에서는 선택한 방법과 기준선의 결과를 모두 공개한다.
5. 개선 주장은 실제 효과 크기·표본 수·실행 환경 범위 안에서만 한다.

결과표는 `방법 / 코퍼스 버전 / 질문 수·검토 상태 / Recall@10 / MRR@10 / nDCG@10 / p95 / GPU peak / 실패 유형 / run_id`를 기본으로 한다. 아직 실행하지 않은 행에는 `예정` 또는 `미측정`을 쓴다.
