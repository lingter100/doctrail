# 회의 지능형 관리: 현재 설명할 수 있는 내용

## 2026-10-22 · 분류 이름과 저장 필드의 의미를 일치시킨다

독립 검토에서 최초 충돌은 다른 회의의 날짜가 현재 회의 날짜로 귀속된 문제로 좁혀졌다. 문서에 등장하는 날짜가 사실이라는 것과 그 날짜가 현재 회의 메타데이터라는 것은 다른 판단이다. 기존 분류 이름은 그 범위가 모호했고 저장 필드는 현재 회의의 단일값을 요구했다.

원문만으로 먼저 고정한37개 AI 주석과 실제 분류를 비교하면 허용 집합 일치33개·명확한 불일치3개·조건부 모호함1개다. 이는 사후 개발 진단이며 일반화 정확도는 아니다. 같은 현재 회의의 복수값 표현 문제라는 가설은 이번 자료로 지지되지 않았다. 현재 회의 귀속과 확약/제안/범위를 명확히 하는 새 prompt 정책을 설계하되 같은 자료·전체 원문·모델·예산·기존 검사를 유지한다. 실제 개선 결과는 아직 없다.

## 2026-10-22 · 출력 형식 통과와 의미·표현 계약은 다르다

실제 batch 개발 실행은37개 단위를5개 모델 호출로 처리했고 모든 응답이HTTP200·EOS로 끝났다. 그런데 제목·날짜·목적 중 단일값 필드의 서로 다른 추출값 때문에 generation_conflicting_metadata가 발생해 회의 분석을 완료하지 못했다. 전체105.672초/시작70.750초와 답변0은 실제 관측이며 이전의 다른 자료 실행과 속도 향상 배수를 비교하지 않는다.

현재 계약은 같은 값의 반복 근거를 허용하지만 서로 다른 제목·날짜·목적은 거부한다. 이것은 모델의 잘못된 분류일 수도 있고 올바른 복수 목적을 단일값으로 표현하지 못하는 문제일 수도 있다. 원문을 보지 않은 상태에서 어느 원인이라고 단정하거나 첫 값만 남겨 실패를 숨기지 않는다.

다음 독립 검토는 원문만으로37개 unit의 허용 분류·현재 회의 여부·복수 값의 관계를 먼저 고정한 다음 실제 모델 분류와 비교한다. 사후 개발 진단용 AI 주석이며 사전 gold·일반화 성능 평가·사용자 검수가 아니다. 아직 요약·결정·작업 추출과 자연어 답변의 전체 품질을 수용할 수 없다. 사용자가 직접 판단할 대상은 최종 결과의 내용과 사용 흐름이며, 현재 실패의 코드 원인 확인을 사용자에게 떠넘기지 않는다.

## 2026-10-22 · 원문을 줄이지 않고 반복 추론을 줄이는 이유

실제 서비스 연결에서 첫 회의 분석은114.182초가 걸렸고 두 번째는120.047초에 시간 초과했다. 원본 단위는54+62=116개였고 분류 모델 호출은105회 시도됐다. 기존 분류기는 각 단위마다 같은 긴 지침과 예시를 다시 처리한다. 이 기록은 반복 호출을 줄여 볼 근거이며, 병목의 모든 시간을 정확히 분해했거나 새 방법이 빨라졌다는 증거는 아니다.

선택한 후보는 최대8개 단위를 ID와 함께 묶어 한 번에 분류하는 방식이다. 모델은 각 ID의 라벨만 반환하고 원문 문장과 근거 위치는 기존 코드가 유지한다. 입력이4096토큰을 넘으면 생성 전에 묶음을 나누며, 단독 단위도 넘거나 답변이 잘리면 실패한다. 문장 선별·축약·실패 뒤 재생성으로 결과를 맞추지 않는다. 목적 heading의 기존 추론용 정규화와 원문 근거는 구분한다.

대안으로 시간 제한 상향과 prompt cache 변경을 검토했다. 전자는 사용자 대기 문제를 남기고, 후자는 호출 수를 줄이지 않으면서 기존 cache 검증 계약을 바꾸므로 우선하지 않았다. Batch는 분류 문법·출력 상한을 바꾸는 새 정책이며 라벨의 의미가 달라질 수 있다. 따라서 원문 좌표·전체 ID 보존 합성 검사와 실제 모델의 제안/결정/작업 구분, 처리 시간 검증을 나눠야 한다. 현재 요약은 최대4개 원문 구절을 선택하는 추출 요약이고 추상 요약을 새로 구현한 것은 아니다.

현재 새 adapter와 서비스 연결은 합성208개·Ruff와 최종 독립 코드 검토를 통과했다. 검토 중 발견한 문제는 실행 코드가 같아도 single과 batch가 다른 분석 정책인데, 선행 평가의 정책을 확인하지 않는 것이었다. 새 실행 의존 코드를 모두 고정하고 calibration과 validation의 정책 일치도 확인하도록 보완했다. 실제 모델의 batch 속도·정확성은 아직 측정하지 않았다. 사용자가 직접 확인할 부분은 제안을 결정으로 잘못 분류하지 않는지, 작업 담당자를 원문과 다르게 연결하지 않는지, 원문 근거를 직접 따라갈 수 있는지다. AI가 작성한 코드·합성 개발 자료·검토와 사용자 직접 검수는 별도로 기록한다. [설계](MEETINGS-ANALYSIS-BATCH-PLAN.md)와 [실제 기존 실패](../experiments/results/meetings-service-rag-analysis-timeout-v2.json)를 근거로 설명한다.

회의가 여러 번 진행되면 결정이 바뀌고 담당 작업이 흩어진다. 일반 문서와 회의록을 함께 검색하되, 답변의 사실·결정 시점·담당자마다 원문을 확인할 수 있어야 한다. 다른 사용자의 비공개 문서를 답변에 섞거나, 수정 전 회의록을 최신 결정처럼 보여주는 것도 실패다.

C2의 보존된 사후 진단에서는 인용 문자열47/47이 원문과 같았지만, 완전한 답변은 기준선과 후보 모두1/7이었다. 개선1건과 퇴보1건도 함께 있었다. 이 검토는 모델·이전 결과 정보를 일부 본 AI의 표본 라벨을 가린 진단이며 완전 맹검이나 최종 성능 수치가 아니다. 전체8쌍 실험은 언어 오류로 중단됐고 실패 상태를 유지한다.

## C3 방법을 선택한 이유와 실제 결과

검증한 C3 가설은 질문에 필요한 정보를 먼저 나누고 각 정보의 근거를 확인한 뒤, 모두 지원될 때만 자연어 답변을 만드는 것이다. 어느 필수정보가 원문에 없으면 전체 답변을 보류한다. 한 요청에서 최대 두 번 호출하며 두 호출이 하나의90초 제한을 공유한다.

대안으로 출력 길이 확대·구조만 강제하기·추가 자기검토를 고려했다. 그러나 이전 정상 출력14개는11~126토큰에 정상 종료됐으므로384토큰 상한 때문에 잘렸다는 관측은 없었다. 구조만 고친 이전 후보도 의미 오류를 남겼다. 따라서 요구사항 누락과 근거 지지를 직접 다루는 한 후보를 고정해서 검증했다.

실제 C3는6요청/9추론을 완료했지만 독립 최종답변 판정은2/6이다. 통과한2건은 모두 근거가 부족한 질문에 대한 적절한 보류다. 원문 인용30/30이 정확해도 원자 사실 지지는39/49에 그쳤다. 답할 수 있는 질문을 보류하거나 필요한 설명을 빠뜨리고, 예정된 일을 실제 완료 사실처럼 표현한 실패를 남겼다. 요구사항을 먼저 생성한다는 구조만으로 그 요구사항이나 근거 선택이 정확해지지는 않았다. [실제 결과](MEETINGS-C3-RESULTS.md)를 근거로 설명하며, 다른 문항을 쓴 C2보다 개선됐다고 단순 비교하지 않는다.

## 평가 순서와 한계

1. 코드를 고정한 뒤 출처·이용 조건을 확인한 공개 문서와 별도 표시한 합성 회의록을 준비했다. 전체 문서의 Python/Java 처리 결과를 대조했다.
2. 원문을 먼저 고정하고 질문·정답·전체 청크 선택을 작성했다. 작성자와 다른 AI가 질문의 요구·근거·문서 전체의 정보 부재를 검토한다.
3. Calibration6은 사전검토6승인 후 고정했고, 공식 입력6개도1,704~3,118토큰으로 상한5,120 안에 들어왔다. 실제 둘째 단계는3건에서만 실행했으며 입력1,437~1,932토큰이었다. 요청 시간은17.016~74.781초로 공유 제한을 지켰다.
4. 별도 validation8도 격리 작성·사전검토·고정·입력 검사를 마쳤지만 품질 생성은0이다. Calibration6/6 조건을 충족하지 못했으므로 validation을 열지 않는다.
5. 출력 검토자는 최종 답변2/6 판정을 먼저 잠근 뒤 중간 계획을 본다. 계획이 그럴듯하다는 이유로 잘못된 최종 답변을 통과시키지 않는다. 서비스 자동 채택은 하지 않는다.

실제 과정에서 부모 개발 에이전트가 Git 공백 검사 출력으로 validation 원문 일부를 보았다. 이를 숨기지 않고 [노출 이탈](MEETINGS-C3-SOURCE-EXPOSURE.md)로 기록했다. 코드·원문을 바꾸지 않고 다른 작성자와 채점자를 유지하지만 원래 비노출 조건이 복구됐거나 영향이 없다고 주장하지 않는다. 작은 AI 작성 표본·AI 검토·사람 검수0이라는 한계도 남는다.

## 자원 검사에서 배운 점

C4-P0는 캐시 모델의 사고 모드로 답변 근거를 한 호출 안에 유지할 수 있는지 확인하기 위한 연결·자원 검사였다. 합성 검사47개와 CI가 통과해도 실제 native는 부하 JSON의 반복 최소값10000을 거절했다. 고정 parser의 한도2000을 사전 검토에서 놓친 것이 원인이다. 오류 진단은 공통 logger를 우회해2167bytes를 기록했으므로 `--log-disable`만으로 원문 비기록을 보장할 수 없다는 점도 확인했다.

정상 합성 요청은62입력·521출력에56.172초였다. 이것은 답변 정확성 점수나 서비스 전체 응답시간이 아니다. 부하는 응답 전에 실패했으므로928token 실행시간은 미측정이다. 다음 계약은 반복 schema를 고정 literal로 바꾸고 진단 내용은 즉시 폐기하면서 전체 byte를 센다. 시간·토큰 상한은 유지하며, 내용이 담긴 파일이 없다는 이유만으로 무로그 통과라고 하지 않는다. [실패 원본](MEETINGS-C4-RESOURCE-RESULTS.md)과 [별도 후속](MEETINGS-C4-COMPAT-PLAN.md)을 구분해서 설명해야 한다.

별도 동일예산 호환성 후속에서는 고정 literal을 캐시 tokenizer로2052tokens라고 먼저 확인한 뒤, 커밋한 새 입력2건을 한 번 실행했다. 정상37.984초와928출력 부하88.000초, 진단0bytes·정리·metadata 재시작을 통과했다. 하지만90초 제한의 여유2초와 작은 표본이라는 한계가 있다. 미완성 padding을 끝까지 생성한 부하 통과를 자연어 답변 품질로 설명하면 안 된다. [별도 실제 결과](MEETINGS-C4-COMPAT-RESULTS.md)를 원래 실패와 함께 설명하고 다음 품질 자료를 새로 준비해야 한다.

## 실제 화면의 비동기 오류를 확인한 방법

결정 연결 삭제는 서버204만 확인하면 충분해 보이지만, 삭제 전 조회 응답이 나중에 도착하면 화면에 삭제한 연결이 다시 나타났다. 실제 Java GET을 받아 둔 상태로 전달만 지연하고, DELETE 뒤 서버에는 연결이 없는지 확인한 다음 이전 응답을 풀어 오류를 재현했다. 성공한 삭제 시 이전 조회의 소유권을 무효화하고 새로 읽도록 수정했다. 실패한 삭제는 기존 연결을 유지하고 자동 재시도하지 않는다.

추가로 복구 조회가 취소되면 이전 finally가 로딩 상태를 해제하지 못하는 오류도 실제 재현했다. 최종 관련 브라우저21개가 통과했지만 모델 전송은 합성 fixture다. 이 결과는 Java·React 동작 검증이며 자연어 답변 품질과 사용자 만족의 증거가 아니다. 구현·재현·문서화는 AI가 도왔고 사용자의 직접 검수는 아직0이다.

## 새 평가에서 원문을 먼저 고정하는 이유

C4에서는 공개 자료와 합성 자료를 각각 표시한12문서를 먼저 검토하고, Java와 Python의 전체 청크 처리를 대조했다. 그 뒤 새 역할이 calibration6개와 격리 validation8개를 작성했다. 질문을 본 뒤 원문을 고치거나, 입력이 길다는 이유로 불리한 근거를 빼면 평가 난도가 바뀌기 때문이다. 현재 독립 문항 검토 중이며 실제 답변 품질 결과는 아직 없다. 과거 자료의 중복 fingerprint 누락과 작성자 탐색 노출도 숨기지 않는다.

면접에서 “왜 작은 표본을 쓰나?”라는 질문에는 “무료 로컬 예산 안에서 필수 사실과 모든 충분한 근거 대안을 직접 검토할 수 있도록 작은 진단 표본을 고정했다. 일반 문서·복수 회의·혼합 근거·양방향 교차언어와 보류를 포함하지만, 이14문항을 전체 서비스 정확도라고 말할 수는 없다”라고 설명할 수 있다. 이 문장은 설명 예시이며 사용자가 직접 설계·검수했다는 주장은 아니다.

## 권한 검사는 서버와 화면에서 서로 다른 일을 한다

서버는 비공개 문서의 새 요청을 차단한다. 화면은 이미 받은 검색 결과가 뒤늦은 접근 거부 뒤에도 남지 않도록 정리해야 한다. 지식 검색의 오래된 근거를 다시 여는 실제 Java 검사에서, 원문404가 확인돼도 이전 결과가 보이는 결함을 재현했다. 원문을 연 질문·필터·동작을 함께 추적하고, 접근 거부 시 그 결과와 답변을 무효화하도록 수정했다.

원문이 바뀐 경우에는 이전 일반 검색 질문으로 이동하거나 모델을 자동 재호출하지 않고, 원래 통합 검색 조건으로 명시적 다시 검색/다시 질문을 제공한다. 새8+관련24 로컬 브라우저 검사가 통과했고 최종 커밋의 전체 브라우저57개도 CI에서 통과했다. 이 검증은 서버 ACL을 대신하지 않으며 조회하기 전 실시간 권한 변경 감지까지 구현했다는 뜻도 아니다. [재현과 한계](KNOWLEDGE-SOURCE-RECOVERY.md)에 원래 실패와 합성 모델 전송 사용을 구분했다.

## 사용자가 직접 확인할 부분

“인용이 원문과 같음”과 “답변 전체가 그 인용으로 지지됨”의 차이를 실제 실패 사례로 설명할 수 있어야 한다. 화면에서 근거로 이동하는 흐름, 결정 변경 이력이 이해되는지, 답변을 보류할 때 원문 검색으로 이어지는 흐름이 유용한지도 직접 확인해야 한다. 이 확인이 끝나면 실제 의견을 별도 사용자 검수로 기록한다. AI가 사용자를 대신해 완료 표시하지 않는다.
