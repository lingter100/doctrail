# 회의 지능형 관리: 현재 설명할 수 있는 내용

2026-10-15 기준. 이 문서는 면접 준비용 기술 설명이며 사용자가 이미 이해·검수했다는 기록이 아니다. 실제 수행 주체는 [기여 기록](CONTRIBUTIONS.md), 최신 실행 상태는 [STATUS](STATUS.md)에서 확인한다.

## 해결하려는 문제

회의가 여러 번 진행되면 결정이 바뀌고 담당 작업이 흩어진다. 일반 문서와 회의록을 함께 검색하되, 답변의 사실·결정 시점·담당자마다 원문을 확인할 수 있어야 한다. 다른 사용자의 비공개 문서를 답변에 섞거나, 수정 전 회의록을 최신 결정처럼 보여주는 것도 실패다.

Java 21/Spring Boot는 로그인·작업공간·접근 권한·문서와 회의 이력을 담당한다. React/TypeScript는 기존 문서 탐색 안에서 회의와 근거를 보여준다. Python은 로컬 모델과 데이터·학습·평가를 담당한다. 개발을 도운 GPT 계열과 서비스에서 실행하는 로컬 모델은 별개다. 현재 서비스 모델 실험은 무료 로컬만 사용한다.

## 기능 동작과 답변 정확성은 다르다

회의 분석·결정 변경·담당 작업·문서 권한과 수정/삭제 흐름을 실제 Java 및 React에서 검증했다. 하지만 그 검사만으로 자연어 답변이 맞다고 주장할 수 없다. 모델이 유효한 JSON을 반환하고 인용 위치가 원문과 같아도 질문의 일부를 빠뜨리거나, 인용이 뒷받침하지 않는 설명을 추가할 수 있다.

C2의 보존된 사후 진단에서는 인용 문자열47/47이 원문과 같았지만, 완전한 답변은 기준선과 후보 모두1/7이었다. 개선1건과 퇴보1건도 함께 있었다. 이 검토는 모델·이전 결과 정보를 일부 본 AI의 표본 라벨을 가린 진단이며 완전 맹검이나 최종 성능 수치가 아니다. 전체8쌍 실험은 언어 오류로 중단됐고 실패 상태를 유지한다.

## C3 방법을 선택한 이유와 실제 결과

검증한 C3 가설은 질문에 필요한 정보를 먼저 나누고 각 정보의 근거를 확인한 뒤, 모두 지원될 때만 자연어 답변을 만드는 것이다. 어느 필수정보가 원문에 없으면 전체 답변을 보류한다. 한 요청에서 최대 두 번 호출하며 두 호출이 하나의90초 제한을 공유한다.

대안으로 출력 길이 확대·구조만 강제하기·추가 자기검토를 고려했다. 그러나 이전 정상 출력14개는11~126토큰에 정상 종료됐으므로384토큰 상한 때문에 잘렸다는 관측은 없었다. 구조만 고친 이전 후보도 의미 오류를 남겼다. 따라서 요구사항 누락과 근거 지지를 직접 다루는 한 후보를 고정해서 검증했다.

실제 C3는6요청/9추론을 완료했지만 독립 최종답변 판정은2/6이다. 통과한2건은 모두 근거가 부족한 질문에 대한 적절한 보류다. 원문 인용30/30이 정확해도 원자 사실 지지는39/49에 그쳤다. 답할 수 있는 질문을 보류하거나 필요한 설명을 빠뜨리고, 예정된 일을 실제 완료 사실처럼 표현한 실패를 남겼다. 요구사항을 먼저 생성한다는 구조만으로 그 요구사항이나 근거 선택이 정확해지지는 않았다. [실제 결과](MEETINGS-C3-RESULTS.md)를 근거로 설명하며, 다른 문항을 쓴 C2보다 개선됐다고 단순 비교하지 않는다.

## 평가 순서와 한계

1. 코드를 고정한 뒤 출처·이용 조건을 확인한 공개 문서와 별도 표시한 합성 회의록을 준비했다. 전체 문서의 Python/Java 처리 결과를 대조했다.
2. 원문을 먼저 고정하고 질문·정답·전체 청크 선택을 작성했다. 작성자와 다른 AI가 질문의 요구·근거·문서 전체의 정보 부재를 검토한다.
3. Calibration6은 사전검토6승인 후 고정했고, 공식 입력6개도1,704~3,118토큰으로 상한5,120 안에 들어왔다. 실제 둘째 단계는3건에서만 실행했으며 입력1,437~1,932토큰이었다. 요청 시간은17.016~74.781초로 공유 제한을 지켰다.
4. 별도 validation8도 격리 작성·사전검토·고정·입력 검사를 마쳤지만 품질 생성은0이다. Calibration6/6 조건을 충족하지 못했으므로 validation을 열지 않는다.
5. 출력 검토자는 최종 답변2/6 판정을 먼저 잠근 뒤 중간 계획을 본다. 계획이 그럴듯하다는 이유로 잘못된 최종 답변을 통과시키지 않는다. 서비스 자동 채택은 하지 않는다.

실제 과정에서 부모 개발 에이전트가 Git 공백 검사 출력으로 validation 원문 일부를 보았다. 이를 숨기지 않고 [노출 이탈](MEETINGS-C3-SOURCE-EXPOSURE.md)로 기록했다. 코드·원문을 바꾸지 않고 다른 작성자와 채점자를 유지하지만 원래 비노출 조건이 복구됐거나 영향이 없다고 주장하지 않는다. 작은 AI 작성 표본·AI 검토·사람 검수0이라는 한계도 남는다.

## 자원 검사에서 배운 점

C4-P0는 캐시 모델의 사고 모드로 답변 근거를 한 호출 안에 유지할 수 있는지 확인하기 위한 연결·자원 검사였다. 합성 검사47개와 CI가 통과해도 실제 native는 부하 JSON의 반복 최소값10000을 거절했다. 고정 parser의 한도2000을 사전 검토에서 놓친 것이 원인이다. 오류 진단은 공통 logger를 우회해2167bytes를 기록했으므로 `--log-disable`만으로 원문 비기록을 보장할 수 없다는 점도 확인했다.

정상 합성 요청은62입력·521출력에56.172초였다. 이것은 답변 정확성 점수나 서비스 전체 응답시간이 아니다. 부하는 응답 전에 실패했으므로928token 실행시간은 미측정이다. 다음 계약은 반복 schema를 고정 literal로 바꾸고 진단 내용은 즉시 폐기하면서 전체 byte를 센다. 시간·토큰 상한은 유지하며, 내용이 담긴 파일이 없다는 이유만으로 무로그 통과라고 하지 않는다. [실패 원본](MEETINGS-C4-RESOURCE-RESULTS.md)과 [별도 후속](MEETINGS-C4-COMPAT-PLAN.md)을 구분해서 설명해야 한다.

## 실제 화면의 비동기 오류를 확인한 방법

결정 연결 삭제는 서버204만 확인하면 충분해 보이지만, 삭제 전 조회 응답이 나중에 도착하면 화면에 삭제한 연결이 다시 나타났다. 실제 Java GET을 받아 둔 상태로 전달만 지연하고, DELETE 뒤 서버에는 연결이 없는지 확인한 다음 이전 응답을 풀어 오류를 재현했다. 성공한 삭제 시 이전 조회의 소유권을 무효화하고 새로 읽도록 수정했다. 실패한 삭제는 기존 연결을 유지하고 자동 재시도하지 않는다.

추가로 복구 조회가 취소되면 이전 finally가 로딩 상태를 해제하지 못하는 오류도 실제 재현했다. 최종 관련 브라우저21개가 통과했지만 모델 전송은 합성 fixture다. 이 결과는 Java·React 동작 검증이며 자연어 답변 품질과 사용자 만족의 증거가 아니다. 구현·재현·문서화는 AI가 도왔고 사용자의 직접 검수는 아직0이다.

## 사용자가 직접 확인할 부분

“인용이 원문과 같음”과 “답변 전체가 그 인용으로 지지됨”의 차이를 실제 실패 사례로 설명할 수 있어야 한다. 화면에서 근거로 이동하는 흐름, 결정 변경 이력이 이해되는지, 답변을 보류할 때 원문 검색으로 이어지는 흐름이 유용한지도 직접 확인해야 한다. 이 확인이 끝나면 실제 의견을 별도 사용자 검수로 기록한다. AI가 사용자를 대신해 완료 표시하지 않는다.
