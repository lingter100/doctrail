# DocTrail 제품 정의

설계 기준일: 2026-10-12. 이 문서는 만들 제품과 검증할 가설을 정의한다. 현재 구현·검증 여부는 [STATUS.md](STATUS.md)를 기준으로 확인한다.

## 해결할 문제

작은 개발팀의 새 구성원이 “배포 후 계속 재시작하는 Pod는 어디부터 확인하지?”라고 묻는다. 관련 문서는 영어 오류명, 한국어 운영 지침, 이전 버전의 메모에 흩어져 있다. 검색 결과를 발견해도 어느 문장이 근거인지, 지금 유효한지, 자신이 볼 수 있는 문서인지 확인해야 한다.

DocTrail은 사용자가 접근할 수 있는 문서에서 관련 원문을 찾고 그 위치와 버전을 확인하게 돕는다. 첫 단계는 실제 업로드와 키워드 검색이다. 이후 의미 검색과 재순위화를 같은 평가셋에서 비교하고, 근거가 충분할 때만 답하는 기능으로 확장한다.

이 문제 정의는 작업 가설이다. 아직 특정 팀의 관찰·인터뷰·업무 성과로 검증한 수요가 아니다. 공개 기술문서 평가와 실제 팀 사용성 검증도 별도로 다룬다.

## 주 사용자와 작업

| 사용자 | 수행할 작업 | 성공 상태 |
|---|---|---|
| 새로 합류한 개발자 | 온보딩 순서, 실행 조건, 오류 대응 절차 찾기 | 검색 결과에서 필요한 근거를 열고 원문 문맥을 확인한다. |
| 운영 지침을 관리하는 개발자 | 문서 수정·삭제·공개 범위 변경 | 변경 후 검색과 원문 조회가 같은 버전·권한을 사용한다. |
| 프로젝트를 평가하는 기술 면접관 | 개선 근거와 실패 사례 재현 | 데이터·모델·설정·실행 환경이 연결된 실험을 다시 실행할 수 있다. |

지원 언어는 한국어 UI와 한국어·영어 문서다. 한국어 질문에 영어 근거를 찾는 기능은 모델 단계의 평가 대상이다. M1의 키워드 검색이 자동 번역이나 의미 검색을 지원한다고 표현하지 않는다.

## 첫 번째 실제 흐름

1. 로컬 계정을 만들고 워크스페이스에 들어간다.
2. 자신이 공개해도 되는 Markdown, UTF-8 텍스트, 텍스트 PDF를 업로드한다.
3. 처리 결과, 문서 제목, 공개 범위와 분할된 근거 수를 확인한다. 스캔 PDF나 처리 실패는 실패 상태로 보여준다.
4. 검색어를 입력하면 접근 가능한 문서의 원문 발췌가 표시된다.
5. 결과를 누르면 현재 문서를 다시 읽고 해당 발췌·PDF 페이지·문서 버전을 확인한다.
6. 문서를 수정하거나 삭제한 뒤 다시 검색한다. 이전 내용이 검색에 남지 않아야 한다.
7. 검색이 도움이 됐는지 표시할 수 있다. 이 클릭은 편향 가능한 사용 피드백이며 확정 정답 라벨로 자동 승격하지 않는다.

이 흐름에 생성 답변, 임베딩, 외부 API 호출은 필요하지 않다. 빈 검색 결과에는 근거를 찾지 못했다는 상태를 보여준다. 이를 LLM의 무응답 판단 정확도로 집계하지 않는다.

## M1 범위

| 포함할 항목 | 확인할 동작 |
|---|---|
| 계정과 워크스페이스 | 서버 세션으로 인증하고 소속을 확인한다. |
| 문서 업로드·보관 | 재시작 후에도 문서와 검색 대상이 유지된다. |
| 문서별 공개 범위 | `workspace`는 소속 구성원, `private`는 소유자만 읽는다. |
| 원문 근거 검색 | BM25로 청크를 정렬하며 발췌가 실제 저장된 본문과 일치한다. |
| 수정·재처리·삭제 | 중복 청크나 이전 버전이 노출되지 않는다. |
| 검색 이력·피드백 | 본인 이력만 확인하고 현재 권한을 검증한다. |
| 실패 상태 | 파일 제한, 처리 실패, 만료된 세션, 권한 거부를 설명한다. |

첫 화면에는 가짜 문서·검색 성공률·절감 시간을 미리 넣지 않는다. 예제 자료를 제공하면 가상 자료임을 표시하고 사용자가 선택해 넣게 한다. API 세부 사항은 [API-CONTRACT.md](API-CONTRACT.md)에 있다.

## 다음 단계의 핵심 기능

- **의미가 같은 질문 찾기:** 영어·한국어 단어가 직접 겹치지 않아도 필요한 근거를 찾는지 실험한다.
- **여러 검색 방법 비교:** 기준선과 개선 방법을 같은 질문·코퍼스에서 평가한다. 개선되지 않으면 채택하지 않는다.
- **검증 가능한 답변:** 문장별 근거와 문서 버전을 연결한다. 근거 부족·질문 모호함·상충하는 문서를 구분한다.
- **변경 반영:** 문서 내용, 공개 범위, 삭제 상태가 검색·답변·캐시에 함께 반영되도록 한다.
- **오류 설명:** 실패를 파싱, 근거 누락, 순위 오류, 문맥 부족, 답변 생성 오류로 나눠 개선한다.

## 의도적으로 제외한 범위

M1에서 Slack·Notion·Jira OAuth 연동, 자동 에이전트 실행, 웹 검색, OCR, 표·이미지 이해, 실시간 공동 편집을 만들지 않는다. 이 기능은 데이터·평가·모델 실험을 완성한 뒤 실제 필요에 따라 다시 검토한다.

공개 GitHub 소스 공개는 승인된 범위다. 실제 사용자의 자료 업로드를 받는 공개 서비스 배포, 유료 모델 API, GPU·클라우드 결제는 별도 승인이 필요하다. 개발 중 사용한 AI 도구와 제품이 사용하는 추론 모델은 구분해 기록한다.

## 검증할 제품 가설

| 가설 | 필요한 증거 | 현재 상태 |
|---|---|---|
| 원문 위치 표시가 근거 확인을 돕는다. | 동의한 사용자의 동일 과제 수행 시간·성공률·막힌 지점 | 미검증 |
| 혼합 검색이 한국어·영어 질문에 더 강하다. | 잠근 평가셋의 BM25 대비 지표·신뢰구간·실패 유형 | 미검증 |
| 재순위화 비용이 품질 개선에 비해 적절하다. | 후보 수별 정확도, p50/p95, 메모리 | 미검증 |
| 근거 부족 시 답변을 보류하면 오답을 줄일 수 있다. | 답변 범위와 오답률을 함께 보여주는 곡선 | 미검증 |

사용성 검증을 진행한다면 소수 참가자의 결과임을 명시하고 개인 식별 자료를 공개하지 않는다. 실제 사용자가 참여하지 않았다면 시나리오 실행을 사용자 검증으로 바꾸어 표현하지 않는다.

## 포트폴리오에 남길 결과

기능 화면보다 다음 질문에 답할 수 있는 자료를 우선한다.

1. 어떤 질문에서 기준선이 실패했고 왜 실패했는가?
2. 데이터·분할·정답 근거를 어떻게 만들고 검토했는가?
3. 모델 변경이 같은 조건에서 무엇을 개선하거나 악화했는가?
4. 제한된 하드웨어에서 선택한 타협은 무엇인가?
5. 권한·문서 변경·근거 없는 질문에 시스템은 어떻게 동작하는가?
6. 작성자가 직접 이해하고 설명한 결정과 AI가 도운 구현은 무엇인가?

경쟁 제품과 채용 요구에 관한 근거는 [research.md](research.md)에 정리했다. DocTrail의 목표는 채용 결과 보장이 아니라 위 질문에 실제 증거로 답할 수 있는 프로젝트를 완성하는 것이다.
