# 결정 기록

## 2026-10-14 · C2 비교와 검토의 실행 계약

원격 Linux의 합성 시간 모순은 서비스 제한을 완화할 이유가 아니다. 질문 작성 전 fixture의 고정10ms만 가짜 backend의 실제 계약값으로 교체하고 source-freeze-v2를 별도로 등록한다. v1·실패CI·기존 실제 자원2회는 그대로 보존한다.

줄 단위 대조군과 문단 후보는 동일 DTO와384출력/4096입력/90초 조건으로 비교한다. 새 실행기는 결과 의미를 스스로 채점하지 않고 정상 실행된 의미 실패도 전체 등록 calibration에 남긴다. Native·구조·설정·시간 오류는 즉시 중단하고 미실행 항목을 보존한다. 이전 자원2회를 다시 호출하지 않는다.

독립 판정은 역할을 숨긴 개별 응답에서 먼저 끝내고 SHA를 잠근 후에만 후보별 점수를 계산한다. 원본 응답 재생·설정/토큰/시간 대조·완전한16개 결과·관련 없는 인용0·C2 8/8·개선≥1·퇴보0을 요구한다. 선택된 C2만12개 검증으로 진행한다. 올바른 보류의 인용/사실 비율은N/A다. 인용문이 길어졌거나 테스트가 통과했다는 사실을 의미 개선으로 바꾸지 않는다.

검증 자료 보호는 hash 비교만으로 충분하지 않다. 파일을 읽은 뒤 잘못된 hash를 거부하면 이미 본문을 열었기 때문에, 계획에서 각 artifact의 경로까지 등록하고 실제 해석 경로의 중첩을 먼저 검사한다. 익명화 역시 label 숨김일 뿐 인용 모양으로 추측할 수 있어 그 한계를 판정에 기록한다. Source 채택 HOLD는 작성자의 검증 작업이며 사용자 승인 대기가 아니다.

## 2026-10-14 · 자원 통과 후 공정한 대조군

같은 고정 모델의 C2-P0 실제2호출이 자원 조건을 통과했다. 강제 반복 출력에서384 tokens를32초 안에 만들었지만 이를 자연어 품질이나 이전C1대비 속도 개선으로 주장하지 않는다. 새 비교에서는 C0의 원래 줄 구간·prompt·mapper를 가져오되 별도 대조군 파일에서 출력384/시간90을 적용한다. 과거 C0 수치를 새로운 예산의 비교군으로 재활용하지 않는다. 대조군·후보 모두 새 동일 입력을 받아야 하며 더 넓은 인용만으로 의미 성공이 되지 않도록 주장별 지지와 불필요 인용을 독립 검토한다.

## 2026-10-14 · 단일 생성과 자원 선행 조건

C1의 자기검토 대신 새 C2-P0에서 원문 단락의 연속성만 바꾸는 후보를 구현한다. 1024-codepoint 제한을 넘는 단위를 조용히 잘라 쓰지 않는다. 384-token/90초는 자원 검증 전 고정한 예산이며 작은 정상 호출과3800~4096 실제 native 입력·384강제 출력 부하를 구분한다. 강제 length 종료는 자원 검사에만 사용하고 서비스 답변 성공으로 쓰지 않는다. 부하 timeout은 안전 정리의 증거가 될 수 있지만 지연 준비 실패이며 후속 품질 평가를 열지 않는다. 기존 코드/질문은 동결 보존한다.

## 2026-10-14 · C1 구조 실패 후 종료와 후속 개발

실제 네 번째 V0에서 초안의 두 주장 중 한 주장 검토가 누락되어 정상적으로 차단됐다. 같은 자료를 고쳐 다시 실행하거나 미실행 네 건을 이어 돌리지 않는다. 전체 후보 선택은 실패이며 앞의 세 정상 반환도 의미 정답으로 승격하지 않는다. 완료형 감사 도구는 그대로 보존하고 별도 사후 부분 검토는 실패 분석에만 사용한다.

후속 구현은 문법에서 모든 주장 인덱스를 한 번씩 요구하는 좁은 구조 수정부터 시작한다. 검토 결과의 의미를 코드가 만들어 주거나 parser 조건을 완화하지 않는다. 실제 생성 속도 약5token/s와 요청119초 관찰 때문에 새 품질 질문을 만들기 전에 수정 경로의 자원 가능성을 별도 중립 자료로 확인하는 방향을 검토한다. 비용은 무료·로컬로 유지한다.

그 뒤 고정된 사후 의미 판정에서 D0/C1 모두0/4이며 선택 인용의 조건·문장 후반·결론 누락이 확인됐다. 따라서 구조 문법만 고친 후보를 새 품질 평가에 넣는 방향은 채택하지 않는다. 아직 그 대기 구현은 시작되지 않았으며, 후속 설계를 근거 단위의 완전성으로 전환한다. 오류 원인 분석에 따른 결정 변경을 보존하고 인용 폭을 넓혀 채점 기준을 우회하지 않는다.

## 2026-10-13 · C1 독립 답변 검토와 입력 무결성

후보 자신의 V0/V1 판단을 정답으로 사용하지 않는다. 실행 전에 등록한 seed로 D0·C1 답변의 순서를 섞고 역할 대응표를 분리한다. 별도 AI가 원문·고정 oracle에 대한 판단을 확정한 뒤 대응표를 열어 개선과 퇴행을 집계한다. 오류 형태와 같은 문장으로 역할을 추측할 수 있다는 한계와 사용자 검수 0을 유지한다.

검토 자료를 만들 때 파일 해시 검사·내용 해석·영수증 기록 사이에 파일이 바뀔 수 있다는 독립 코드 검토 지적을 수정했다. 각 입력을 한 번 읽은 바이트로 해석하고 해시를 계산해 동일 snapshot을 기록한다. 동시 파일 변경·중복 JSON 키·NaN·크기 제한의 합성 회귀를 포함해 12개 검사가 통과했다. 이는 감사 자료의 무결성 검사이며 모델 답변 품질의 증명이 아니다.

## 2026-10-13 · 목표 기반 연속 진행과 C1 구현

사용자가 목표 설정을 통한 지속 개발을 직접 요청했다. 도구에 회의 1차 확장 완료 목표를 등록했고 다음 단계 승인 없이 C1 구현을 시작했다. 이전 무료 전용·비공개 로컬 실행·사용자 검수 경계는 그대로 따른다. 새 의미 거부는 Python에서 별도 오류로 기록하고 기존 Java에서는 안전한 일반 실패 `generation_unavailable`로 매핑된다. `insufficient_evidence` 성공 보류와 구분되므로 현재 오프라인 후보 단계에서는 동결 Java 계약을 수정하지 않는다. 별도 합성 HTTP 경계 테스트로 이를 확인했다.

실제 생성 전 C1 소스·정책·가족 등록을 고정한다. 이전 native launcher의 기본 warmup은 숨은 생성 예산으로 오해하지 않도록 새 launcher에서 명시적으로 끈다. D0의 prompt·구간·decoder·생성 설정과 가중치는 유지하지만 이전 launcher 시간과 동일 조건의 비교라고 쓰지 않는다. 저장 파일의 Windows 일시적 PermissionError는 같은 임시 파일의 교체만 3회로 제한하며 모델·문항은 반복하지 않는다. 독립 검토의 두 운영 결함을 수정한 후에만 질문 작성과 실제 비교로 넘어간다.

## 2026-10-13 · 무료 전용 진행과 C0 종료

사용자는 구체적 API 비용 제안을 검토한 뒤 무료 방식만 사용하도록 정했다. API 비교는 승인 대기가 아니라 보류 상태이며 실제 호출·과금은 0이다. 이후 유료 선택을 반복 권유하지 않는다. 개발 보조 모델 설정과 서비스 운영 모델 비용을 구분한다.

C0는 정확한 인용 9/9를 확보했지만 의미 기준 2/4로 실패했다. 이득은 인용 복사와 진행자 답변 누락 회복이며, 의제의 완료 사실화와 선택 근거 밖의 이유 추가는 남은 실패다. 동일 네 질문에 후속 문구·모델을 맞추는 실험은 끝낸다. 무료 후속은 새로운 가설·별도 calibration·평가 분리를 먼저 설계하며 기존 결과를 성공으로 바꾸지 않는다.

[C1 후속 설계](MEETINGS-FREE-ANSWER-PLAN.md)는 같은 9B로 초안·검토·수정 최대 1회·재검토만 허용한다. 전체 요청 120초를 공유하고 최대 4회 호출한다. 새 calibration 8건에서 기존 초안보다 실제로 개선되고 완전성·자원 기준을 통과해야 별도 가족의 validation 8건을 준비한다. 같은 모델의 검토를 독립 정답으로 쓰지 않고 잘못된 보류·의미 거부도 실패로 센다. 계획 최대 72회와 실제 0회를 구분하며 구현·새 자료·실행은 다음 묶음이다.

## C0 실행 전 고정

원문 복사를 모델 생성에서 분리하는 C0를 새 Python 어댑터·별도 실행기로 구현했다. ID가 가리키는 청크·원문·codepoint 위치는 요청별 불변 값이며 기존 Java가 현재 권한·리비전·청크 내 인용을 재검증한다. API/DB/React 계약을 추가하지 않는다. 동적 문법은 실제 요청의 인용 가능한 ID와 JSON 구조만 허용하고 사실·정답을 넣지 않는다.

분할 상한·정책 선택은 일부 새 공개 원문의 우발 노출보다 먼저 끝났다. 원래 새 12문항은 미실행으로 보존하고 현재 실행 계획은 중립 2건·이미 공개된 개발 회귀 4건만 포함한다. 데이터 수량이나 통과 기준을 사후 바꾸지 않는다. 코드 검토에서 Java quote의 기존 검사가 nonblank가 아닌 길이 검사임을 확인해 문서 설명만 바로잡았다. C0의 더 엄격한 공백 전용 인용 제외 정책은 유지한다.

## 2026-10-13 · 9B 실패 보존과 다음 비교의 경계

9B는 중립 실행 조건을 통과했지만 전체 답변 기준은 1/4만 통과했다. 인용 복사 오류, 누락, 선택한 근거보다 넓은 부연을 구분한다. 원문에서 비슷한 문자열을 찾아 교정하거나 실패한 의미 gate를 완화하지 않는다. 새 검증 질문은 닫아 두고 현재 결과를 독립 정확도로 발표하지 않는다.

다음 무료 대안은 모델에게 원문 문자열을 재작성시키지 않고, 요청별 고정 span ID를 선택하게 하는 별도 구조다. 인용 복원은 서버 코드가 맡되 사실 지지·완전성은 별도로 평가해야 한다. 기존 Java 권한·revision 재검증과 외부 DTO를 최대한 재사용한다. 설계만 준비한 상태이며 아직 효과를 주장하지 않는다.

유료 API 비교는 공개·합성 자료, 최대 24호출, 사용료 US$2의 구체적 제안으로 분리했다. 사용자 비용 승인 전 호출·자동 결제·키 접근은 하지 않는다. 이는 일반 구현 선택의 재승인이 아니며 기존 무료 작업을 중단하는 조건도 아니다. 서비스 외부 배포는 별도 승인 범위다.

선택 의존성 없는 CI의 psutil 오류는 테스트 환경 문제였다. 동결된 pyproject/lock을 바꾸거나 무거운 retrieval 전체를 설치하지 않고, 이미 lock에 존재하는 Linux wheel을 CI 전용 해시 파일로 설치한다. 실제 모델 비교를 다시 실행하지 않는다.

## 2026-10-13 회의 생성 모델의 제한된 용량 비교

회의 개발 v11은 영어 근거 유실을 제거한 뒤에도 날짜·주체·인용 혼동과 담당자 미정 작업 누락을 해결하지 못했다. 기존 출력과 실패한 Java 운영 v2를 보존하고 Qwen3-4B-Instruct-2507/Unsloth Q5_K_M 후보 하나를 무료 로컬 환경에서 비교한다. 기존 잠금 의존성을 바꾸지 않는 별도 llama.cpp 실행 파일과 Python HTTP 어댑터를 사용한다. 실제로 바뀌는 모델·양자화·runtime을 모두 기록하며 모델 크기만의 인과 효과로 해석하지 않는다. ## 2026-10-13 회의록 확장 우선순위와 호환성

사용자가 회의록 등록·AI 요약·문서와 통합된 RAG·결정 변경 이력·담당자별 작업·기존 UI 통합·실제 데이터 검증을 1차 범위로 지정했다. 이 요청을 기존 M5-B 실행보다 우선한다. M5-B의 고정 자료와 정책 비교는 수정하거나 수행한 것으로 처리하지 않는다. 새 제품 개발 자료를 기존 평가에 섞지 않는다.

회의록은 기존 문서 ID·내용·청크·권한·리비전을 그대로 사용하고 추가 분석·편집·연결 정보만 별도 테이블로 보존한다. AI 원본 결과와 사용자 편집을 분리하고 원문 수정 후에는 이전 분석을 최신으로 제공하지 않는다. 통합 검색은 접근 가능한 작업공간의 문서와 회의를 권한 및 메타데이터로 먼저 거른 뒤 동일 검색 방식을 적용한다. 결정 연결은 명시적 근거와 사용자 편집으로 생성하며 유사도·최신 날짜만으로 이전 결정을 폐기하지 않는다.

기존 로컬 Qwen 후보의 실제 품질 한계를 감안해 새 worker는 근거 문장 선택·분류를 중심으로 제한된 초안을 제공한다. 원문 인용 일치는 의미 정답 증명이 아니며 실제 호출·내용 검토를 별도로 남긴다. 새 API·GPU 임대·클라우드·공개 서비스 배포 비용은 발생시키지 않는다. [설계](MEETINGS-DESIGN.md)에 세부 계약과 완료 조건을 기록한다.

### 실제 통합 실패에 따른 변경

자유 JSON 회의 추출은 길이 초과와 schema 실패가 반복되어 실제 Qwen의 제한 라벨 분류와 발췌 요약으로 바꿨다. 담당자·기한을 추측해 채우지 않고 사용자 확인 전 상태로 둔다. 답변은 자유 자연어 생성을 유지하되 모델이 긴 UUID와 Markdown 인용문을 다시 쓰게 하지 않고 짧은 근거 ID를 선택하게 한다. 서버가 원문·절대 위치를 복원하고 Java가 현재 revision과 다시 대조한다. 이는 문장 의미를 인증하는 기능은 아니다.

짧은 문장 ID를 줄이려고 worker 안에서 BM25를 한 번 더 적용한 v9 경로는 한국어 질문의 영어 근거를 버렸다. 실제 hybrid 검색이 영어 운영 문서를 찾아도 생성 모델에 전달하기 전에 잃는 회귀다. v10 개발·v2 실제 서비스 결과를 보존하고, 제한적인 Astra max 비교의 권고에 따라 Java가 보낸 각 chunk 전체에 ID 하나를 주는 후속 경로를 선택한다. 기존 토큰 한도를 초과하면 명시적으로 실패한다. 새 데이터베이스·검색 기술·추론 심판을 추가하지 않고 근거 유실 지점부터 고친다. 넓어진 인용 범위와 여전히 남는 날짜·주체·질문 일부 누락 위험을 별도로 검토한다.

## 2026-10-13 M5-B 자료를 질문보다 먼저 분리

답변의 원문 인용 검사 통과가 의미 지지·질문 전체 완전성을 보장하지 않는다는 M5-A 실패를 바탕으로, 기존 정책과 짧은 예시 세 개를 더한 정책 하나만 비교한다. 모델 용량 변경이나 JSON 수선부터 적용하지 않는다. 문서 계열 배정을 `2de1487`에 먼저 저장한 뒤 질문 작성을 시작했다. LF로 정규화한 registry SHA는 `b2fb4f0749995a2aa7f87f30a5531e23fb5373f0b42b0b778e0bf7ea7674b4cc`이며 Git blob과 같다. 최초 Windows CRLF 사본의 hash는 배정 변경 없이 LF로 대체했다.

같은 사실의 번역·수치 변형·근거 제거를 서로 다른 독립 표본처럼 나누지 않는다. 새 가상 업무 문서 12계열을 고정 SHA 순서로 calibration/validation 각 6계열에 배정한다. 각 계열의 4문항은 상관된 사례다. 별도 예시 3계열은 양쪽 자료에서 제외한다. 이는 통제된 생성 정책 진단이며 실제 개발 조직 문서에 대한 일반 성능 검증은 아니다. 완성된 자료·프롬프트·검토·토큰 한도를 고정하기 전 생성 실행은 하지 않는다.

사전 선택 기준은 수락된 오류·불완전 답변 수 감소, 완전 지지 답변 수 비감소, 구조 성공 수 비감소를 모두 만족하는지다. 자동 상태 일치나 정확한 인용만으로 선택하지 않는다. validation을 본 뒤 예시·규칙을 바꾸지 않으며, 공개 저장소에 있는 검증 자료의 접근 제한은 역할·절차상의 통제이지 암호화나 접근 제어 보장이 아니다.

## 2026-10-13 M5 v2 결과에 따른 다음 판단

## 2026-10-13 M5 첫 생성 실험의 경계

프롬프트·모델 manifest·합성 질문·소스·실행 계획을 실제 생성 전에 고정한다. 구조 실패는 그대로 기록하며 남은 항목을 실행하고, 자원·시간·런타임 실패는 실행을 중단한다. 자동 복구·재시도·정답 사후 변경 없이 실패 보고서를 보존한다. 생성 과정의 특수 토큰을 지워 JSON을 수선하지 않는다. 사전 AI 검토에서 상충 정책의 적용 대상이 모호해 같은 현재 작업공간/로그임을 명시했고, 변경 전후 질문 해시를 검토 영수증에 남긴다.

## M2 데이터와 측정

- Kubernetes 고정 커밋을 선택했다. 사내 문서를 수집하지 않고 한·영 원문·라이선스·개정 식별자를 재현할 수 있기 때문이다. 실제 조직 문서·직원 질문의 대표 표본은 아니다.
- 단순 Hugo 태그 삭제 대신 `hugo-strict-v1`의 허용 목록 정제와 미해결 문서 제외를 택했다. 2,287개 검사 목록에서 313개만 채택했고 1,000개 목표 미달을 공개한다. 정제 확대는 v1을 덮어쓰지 않는 후속 작업이다.
- 질문 작성 전에 번역 경로·정확 중복·5-token shingle Jaccard 0.85 이상을 연결해 분할했다. 문서 무작위 분할은 번역·복제본을 양쪽에 보낼 수 있다. 연결 그룹도 의미 중복 전체를 찾지는 못한다.
- Train 문서는 향후 학습용으로 예약했다. 현재 검색 인덱스는 313문서 전부이고 dev 질문만 평가한다. 검색 대상 문서의 존재와 정답 라벨을 학습에 쓰는 것은 구분한다. Test 질문 성능은 실행기에서 거부한다.
- AI 후보 240개를 원본으로 동결했다. 평가 전 AI 검토에서 `m2-dev-055`의 두 문서 필요성이 불확실해 원본을 유지한 79문항 dev v1.1을 만들었다. 올바른 수정 답안을 확정한 것이 아니며 사용자 검수도 아니다. 결과를 본 뒤 유리한 질문을 제외한 것이 아니다.
- 하나의 필수 사실에 대한 대체 구절은 OR, 서로 다른 필수 사실은 AND로 평가한다. 문서 적중과 근거 적중을 분리하며 10청크 결과의 고유 문서 순위를 전체 문서 top-10이라고 부르지 않는다.
- 양성 59개 중 30개만 필수 근거를 모두 찾았다. 주석상 교차 언어만 가능한 23개 중 1개가 성공했다. 다국어 임베딩 비교의 동기를 얻었지만 개선 효과는 아직 측정하지 않았다.
- 3질문은 주석 span이 현 청크 안에 온전히 들어가지 않는다. 기준선 점수·라벨을 유지하고 청크 설정 실험을 분리한다. 순위 모델 변경과 청크 변경을 한 번에 묶지 않는다.
- 오프라인 순위 계산과 실제 loopback HTTP를 각각 측정했다. 첫 HTTP 실행의 Windows 임시 파일 정리 실패를 보존하고 경로 검사·제한된 재시도를 추가했다. 영구 오류는 계속 실패하며 성공으로 숨기지 않는다.
- 검수 화면은 실제 사람이 입력한 판단을 별도 영수증에 기록한다. 자기 기입 이름은 인증 신원이 아니며 AI가 사용자 대신 확인 체크나 승인을 하지 않는다.

## M3 실행 전 동결한 선택

- 사용자의 자동 진행 위임에 따라 현재 채팅의 매시간 후속 실행을 등록했다. 유료 자원·서비스 외부 공개·실제 사용자 검수는 위임 범위에 포함하지 않는다.
- E5-small 다국어 임베딩(MIT)과 BGE reranker v2 m3(Apache-2.0)를 공식 저장소 리비전·파일 해시로 고정했다. 6GB GPU에서 두 모델을 순차 로드하고, E5는 FP32·문서 batch8/query1, BGE는 FP16·batch1로 시작한다. 최신·최고 성능 모델이라는 주장은 하지 않는다.
- 검색 모델과 청크 변경의 효과를 분리하려고 M2의 313문서·3,588청크·dev v1.1 79질문을 그대로 쓴다. BM25의 기존 top10 순위·점수·지표까지 일치해야 비교를 진행한다.
- BM25 50후보와 dense 50후보를 각각 평가하고, RRF 상수 60으로 결합한 상위50을 같은 리랭커 입력으로 사용한다. 각25후보 결합도 별도 진단으로 남겨 후보 예산의 차이를 드러낸다.
- 합성 query 2회 warmup 뒤 단일 dev 순회를 측정한다. 반복 실행의 분산·통계 검정·전력 효율은 측정하지 않는다. 모델 로드·문서 임베딩 준비와 질의 시간을 분리하고 CPU RSS 샘플 및 GPU allocator peak를 기록한다.
- PyTorch 2.10.0(CUDA 12.8 Windows)과 Transformers 4.57.6을 별도 `retrieval` 그룹으로 잠갔다. 검증할 native AutoModel 인터페이스를 명시적으로 선택한 버전이며 최신 버전이라고 소개하지 않는다. 기본 서비스·CI에는 GPU 라이브러리나 모델 다운로드를 강제하지 않는다.
- 모델 파일은 공식 고정 URL의 JSON·safetensors만 받고 원격 Python 실행·pickle 가중치·묵시적 CPU/BM25 fallback을 허용하지 않는다. 다운로드·추론 실패는 별도 실패로 기록한다.
- 오프라인 비교와 서비스 통합을 분리한다. 모델 결과만으로 권한·갱신·삭제·캐시 정확성을 검증했다고 하지 않는다. 이 회귀 검증을 마치기 전에는 M3 전체 완료로 표시하지 않는다.

## M3 첫 실측 뒤의 판단

- 같은 양성 dev 59질문에서 BM25 30, E5 29, RRF 27, RRF+리랭커 36개가 모든 필수 근거를 찾았다. 모델을 추가하면 좋아진다는 가정을 채택하지 않는다. 이전 기준선과 모든 퇴보 사례를 보존한다.
- 혼합+리랭커는 예비 회수 지표에서 순증6개지만, 측정 단계 합계의 중앙값은 약 2.56초다. 이 결과만으로 웹 서비스 기본 경로를 교체하지 않는다. BM25를 유지하고 추가 방식의 명시적 선택·실제 HTTP·권한·갱신 검증을 다음 작업으로 삼는다.
- H50 후보의 모든 근거 회수는 37/59로 리랭커 결과36/59와 가깝다. 현재 후보에 없는 근거를 리랭커 학습만으로 되찾을 수 없다. 후보 회수·문서 잘림·청크 경계를 먼저 구분하고 학습 대상을 선정한다.
- 문서 청크38/3,588과 query-passage803/3,950이 토큰 한도를 넘었다. 입력별 기록을 바탕으로 다음 잘림 진단을 수행하되, 현재 source-span 점수를 모델이 직접 본 근거의 정확도로 바꾸어 표현하지 않는다.

## 사용자 요청에 따른 Java 서비스 전환

- 서비스 백엔드를 Java 21 + Spring Boot로 변경했다. TypeScript 화면과 Python 데이터·학습·평가를 유지한다. [ADR-0002](decisions/0002-java-service.md)가 서비스 언어 선택을 대체하며 M1~M3의 과거 기록은 보존한다.
- 언어 전환과 DB·검색 알고리즘 변경을 분리하기 위해 기존 SQLite 스키마·서버 세션·scrypt·BM25 계약을 유지했다. 별도 `server/`에서 직접 구현했고 Python을 호출하는 서비스 대리 경로는 두지 않았다.
- Spring Boot 3.5.16의 Java 21 호환은 [공식 시스템 요구사항](https://docs.spring.io/spring-boot/3.5/system-requirements.html)에서 확인했다. Maven Central metadata로 실제 배포 버전을 확인한 뒤 POM과 체크섬 고정 wrapper에 버전을 명시했다. 최신 major를 사용했다거나 취약점 검토가 끝났다는 주장은 하지 않는다.
- Java 기본 DB는 새 경로다. 실제 사용자 자료를 자동 이전하지 않고 합성 Python DB의 복사본으로 호환·역방향 읽기·재시작·원본 보존을 검증했다. 원문 오프셋은 Java UTF-16 인덱스가 아닌 기존 codepoint 계약을 유지한다.
- 실제 Java API에서 313문서·3,588청크·dev 79질문의 기존 순위·점수를 대조했다. 이것은 전환 회귀 검증이며 Python GPU 실험의 모델 성능이나 지연을 Java 서비스 수치로 옮기지 않는다.
- PDFBox를 새 Java 파서로 선택했다. PDFBox/pypdf의 파싱 차이는 남아 있고 예전 저장 본문은 자동 변환하지 않는다. 일반 PDF 동등성·OCR·파서 격리는 미검증이다.

## 후보 선택 후속 비교 · 실행 전 결정

- Java 전환 검증 후 첫 실제 heartbeat에서 후보 누락과 입력 잘림을 구분하는 진단을 먼저 구현한다. 서비스는 Java BM25를 유지하고 이번 Python 코드는 오프라인 연구에만 사용한다.
- 저장된 B50·D50에서 `B1,D1,B2,D2,...` 순으로 중복 없이 50개까지 모은다. 각 분기의 같은 순위까지 살피며 중복으로 남는 예산을 채우는 정책 하나만 비교한다. 선택한 후보의 순서는 원래 전체 B50+D50 RRF와 corpus 동점 규칙으로 정하므로 변경 대상은 후보 집합이다.
- 기존 B25+D25 진단의 연장으로 두 검색기에 대칭적인 예산을 부여한다. 특정 실패 질문의 정답 순위를 보호하거나 dev 결과를 보며 후보 수·가중치를 탐색하지 않는다. 개선이 없어도 보존하며 전체 합집합 100개 재랭킹과 다양성 억제를 동시에 추가하지 않는다.
- 기존 E5/BM25 순위를 해시 검증 후 재사용한다. 원래 보고서는 BGE 50개 전체 점수를 저장하지 않았으므로 새 후보는 같은 BGE 설정으로 실제 추론한다. 새 후보 선택·재랭킹 시간과 과거 검색 시간을 합쳐 이번 요청의 실측처럼 표시하지 않는다.
- 별도 tokenizer 진단은 잘림 전 근거 토큰이 잘림 후에도 남는지를 확인한다. 반환된 전체 청크 점수와 구분하며 토큰 보존을 의미 이해·정답으로 해석하지 않는다. 질문과 원문 라벨·test 잠금은 그대로 유지한다.

## 후보 선택 후속 실측 뒤의 판단

- 균등 깊이로 후보를 채운 후 BGE를 적용했을 때 36/59에서 37/59로 1문항을 회복했다. 후보 단계도 37/59에서 38/59로 1문항만 늘었다. 이 작은 dev 차이로 일반적 우위나 서비스 기본값 교체를 결정하지 않는다. 기존 정책과 새 정책을 모두 보존하며 같은 dev에서 정책 탐색을 더 진행하지 않는다.
- 기존 HR top-5의 근거 토큰 보존은 전체 원문 근거 회수와 같은 36/59였다. 803쌍이 잘렸다는 비율 자체를 현재 실패의 원인으로 삼지 않는다. offset 합집합의 문자 포함 27/59도 잘림 전후가 같아 공백 mapping과 모델 잘림을 구분해야 한다.
- 재랭커 이후 남은 실패22개 중 후보부터 부족한21개와 최종 순위 문제1개를 나눈다. 합집합에 없는 근거를 확보하는 임베딩/후보 생성 문제와 청크 경계3개를 우선 연구하며, 근거 없이 리랭커 학습부터 선택하지 않는다. Java 모델 연결의 권한·갱신 검증을 마친 뒤 train 자료만으로 학습 문제를 구체화한다.

## 사용자 승인에 따른 React 화면 전환

- 사용자가 React + TypeScript + Vite 전환 제안을 승인했다. Java 21 + Spring Boot와 Python 연구 코드의 역할은 유지한다. 기존 문서 탐색 디자인과 실제 API 계약을 보존하며 [ADR-0003](decisions/0003-react-frontend.md)에 비교와 회귀 조건을 기록했다.
- Java가 인증·문서·검색 API와 정적 화면 제공을 맡으므로 현재 필요가 없는 SSR·Next.js·별도 API 중계는 추가하지 않는다. 작은 화면 범위에서는 React 자체 상태와 요청 세대로 경합을 제어하고, 라우팅·캐시 요구가 커지면 별도 도입을 검토한다.
- React 도입을 검색 품질·속도 개선으로 주장하지 않는다. 화면의 상태 소유권과 폼·패널 분리가 목적이다. 서버 ACL, 최신 revision과 원문 codepoint 검증은 프레임워크에 맡길 수 없는 계약으로 유지한다.
- Playwright 검사는 새 합성 DB의 실제 Java JAR과 production 번들을 사용한다. 경합 시험은 실제 서버 응답을 보류해 순서를 바꾸고, 오래된 401 합성 오류는 명시적으로 구분한다. 사용자 DB와 동결 M2/M3 입력·실험 결과는 건드리지 않는다.

## 선택적 Java 검색 모델 연결

- [ADR-0004](decisions/0004-model-serving.md): Python은 고정 E5/BGE의 추론만 처리하고 Java가 권한·현재 문서·cosine·RRF·후보 정책·최종 순위·기록을 관리한다. Java ONNX도 가능한 대안이지만 tokenizer/pooling/precision 변환 검증을 이번 서비스 경계 변경과 동시에 추가하지 않았다.
- 기본 검색은 BM25다. 고정 dev에서 1문항 늘어난 정책을 일반적 우위로 해석하지 않고, `balanced_depth_rrf50_v1`은 선택한 `hybrid_rerank`에서만 사용한다. 새로운 dev 정책 탐색이나 최종 test 평가는 수행하지 않는다.
- 추론 전 현재 허용 청크를 읽고 DB 트랜잭션을 끝낸다. 추론 이후 쓰기 트랜잭션에서 동일 세션·membership·전체 가시 청크를 다시 확인한다. 수정·삭제·새 문서·권한 변경 경합은 409로 폐기하며 결과와 이력을 함께 저장하거나 함께 거절한다.
- 단일 모델 검색 진입, 4,096청크, 64개 passage batch, 최대120초 deadline과 4MiB 응답 제한을 둔다. Worker는 인증된 loopback·512KiB body·직렬 추론·4,096개 메모리 LRU다. 모델 오류 시 묵시적 BM25/CPU fallback과 자동 재시도를 하지 않는다.
- Cache는 고정 encoder 설정·revision·본문 hash로 결정한다. 문서/권한 인덱스로 사용하지 않는다. 동결 offline telemetry 누적 배열은 wrapper에서 비워 상주 프로세스의 누적을 막는다. 동결 Python 모듈은 수정하지 않는다.
- UI에는 검색 방식과 실제 결과 방법을 표시하고 이력 재검색도 당시 방법을 사용한다. 외관·가독성·문서 탐색 완성도는 최종 기준에 포함하되 사용자 의도대로 로드맵 순서를 바꾸지는 않는다. 이번에는 실제 모델 선택과 오류 안내에 필요한 화면만 추가했다.

## M4 train 전용 pilot과 조건부 E5 학습

- 후보 누락21개/순위 실패1개의 기존 집계를 바탕으로 첫 학습 가설을 E5 후보 회수로 정했다. BGE 학습·청크 변경을 한 번에 섞지 않는다. [M4-DESIGN](M4-DESIGN.md)에 원 논문·고정 모델 카드·대안과 실행 계약을 기록했다.
- 원래 train의 연결 그룹을 고정 해시로 fit/calibration에 나눴다. 번역·중복 그룹 전체를 함께 이동하며 seed를 탐색하지 않았다. Calibration은 gradient·fit 음성에서 제외한다. 기존 dev/test 라벨·모델 결과는 변경하지 않는다.
- Metadata로 정한16+4문서를 읽어 질문64+14개를 만들었다. 링크 모음에서 독립 사실이 모자라는2개를 미달로 기록했다. 학습 준비 기준을 낮추거나 같은 뜻의 질문으로 채우지 않았다. 보완은 새 선택·초안 버전으로 남긴다.
- 검색 상위 후보를 오답으로 간주하지 않는다. 알려진 양성 계열·인용·정확/유사 청크를 격리하되 남은 후보도 unknown이다. 독립 의미 검토·실제 token 보존·명시적 음성2개/fit 질문 조건이 충족되기 전 학습하지 않는다.
- 독립 AI 의미 검토를 원본 초안과 분리했다. 질문·문서·pack hash 및 배정 역할을 검증한다. AI가78개를 수락한 것은 사용자가 검수했다는 의미가 아니다. 컴파일 당시 pending과 나중에 기록한 AI review를 모두 보존한다.
- 학습은 기존 PyTorch/Transformers 잠금으로 full-weight InfoNCE를 한 번 제한해 시험하는 조건부 안이다. 자동 in-batch 음성은 제외하며, 마지막 checkpoint 하나와 사전학습 모델을 동일 calibration에서 비교한다. 먼저 실제 backward/optimizer 자원 probe가 필요하다. 아직 실행·OOM·성능 결과는 없다. LoRA는 별도 의존성/새 계획이 필요한 비교 대안으로 남겼다.
- 파일 해시는 Git과 같은 UTF-8 LF 바이트로 고정한다. 임시 V1/V2 pack의 바인딩 문제를 해결한 뒤 V3를 썼고 원문과 선택이 동일했음을 확인했다. 생성 재호출의 동일 문장 재현과 저장 초안의 결정적 재컴파일은 구분한다.


## M4 준비 검증에서 발견한 대체 정답과 잘림

- 보충 calibration은 기존 질문과 계열을 보존하고 metadata만으로 정한 새 문서에서2개를 추가했다. AI 작성·독립 AI 검토·사용자 pending 상태는 서로 다르다.
- BM25 상위 후보를 음성으로 바로 쓰지 않고256개를 실제 문맥과 비교했다.4개는 대체 정답,8개는 불확실해서 제외했다. 특히 fit048의 첫4개는 전부 음성이 아니므로 준비를 차단했다. 이 발견을 기존 평가 정답에 소급 추가하지 않는다.
- 실제 tokenizer에서80개 query와 양성 인용은 보존됐으나12질문의 고정 음성은 잘렸다. v1의 전체 입력 보존 조건 실패를 남기고 v2에서 실제 입력 자체를 별도 검토한다. 후보를 짧은 것으로 바꾸거나 원래 질문을 빼서 통과시키지 않는다.
- 준비 자료 통과, 실제 GPU optimizer 자원 probe, 본 학습, 검색 품질 비교를 별개로 기록한다. CI는 저장된 token 증거와 검토 연결을 재생하며 실제 tokenizer 재실행이나 의미 판정 증명이 아니다.

## M4 실제 입력 검토와 수치 실패 비교

- v2는 fit048의 다음 네 후보와 기존에 잘린 12쌍만 추가 검토했다. 원래 63질문의 음성 선택은 보존한다. 실제 모델 입력도 negative라는 독립 AI 판정과 token ID·mask hash를 결합했고, 학습 직전과 각 forward에서 이를 다시 확인한다.
- v1.1 probe는 네 유한 손실값과 backward 이후 비유한 gradient norm으로 optimizer 전에 중단됐다. 이를 OOM이나 학습 실패 후 가중치 갱신으로 기록하지 않는다. 초기 scale만 65536에서 1024로 낮춘 후속 계획을 먼저 동결했다. 원래 실행기·실패 결과·수식·seed·데이터는 유지한다.
- 후속 probe는 동일 네 손실값, 유한 norm 56.11948, 실제 갱신 1회와 peak allocated 2612.10MiB를 확인했다. 이 관측은 scale 민감성 가설에 부합하지만 최초 비유한 연산이나 유일한 원인을 확정하지 않는다. 본 학습은 probe 상태를 버리고 원래 base에서 시작한다.
- 품질 평가는 마지막 저장본 하나만 원 모델과 비교한다. 16개 calibration은 원래 train 내부 계열 분리 자료이며 main dev/test와 다르다. 작은 내부 비교·AI 라벨·한 번의 측정이라는 한계를 유지하고 자동 서비스 채택을 하지 않는다.
- Calibration001의 주석 영어 근거는 회복됐지만 원 모델도 한국어 번역의 대체 근거를1위에 찾았다.002도 주석 표 행 밖의 대체 설명이 있다. 고정 라벨 점수를 사후 변경하지 않고 이러한 주석 불완전성을 정성 분석으로 별도 남긴다. 지표 증가를 새 답변 가능성의 동일한 증가로 해석하지 않는다.

## 한 번의 별도 main-dev 비교

- 기존 M3 전체 실험을 다시 실행하지 않는다. 같은 런타임에서 base E5와 학습 마지막 저장본의 dense 검색만 한 번씩 비교하고, 과거 M3의 저장 순위는 재생·차이 확인용으로 보존한다. 현재 base와 과거 base 중 유리한 비교군을 골라 쓰지 않는다.
- 기존313문서·3588청크·dev79질문과 OR/AND 근거 그룹 조건을 유지한다. Calibration 전용 단일 사실 평가 함수를 dev에 재사용하지 않는다. Main-dev는 최종 test와 다르며, 여기서 나온 점수로 이 저장본을 재튜닝하지 않는다.
- 사전 진행 기준은 양성59질문의 전체 주석 근거 @50이 최소1개 늘고 @5 총수가 감소하지 않는 것이다. 통과해도 별도 운영 검증 후보일 뿐 서비스 모델을 자동 교체하지 않는다. 모든 이득·퇴보와 미주석 대체 근거의 한계를 남긴다.
- 정적 공개 코퍼스 비교는 사용자 세션·ACL·수정·삭제를 검증하지 않는다. 고정 코퍼스 식별·해시 검증과 Java 운영 회귀를 구분하며, 새로운 저장본의 실제 서비스 채택 검사는 후속 단계다. 기존 완료 실험 소스는 바꾸지 않고 새 실행기를 추가한다.

## 고정 학습 저장본의 운영 연결

- 품질 gate 통과 뒤에도 기본 모델을 자동 교체하지 않는다. 별도 실험 실행기와 기본값이 다른 로컬 DB로 terminal을 연결하고, 원래 base 실행기를 보존한다. 모델 manifest hash를 서비스 revision으로 사용해 가중치와 실행 영수증을 함께 식별한다.
- Java는 health뿐 아니라 모든 query/passage 응답의 model/revision을 검사한다. 모델 호출 전 ACL 필터와 호출 후 권한·문서 snapshot 재검증은 유지한다. 원문과 질문은 운영 로그에서 제외한다.
- 검색 방식만 저장하면 모델 교체 후 같은 이력의 의미가 달라진다. 추가 search_model_metadata 테이블에 성공 당시 identity를 저장하고, 미기록 이력은 unknown으로 둔다. UI의 과거 기록 재실행은 현재 모델과 비교하고 불일치 시 명시적 새 검색을 요구한다.
- Terminal은 원래 tokenizer·FP32·eager를 유지한다. 실행 전후 파일 hash를 검사하고 파일 링크·잘못된 영수증·중간 identity 교체를 거부한다. 새 source를 추가해 완료된 연구 실행기의 재생 가능성을 보존한다.
- 운영 검증은 합성 문서·실제 GPU HTTP와 모의 worker 경합 검사를 구분한다. 통과해도 새로운 검색 품질, 사용자 만족도, 고부하 성능이나 학습 모델 채택을 뜻하지 않는다.

실제 terminal 서비스 운영16묶음이 통과해 명시적 실험 실행 경로를 제공한다. 기본 채택은 여전히 별도 판단이다. 기존 dev의 다중 문서 퇴보와 사용자 검수 부재가 남으므로, 다음 단계는 기존 검색 정책 재튜닝 대신 M5 답변·보류·인용 검증을 설계한다. 순차 HTTP8샘플의 지연은 cache가 공유되어 방식 간 성능 비교에 사용하지 않는다.

## 2026-10-13 · 답변 v2 실패와 출력 구조 비교

원문 우선 v2는 한국어 변경 날짜와 로그 금지, beta 예정 표현을 회복했으나 출시 시점 합성과 진행자 답변 JSON/인용 오류를 남겼다. 고정 GBNF로 출력 구조만 제한하는 비교를 한 번 허용한다. 사실·정답·특정 인용을 문법에 넣거나 v2 프롬프트를 다시 맞추지 않는다. 구조 통과는 의미 통과가 아니며 같은 네 사례 전체를 별도 검토한다. 결과에 따른 서비스 연결과 미완성 범위를 분리한다.


## 2026-10-13 · JSON 구조 비교 실패와 검증 범위 분리

구조 제한은 진행자 출력의 JSON만 고쳤고 잘못된 원문 인용·공개 출시 시점은 그대로다. 원본 비교의 네 질문과 프롬프트를 더 조정하지 않는다. 자연어 RAG는 미완성으로 유지한다. 정상 분류를 이용하는 분석·사용자 편집·결정 변경·담당 작업·ACL·revision·삭제를 별도 실제 Java/React 운영 검사로 검증한다. 실패한 전체 서비스 검사를 이 부분 검사로 교체하거나 성공으로 바꾸지 않는다. 새 실행 경로는 experimental로만 제공하고 기본 모델 채택으로 기록하지 않는다.


## 2026-10-13 · 회의 관리 운영 통과와 독립9B 비교
