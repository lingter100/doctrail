# Java 서비스 전환

결정일: 2026-10-12. 사용자가 서비스 개발 언어를 Java로 바꾸도록 요청했다. Java 21 + Spring Boot로 서비스 API를 옮기고, TypeScript 화면과 Python 데이터 준비·모델 실험·오프라인 평가를 유지한다. 이 문서는 전환 결정과 검증 기준이며, 통과 결과는 [STATUS](STATUS.md)와 실제 테스트·실행 보고서에 별도로 기록한다.

## 범위와 보존 대상

| 영역 | 전환 결정 |
|---|---|
| 사용자 서비스 | `server/`의 Java 21 + Spring Boot MVC가 계정·권한·업로드·검색·근거·문서 변경을 담당한다. |
| 데이터 저장 | 기존 SQLite 스키마 v1과 명시적 JDBC를 유지한다. ORM의 자동 스키마 생성·변경을 사용하지 않는다. |
| 웹 화면 | `web/`의 TypeScript와 기존 `/api` 호출 계약을 유지한다. 로컬 API 포트는 8000을 사용한다. |
| 문서 처리 | Java에서 UTF-8 TXT·MD와 PDFBox 기반 텍스트 PDF 처리를 담당한다. |
| 검색 기준선 | 서비스 BM25를 Java로 구현하되, 기존 Python 기준선과 입력·순위·점수를 비교한다. |
| 연구 코드 | `src/doctrail/`, `scripts/`, Python 3.11·uv 잠금 파일을 보존한다. 기존 서비스는 회귀 비교와 롤백의 참조 구현으로 남는다. |
| 동결 실험 | M2 코퍼스·질문·보고서와 M3 모델 비교 결과를 덮어쓰거나 Java 결과로 다시 이름 붙이지 않는다. |
| 실행 데이터 | Java 기본 경로는 `var/doctrail-java.sqlite3`다. 기존 `var/doctrail.sqlite3`를 자동으로 열거나 변환하지 않는다. |

Java 구현을 추가하는 일이 검색 품질 개선, M3 모델의 서비스 연결, 학습, 생성 답변 또는 외부 배포를 뜻하지 않는다. Python 연구 도구를 남기는 것은 사용자 서비스의 Java 전환과 양립한다. 서비스 요청에서 Python 프로세스를 자동 호출하는 임시 연결은 이번 전환에 필요하지 않다.

새 기본 DB는 처음에 비어 있다. 기존 계정·문서가 Java 화면에 나타나는 것은 복사본 이전과 검증을 실제로 수행한 경우에만 보고한다. 로컬 DB·세션·업로드 파일은 Git에 넣지 않는다.

## 구현 경계

작은 단일 서비스로 시작한다. HTTP 입출력과 오류 처리는 컨트롤러·필터가, 세션과 권한 확인은 서비스 계층이, SQL과 트랜잭션은 저장 계층이 맡는다. 문서 추출·청크·BM25는 HTTP나 DB 없이 검증할 수 있는 구성요소로 분리한다. 별도 인증 서버·메시지 브로커·벡터 DB를 이번 전환에 함께 넣지 않는다.

Maven과 각 의존성 버전은 빌드 설정에 고정하고 빌드에 사용한 Java·Maven 버전을 실행 기록에 남긴다. Spring Boot·SQLite JDBC·PDFBox·scrypt 구현 의존성을 사용하되, 버전이 고정됐다는 사실과 취약점 검토 결과는 구분한다. 정확한 버전의 기준은 `server/pom.xml`과 빌드 설정이며 이 문서에 별도 버전 사본을 만들지 않는다.

## 호환해야 하는 계약

### HTTP와 인증

[API-CONTRACT](API-CONTRACT.md)의 경로·JSON 필드·오류 코드·상태 코드를 유지한다. 새 프레임워크 기본 응답으로 비밀번호·원문·질문을 반환하지 않는다. 검증 실패는 `422 {"detail":"invalid_request"}`를 기본으로 사용하고, 알 수 없는 JSON 필드도 거부한다. 문서 파싱 실패는 문서를 `failed` 상태로 저장한 `201` 응답이며, HTTP 요청 자체의 검증 실패와 다르다.

기존 비밀번호는 `saltHex:digestHex`다. UTF-8 비밀번호와 16바이트 salt에 scrypt `N=16384, r=8, p=1`, 출력 64바이트를 적용한다. Java가 만든 새 해시도 이 형식을 유지하며 상수 시간 비교를 사용한다. 다른 라이브러리의 기본 인코딩 문자열로 바꾸면 기존 로그인과 Python 롤백이 깨질 수 있다. 존재하지 않는 계정도 더미 해시 검증 경로를 사용한다.

세션 쿠키 이름은 `doctrail_session`이고, DB에는 원시 토큰 대신 SHA-256 소문자 hex와 사용자 ID·만료 시각을 저장한다. 만료는 UNIX epoch 초 단위이며 기본 유효기간은 7일이다. 로그인 때 기존 토큰을 폐기하고 로그아웃 때 서버 세션을 삭제한다. `HttpOnly`, `SameSite=Strict`, `Path=/`와 `DOCTRAIL_SECURE_COOKIE=1` 설정을 유지한다. 클라이언트가 보낸 사용자 ID는 신원 근거로 쓰지 않는다.

원래 구현의 인증 시도 제한은 프로세스별·접속 주소별 60초당 20회이며 초과 시 `429`와 `Retry-After: 60`을 반환한다. 여러 서버가 공유하는 제한기로 소개하지 않는다.

### DB와 트랜잭션

기존 테이블·열·키·외래키와 `PRAGMA user_version=1`을 유지한다. 연결마다 외래키와 10초 busy timeout을 켜고 WAL을 사용한다. 알 수 없는 스키마 버전은 안전하게 시작을 거부하며 기존 DB를 덮어쓰지 않는다.

| 작업 | 유지할 트랜잭션 경계 |
|---|---|
| 조회·목록·이력 | 권한 확인과 관련 행 조회가 같은 읽기 스냅샷을 사용한다. |
| 업로드·편집·삭제·회원 추가 | `BEGIN IMMEDIATE` 뒤 권한을 다시 확인하고 관련 행 전체를 하나의 트랜잭션으로 변경한다. |
| 재처리 | 현재 저장 소스 확인, 추출, 리비전 증가, 청크 교체를 한 경계에서 수행한다. `ready` 문서 추출이 실패하면 기존 리비전을 보존한다. |
| 검색 | 현재 ACL로 청크 선택, 해당 집합의 BM25 계산, 검색 이력과 결과 저장이 같은 `BEGIN IMMEDIATE` 경계에 있다. |
| 피드백 | 검색 소유자·현재 소속·현재 문서 ACL·반환 이력·리비전을 확인한 뒤 같은 트랜잭션에서 저장한다. |

JDBC 자동 커밋 설정과 수동 `BEGIN`을 혼용해 중첩 트랜잭션을 만들지 않는다. 연결은 요청·작업 단위로 소유하고 여러 요청이 동시에 하나의 연결을 사용하지 않는다. SQLite는 동시 쓰기를 직렬화하며 `BEGIN IMMEDIATE`가 다른 쓰기와 충돌하면 busy가 발생할 수 있다. 이번 전환은 이 저장소 특성을 바꾸지 않는다. [SQLite 트랜잭션 문서](https://www.sqlite.org/lang_transaction.html)

편집 시 본문과 새 청크를 원자적으로 교체하고 리비전을 올린다. 편집한 본문을 현재 UTF-8 TXT 소스로 저장하므로 뒤이은 재처리는 최초 PDF의 오래된 내용을 되살리지 않는다. 삭제는 청크·검색 결과·피드백의 외래키 정리까지 포함한다. 검색 이력의 `result_count`는 현재 접근 가능하고 리비전이 같은 결과만 센다. 예전 검색 결과에 대한 피드백은 변경된 문서이면 `409`, 현재 읽을 수 없는 문서이면 `404`다.

### Unicode와 근거 위치

오프셋 단위는 언어가 바뀌어도 Unicode code point다. Java `String`의 인덱스와 길이는 UTF-16 code unit이므로 그대로 사용하면 이모지 같은 보조 문자가 있는 근거 위치가 어긋난다. 코드포인트 배열이나 명시적인 변환을 사용한다. [Java 21 String 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/String.html)

1. UTF-8 BOM을 허용하되 잘못된 바이트는 대체 문자로 복구하지 않고 `utf8_required`로 거부한다.
2. CRLF·CR을 LF로 바꾸고 NFC 정규화를 적용한 본문을 저장한다.
3. 청크는 최대 1,000코드포인트, 기본 겹침 150코드포인트다. 중간 청크는 시작+500부터 끝 직전까지 마지막 LF 또는 공백 뒤에서 자른다.
4. 청크 생성 뒤 `trim`·`strip`으로 내용을 바꾸지 않는다. 정규화된 본문의 `[start_offset:end_offset]`가 청크 문자열과 정확히 같아야 한다.
5. 제목·질의·본문의 기존 문자 수 제한도 코드포인트 기준으로 검사한다. Python과 Java의 공백 판정 차이를 경계 사례로 검증한다.

파일 상한은 5MiB, 추출 본문은 300,000코드포인트, PDF는 100페이지다. PDF 페이지 번호는 1부터 시작하고 일반 텍스트는 `null`이다. 페이지 본문을 LF 하나로 연결하되 해당 연결 구분자는 앞 페이지 청크의 근거 범위에 넣지 않는다.

PDFBox와 기존 pypdf가 모든 PDF에서 같은 문자 순서·공백을 반환한다고 가정하지 않는다. 기존 DB에 저장된 본문·청크·페이지·오프셋은 시작 과정에서 다시 추출하지 않는다. 사용자가 명시적으로 재처리하면 새 추출 결과를 새 리비전으로 저장한다. 따라서 기존 PDF의 보존 검증과 새 PDF 파서의 정확성 검증을 나눈다. OCR·원본 좌표 하이라이트·파서 프로세스 격리는 이번 전환만으로 추가되지 않는다.

### BM25 기준선

점수 계산에는 **현재 사용자에게 허용된 청크만** 넣는다. 숨겨진 문서를 추가해도 허용된 결과의 점수·순서·개수가 달라지지 않아야 한다. 권한 확인 뒤 전체 코퍼스로 점수를 계산하거나, 전체 검색 후 결과만 거르는 구현은 계약에 맞지 않는다.

| 항목 | 기존 기준선 |
|---|---|
| 토큰 | 소문자화 후 `[a-z0-9]+` 또는 `[가-힣]+`. 한글 2글자 이상은 겹치는 bigram, 한 글자는 그대로 사용 |
| 질의어 | 중복 제거 후 정렬하여 점수 합산 |
| 문서 단위 | 접근 가능한 청크. 평균 길이와 DF도 이 청크 집합에서 계산 |
| 계수 | `k1=1.5`, `b=0.75`; `IDF=log(1+(N-df+0.5)/(df+0.5))` |
| 포함 조건 | 점수 양수만 반환. 매칭되지 않거나 토큰이 없는 질의는 빈 결과 |
| 점수·순서 | 기존 Python `round(score, 8)` 결과를 기준으로 내림차순 정렬 |
| 동점 순서 | 파일명 → 제목 → 시작 오프셋 → 본문 → 청크 ID |

문자열 동점 정렬은 Python의 코드포인트 순서와 맞춰야 한다. Java 기본 UTF-16 비교나 로케일별 비교로 바꾸지 않는다. 점수의 소수 8자리 반올림은 Java 구현이 비슷해 보이는 것만으로 동등하다고 하지 않고 고정 예제 및 동일 코퍼스 출력으로 확인한다. 현재 동결 코퍼스에서 순위·점수가 일치해도 모든 Unicode 입력과 부동소수 경계에 대한 수학적 동등성을 증명한 것은 아니다.

### 요청 경계와 로그

상태를 바꾸는 요청은 기존과 같이 `Sec-Fetch-Site: cross-site` 또는 다른 scheme·host·port의 `Origin`을 거부한다. 쿠키 인증을 사용하므로 프레임워크 교체 과정에서 이 검사를 빠뜨리지 않는다.

HTTP 전체 본문 상한은 파일 상한에 multipart 여유 65,536바이트를 더한 값이다. `Content-Length` 검사와 multipart 제한만으로 끝내지 않고 길이 헤더 없는 스트리밍 본문도 제한한다. `413`은 안전한 코드로 반환하며 실패한 요청에서 문서가 생성되지 않아야 한다.

API 응답의 요청 ID, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, 기존 CSP를 유지한다. 운영 로그는 요청 ID·HTTP 메서드·경로 템플릿·상태·시간으로 제한한다. 검색 질의가 포함된 URL·요청 본문·비밀번호·쿠키·파서 예외 원문을 기록하지 않는다. HTTP 서버의 기본 access log와 PDF 파서 로그도 같은 검증 대상이다.

| 7. 통합 | Python 회귀 검사와 데이터 동결 검증, Java 테스트·패키징, TypeScript 타입 검사·production build, 실제 Java HTTP와 웹 주요 동작 확인 |
| 8. 원격 기록 | 해당 커밋의 필수 CI, PR 목적·검사·한계, 작성자·AI 기여와 결과 보존. 로컬 통과와 원격 CI 통과를 구분 |

`tests/test_api.py`·`tests/test_retrieval.py`·`tests/test_backup.py`는 기존 동작을 읽기 위한 출발점이다. Python 테스트가 통과했다는 사실만으로 Java 서비스가 검증된 것은 아니다. 마찬가지로 Java 단위 테스트만으로 실제 HTTP 요청 경계나 기존 DB 호환이 검증됐다고 하지 않는다.

## 실제 데이터 이전과 되돌리기

1. 진행 중인 모델 실행과 서비스 프로세스를 확인한다. 기존 서비스 쓰기를 중지하고 동시에 두 런타임이 같은 실사용 DB를 변경하지 않게 한다.
2. SQLite의 일관된 백업 방식으로 별도 복사본을 만든다. WAL이 있는 실행 중 DB 파일 하나만 임의 복사하지 않는다. 백업은 로컬에만 보관한다.
3. 먼저 합성 DB로 이전 경로를 검증한 뒤, 필요할 때 기존 데이터의 복사본에서 검증한다. 기존 DB는 덮어쓰지 않는다.
4. 문서·청크·원문 해시·리비전·사용자·소속·이력을 비교한다. 외래키 검사·무결성 검사와 로그인·권한·검색·재시작을 확인한다. 내용 자체를 운영 로그에 출력하지 않는다.
5. 기존 백업·복구 도구가 복구 시 세션을 폐기하는 정책은 유지한다. 무변경 DB 복사본의 세션 호환 검증과 보안 목적의 복구 세션 폐기는 별개다.
6. Java를 사용할 데이터 경로를 명시한 뒤 로컬 진입점을 전환한다. 실제로 전환한 경로와 시각·검사를 상태 기록에 남긴다.
7. 문제가 생기면 Java 쓰기를 멈추고 보존된 원본에서 기존 Python 서비스를 시작한다. Java에서 새로 생긴 변경을 버리고 되돌리는 경우 데이터 손실 범위를 먼저 확인한다. 복사본 검증 없이 Java 변경 DB를 원본에 덮어쓰지 않는다.

기본 경로를 분리하는 것은 보존 장치이며 이전 완료의 증거가 아니다. 실제 사용자 DB를 아직 옮기지 않았다면 Java 전환 결과에 그 상태를 명시한다.

## 수행한 검증

첫 로컬 전환에서 Java 테스트 20개, Python 테스트 129개, 프런트엔드 타입 검사·빌드가 통과했다. [실제 HTTP 보고서](../experiments/results/java-migration-v1.json)는 합성 DB 복사본의 호환·역방향 읽기·재시작·요청 크기·로그 검사를 11개 묶음으로 기록한다. 공개 문서 313개를 Java API로 등록하고 3,588청크·dev 79질문의 top10 ID·점수·오프셋이 동결 Python 기준선과 같음을 확인했다.

보고된 17개 소스·설정 해시는 실행 커밋의 Git blob과 일치한다. 이것은 확인한 입력에서의 호환성이다. 모든 Unicode 문자열·모든 PDF·동시 운영 상황을 증명하지 않으며, 기존 실사용 DB는 옮기지 않았다. 최초 Windows JVM 종료 실패와 수정, 해당 SHA의 원격 CI는 [STATUS](STATUS.md)에 별도로 기록한다.

## 후속 M3 연결

이번 전환의 서비스 검색은 BM25를 유지한다. 다음 M3 작업에서만 검증한 다국어 임베딩·RRF·재순위화를 서비스 후보로 연결한다. Python이 연구와 추론을 담당하게 될 경우 Java는 세션·ACL·현재 리비전·삭제 정책의 소유자이며, 허용된 후보만 추론 입력으로 보낸다. 네트워크 API, 로컬 프로세스 또는 내보낸 모델 중 어떤 연결을 쓸지는 아직 결정하지 않았다.

후속 연결은 요청 지연·권한·개정·삭제·실패 처리·로그·모델 버전 검사를 별도로 통과해야 한다. 이번 언어 전환의 성공을 모델 품질이나 외부 운영 준비의 근거로 사용하지 않는다. 유료 API·임대 GPU·클라우드 및 공개 서비스 배포는 기존 승인 경계를 유지한다.
