# 요약 도구 취득의 한정된 30분 정책

2026-10-30 설계 결정과 구현. [집중 검사·독립 검토 기록](../experiments/results/meetings-summary-acquisition-1800-implementation-v1.json)과 최신 게시·CI 상태는 [STATUS](STATUS.md)에 기록한다. 실제 취득 성공이나 요약 품질의 증거가 아니다.

## 해결하려는 문제

실제 [v4](../experiments/results/meetings-summary-engine-v4-acquisition-v1.json)와 [v5](../experiments/results/meetings-summary-engine-v5-acquisition-v1.json)는 같은 600초 한도에서 LLVM·CMake 준비를 마쳤지만 전체 취득은 끝내지 못했다. Ninja 다운로드 시작은 각각 558.422초와 587.187초였다. 중복 파일 상태 조회를 줄인 뒤에도 전체 완료 시간 개선은 입증되지 않았다.

현재 구현에는 도구 3개마다 다운로드·추출·목록 확인 3단계와 소스 메타데이터·소스 파일·라이선스·최종 기록 4단계, 총 13단계가 있다. 두 실행은 6단계만 완료했다. 작업자 전체 파일 조사는 계획상 28회 중 14회가 기록됐다. 소스별 HTTP 지연과 남은 총시간은 아직 측정하지 못했다. 단계 시간과 조사 시간은 겹치므로 합산하거나 차감해 속도 개선을 주장하지 않는다.

## 선택한 방법

새 고정 정책 `llvm-x64-sampled-50ms-1800s-v1`로 미래 취득 한 번에만 최대 1,800초를 허용한다. 첫 두 도구의 준비에 약 10분이 걸린 실제 기록과 남은 작업을 고려해 추가 20분을 배정한 **유한한 실행 상한**이다. 30분이면 끝난다는 예상이나 보장이 아니다.

기본 방식과 기존 `llvm-x64-sampled-50ms-v1`의 600초는 유지한다. 기존 실패·소비 기록·부분 파일을 수정하거나 재개하지 않는다. 새 정책은 별도 폴더에서 한 번만 실행하며, 실패하면 자동 연장·재시도를 하지 않는다.

| 조건 | 새 정책 |
| --- | --- |
| 취득 전체 | 최대 1,800초, 마지막 5초는 정리용 |
| 다운로드 / 합산 저장 공간 | 기존 512MiB / 4GiB 유지 |
| 프로세스 메모리 / 호스트 여유 | 기존 2GiB / 실행 중 2GiB·시작 시 4GiB 유지 |
| 파일·로그·권한·무결성·프로세스 소유 확인 | 기존 검사와 실패 처리 유지 |
| 빌드 / 문법 검사 | 기존 900초 / 60초 유지 |
| AI 모델·QA 평가 예산 | 변경 없음 |

바깥 실행 관찰의 상한은 기존 사후 기록 여유 300초를 더한 2,100초다. 취득을 2,100초 동안 허용한다는 뜻은 아니다. 각 단계마다 시간을 새로 부여하거나 늦은 종료를 성공으로 바꾸지 않는다.

## 비교한 대안과 검증

전체 파일 조사를 공유·생략하거나 캐시를 도입하면 기록과 독립 관찰 방식을 다시 설계해야 한다. 실패 폴더의 부분 도구를 재사용하려면 별도의 무결성 확인·가져오기 경로가 필요하다. 현재 기록에는 같은 고정 엔진과 검사 프로그램에 사용할 수 있도록 승인된 사전 빌드 산출물도 없다. 이번에는 기존 알고리즘을 유지하는 고정 시간 정책을 선택했다.

임의 시간 입력 옵션이나 일반 설정 체계를 추가하지 않는다. 기존 600초와 새 1,800초의 정확한 종료 시점·경과 시간, 정리 5초, 시간 초기화 방지, 서로 다른 정책의 기록 혼합 거절을 집중 검사한다. 이전 중복 조회 검사의 통과 기록은 재사용한다. 소스 변경·독립 검토·필수 CI 후 새 실행을 진행하며, 성공한 취득물의 별도 검토를 통과해야 빌드로 넘어간다.

설계·코드 검토·자동 실행은 AI 기여다. 사용자 직접 검수와 실제 AI 내용 평가를 대신하지 않는다.
