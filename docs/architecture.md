# DocTrail 아키텍처

설계 기준일: 2026-10-12. M1의 계약과 목표를 설명하는 문서다. 아래에 적힌 검증 조건이 모두 통과했다는 의미는 아니다. 실제 완료 기록은 [STATUS.md](STATUS.md), HTTP 계약은 [API-CONTRACT.md](API-CONTRACT.md)를 따른다.

## 선택한 구조

| 계층 | M1 선택 | 이유 |
|---|---|---|
| 화면 | Vite + TypeScript, 한국어 UI | 업로드·검색·원문 확인 흐름에 집중한다. |
| API | Python 3.11 + FastAPI | 문서 처리와 이후 모델 실험을 같은 언어에서 연결한다. |
| 영속 저장 | SQLite | 단일 로컬 실행에서 계정·권한·문서·청크를 함께 관리한다. |
| 검색 | 자체 BM25, 영어 단어·한국어 bigram을 이용한 토큰화 | 학습 모델 이전의 작은 기준선을 만든다. |
| 인증 | 서버에 저장되는 세션, scrypt 비밀번호 해시 | 클라이언트가 보낸 사용자 ID를 권한 근거로 사용하지 않는다. |
| 패키지 관리 | uv, 잠금 파일, 별도 프런트엔드 잠금 파일 | 설치 환경과 실제 실험 버전을 재현한다. |

개발 시 화면의 `/api` 요청은 로컬 API로 전달한다. 빌드된 화면은 API와 같은 출처에서 제공하는 구성을 목표로 한다. 외부 모델 호출과 클라우드 저장소는 M1 실행 의존성이 아니다.

SQLite는 단일 파일과 로컬 서비스에 적합하지만 동시에 쓰기를 수행하는 작업은 제한된다. 이를 대규모 다중 사용자 구조로 소개하지 않는다. 동시 처리 요구가 실제로 생기면 PostgreSQL 전환을 판단한다. [SQLite의 적합한 사용 사례](https://www.sqlite.org/whentouse.html)

## 문서가 검색 대상이 되는 과정

1. 서버가 세션, 워크스페이스 소속, 업로드 크기와 허용 형식을 확인한다.
2. 원본을 해석해 정규화된 본문을 만든다. 텍스트 PDF는 페이지 번호를 보존한다.
3. 청크마다 원문 오프셋, 순서, 문서 버전을 연결한다.
4. 문서와 청크를 영속 저장하고 성공 또는 안전한 실패 상태를 반환한다.
5. 검색 때 현재 사용자에게 허용된 청크만 읽어 점수를 계산한다.

M1은 최대 5MiB 파일과 추출 텍스트 상한을 둔다. 세부 상한은 실제 구현 설정을 기록한다. 파일 확장자가 PDF여도 스캔 문서를 읽는 OCR이 있다는 뜻은 아니다. 처리가 실패하면 빈 성공 문서로 바꾸지 않고 실패 이유를 보여준다.

## 원문 근거의 식별

검색 결과는 최소한 `document_id`, `revision`, `chunk_id`, `text`, `page`, `start_offset`, `end_offset`을 가진다. 청크의 텍스트는 해당 버전 정규화 본문에서 정확히 잘라낸 문자열이어야 한다.

- PDF 페이지는 1부터 시작하며 일반 텍스트 문서는 `null`이다.
- 오프셋은 Python Unicode code point 기준이다. JavaScript UTF-16 인덱스와 같다고 가정하지 않는다.
- 프런트엔드는 서버가 반환한 청크 문자열을 근거로 사용할 수 있다. 자체 오프셋 변환 없이 `slice()`로 원문을 자르지 않는다.
- 검색 결과를 연 뒤 현재 문서를 다시 조회한다. 버전이 달라졌다면 이전 근거를 최신 문서 근거인 것처럼 표시하지 않고 다시 검색하도록 안내한다.
- PDF에서 추출한 텍스트의 위치는 원본 페이지 번호까지 보장하는 범위로 설명한다. PDF 좌표나 시각적 하이라이트를 구현하지 않았다면 지원한다고 쓰지 않는다.

편집은 추출된 본문을 수정하는 동작이다. 원래 PDF 파일을 재작성했다고 표현하지 않는다. 편집 이후 재처리는 저장된 현재 소스를 기준으로 해야 하며, 최초 PDF의 오래된 내용으로 되돌리지 않아야 한다.

## 권한 불변 조건

`workspace` 문서는 그 워크스페이스의 구성원이, `private` 문서는 소유자가 읽는 M1 규칙을 따른다. 워크스페이스 관리자가 개인 문서를 자동으로 읽을 수 있다고 해석하지 않는다. 편집·삭제는 문서 소유자에게 한정한다.

권한 검사는 다음 위치 모두에 필요하다.

| 경로 | 검증 조건 |
|---|---|
| 목록·검색 | 워크스페이스 소속과 문서 공개 범위를 후보 생성 전에 검사한다. |
| BM25 점수 | 허용된 청크 집합으로 문서 빈도와 평균 길이를 계산한다. 숨긴 문서가 결과 수나 점수에 섞이지 않게 한다. |
| 문서 직접 조회 | 문서 ID를 알고 있어도 현재 권한을 다시 검사한다. |
| 수정·삭제·재처리 | 서버에서 소유권을 검사한다. |
| 이력·피드백 | 이력 소유자, 당시 반환한 문서, 현재 접근 가능 여부를 검사한다. |
| 향후 임베딩·재순위화·생성 | 권한이 없는 텍스트는 후보·모델 입력·출처·캐시 어디에도 보내지 않는다. |

문서가 비공개로 바뀌면 새 검색뿐 아니라 이미 얻은 링크의 직접 접근도 막아야 한다. 이미 사용자가 합법적으로 읽고 내려받은 내용을 회수할 수 있다고 주장하지 않는다. 오류 응답에서 타인의 문서 제목이나 본문을 노출하지 않는지도 테스트한다.

## 수정·삭제와 일관성

수정은 새 본문과 청크를 검증한 뒤 하나의 트랜잭션으로 교체한다. 성공하면 버전을 올리고 이전 청크를 제거한다. 실패하면 이전 버전을 계속 사용하거나 명시적인 실패 상태를 유지하되 본문과 청크가 서로 다른 버전이 되면 안 된다.

재처리는 같은 소스로 반복해도 청크가 누적되지 않아야 한다. 삭제가 성공한 뒤 문서 목록·검색·직접 조회에서 해당 문서를 읽을 수 없어야 한다. 검색·변경 동시 실행은 요청이 사용한 버전이 일관된지 확인한다. 향후 비동기 인덱스를 도입하면 데이터베이스 트랜잭션과 별도로 삭제·권한 변경 전달과 지연을 측정해야 한다.

현재 단일 저장소의 변경 반영 테스트가 통과했다고 해서 외부 SaaS 커넥터의 실시간 동기화를 구현한 것은 아니다.

## BM25 기준선의 한계

영어 단어와 한국어 연속 글자의 bigram은 형태소 분석·번역·의미 이해를 대신하지 않는다. 식별자·오류 코드가 들어간 질문에는 유리할 수 있으나 동의어, 조사 변화, 띄어쓰기, 한국어 질문과 영어 문서 조합에서 실패할 수 있다. 한글 한 글자나 구두점만 있는 질의도 명시적으로 다룬다.

자체 구현을 사용할 때 토큰화 규칙, Unicode 정규화, 소문자화, 숫자·코드 처리, `k1`, `b`, IDF 식, 중복 질의어 처리, 동점 정렬을 실험 설정으로 남긴다. 작은 계산 가능한 예제로 수식과 순서를 검증한 뒤 공개 라이브러리와 같은 토큰 입력에서 비교하는 점검도 계획한다. 자체 구현이라는 사실이 더 높은 검색 품질을 뜻하지 않는다.

청크 순위를 바로 문서 단위 정확도로 사용하지 않는다. 문서 중복 제거 후 지표와 청크 근거 지표를 따로 계산한다. 결과가 없다는 사실과 질문에 답할 수 없다는 판단도 구분한다.

## M2 이후의 확장 지점

| 구성 | 예정한 인터페이스·계약 | 채택 조건 |
|---|---|---|
| 청크 생성 | 동일 원문에서 버전별 청크 매핑 생성 | 제목·문단·토큰 경계 실험으로 근거 회수율 개선 |
| 밀집 검색 | 질의와 접근 가능한 청크의 벡터 유사도 | 모델 메타데이터와 임베딩 버전 보존, 지표·자원 실측 |
| 혼합 검색 | BM25와 밀집 검색의 순위를 RRF 등으로 결합 | 개발셋으로 후보 수·결합 설정을 고른 뒤 최종셋에 고정 |
| 재순위화 | 권한을 통과한 후보 `(질의, 본문)` 점수화 | 품질 개선과 p95·메모리 비용이 함께 보고됨 |
| 답변 생성 | 승인된 근거 집합에서만 답변·근거 또는 보류 상태 반환 | 인용 정확도·근거 없는 답변 비율·유보율 검증 |
| 영속 인덱스 | PostgreSQL + pgvector 후보 | 로컬 벡터 비교를 먼저 만들고 운영상 이득이 있을 때 이전 |

처음 1,000개 문서 수준의 비교에는 정확한 벡터 전수 비교도 유효한 후보다. 곧바로 근사 최근접 인덱스를 도입해 측정 변수를 늘리지 않는다. pgvector는 기본 정확 검색과 근사 검색을 구분하며 근사 인덱스의 필터링은 회수율에 영향을 줄 수 있다. 전환 시 권한 필터와 후보 고갈을 별도로 검증한다. [pgvector 공식 문서](https://github.com/pgvector/pgvector)

## 저장할 데이터의 책임

M1의 계정·세션·소속·문서·청크·검색 이력·피드백과, 실험용 코퍼스·정답셋·실행 결과는 목적이 다르다. 사용자가 올린 문서나 검색어를 자동으로 공개 평가셋 또는 학습 데이터로 넣지 않는다.

후속 실험 저장 형식에는 `source_id`, `canonical_url`, `source_revision`, `sha256`, `license`, `language`, `document_family_id`, `parser_version`, `chunker_version`를 넣는다. 이 필드가 모두 현재 서비스 스키마에 존재한다는 의미는 아니다. 데이터 계약은 [data-evaluation.md](data-evaluation.md)에 있다.

## 운영과 공개 경계

로컬 데이터베이스, 업로드 파일, 모델 가중치, 수집 코퍼스와 개인 환경 경로는 Git에 넣지 않는다. 요청 추적은 ID·소요시간·오류 코드 중심으로 남기고 원문과 질문을 운영 로그에 그대로 기록하지 않는다. 서비스에 필요한 개인 검색 이력과 공개 가능한 운영 로그는 분리한다.

계정 기능이 있다는 이유만으로 인터넷 공개 준비가 된 것은 아니다. 공개 서비스 전에는 TLS와 쿠키 설정, 교차 출처 요청 방어, 업로드 자원 격리, 속도 제한, 복구·삭제 정책과 취약점 검토가 필요하다. 구현한 보호와 미구현 항목을 구분한 뒤 사용자의 배포 승인을 받는다.

개발 보조 AI의 실제 도구 수락 설정은 기여 기록에 남긴다. 설계 에이전트에 지정한 모델, 부모 채팅의 확인되지 않은 모델, 서비스의 추론 모델을 하나로 표현하지 않는다. M1 서비스에는 생성 모델이 없다.
