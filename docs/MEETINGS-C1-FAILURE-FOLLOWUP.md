# C1 실패 이후 근거 단위 설계 제안

작성일: 2026-10-14. 상태: **제안만 작성. 구현·모델 실행·새 품질 자료 작성·채택 없음**.

권고는 기존 무료 로컬 모델과 한 번의 답변 생성을 유지하면서, 물리적 줄 대신 **문단과 문장 연속성을 보존하는 원문 구간**을 인용 ID의 단위로 쓰는 후보 하나를 검토하는 것이다. 문단 내부의 조건과 결론을 여러 ID로 나누는 부담을 줄일 수 있는지가 가설이다. 아직 의미 품질이나 자원 적합성이 증명된 방식은 아니다. 아래 `C2-P0`는 제안 식별자이며 실행 등록이나 채택 기록이 아니다.

## 판단에 사용한 증거와 범위

C1의 사후 부분 검토는 계획 8문항 중 시도한 4문항의 D0/C1 응답 8개를 대상으로 했다. 두 역할 모두 완전 적합은 0/4였다. 필수 답변 항목이 글에 포함된 경우는 각각 3/4였지만, 이는 주장별 선택 인용의 지지가 충족됐다는 뜻이 아니다. 전달된 인용은 D0 31/31, C1 27/27가 정확했고, C1에는 인용이나 정상 답변을 반환하지 못한 오류 1개가 있었다. 이 수치를 계획 전체의 성능이나 서비스 정확도로 확대하지 않는다.

잠긴 판정의 추상적 실패 범주는 다음과 같다. 범주별 수는 서로 중복된다.

| 실패 범주 | D0 | C1 | 구조 검토에서 다룰 부분 |
|---|---:|---:|---|
| 선택 인용에서 필수 조건·문장 후반·결론이 빠짐 | 3 | 3 | 문장이 물리적 줄마다 다른 ID로 갈라지는 문제 |
| 추가 열거·비교 사실이 선택 근거 밖에 있음 | 2 | 1 | 큰 단위로도 자동 해결되지 않는 사실 선택 문제 |
| 원문의 한정 조건을 넓게 표현함 | 1 | 1 | 생성 문장의 의미 보존 문제 |
| 전체 질문에 보류가 필요한데 부분 답변을 반환함 | 1 | 0 | 답변 가능성 계약 문제 |
| 정상 보류 대신 오류를 반환함 | 0 | 1 | 실행 실패이며 성공 보류로 계산할 수 없음 |

첫 세 문항의 D0/C1 응답이 같았고 완전 정답의 개선은 관측되지 않았다. 이것만으로 모든 자기검토 방식이 무효라고 일반화하지는 않는다. 다만 **같은 자기검토를 더 붙이고 질문 수를 늘릴 근거는 이번 부분 실행에서 얻지 못했다.**

부모가 실행 결과에서 전달한 자원 관측은 생성 속도 약 5 tokens/s, 첫 세 사례의 D0+V0 누적 시간 약 69/79/119초, 네 번째 사례의 형식 누락에 따른 중단이다. 이 설계 역할은 C1 원본 보고서를 다시 열어 수치를 재검증하지 않았다. 이 시간은 전달받은 로컬 모델 경로의 관측이며 Java 서비스나 브라우저의 응답 시간 측정이 아니다.

판정 SHA256은 `6526bce4c417744a89a7a51bf7e9e04e24e787324bc8aa264d88ae15a265a12e`, 대응표 연결 후 요약 SHA256은 `50fd6f5ef79477f27c87c65b2a5802a4f82e73a449f456c18016985a1bada0c1`이다. 이 설계를 위해 원본 응답, 네 문항의 질문·oracle, 잠긴 판정 파일을 다시 읽지 않았다. 기존 대화에 남은 추상 집계와 [C0 인용 구조 제안](MEETINGS-CITATION-ARCHITECTURE-PROPOSAL.md)의 구조 설명을 사용했다.

## 대안 비교와 단일 권고

| 대안 | 기대 효과 | 남는 문제 | 이번 권고 |
|---|---|---|---|
| 문단을 중심으로 문장 연속성을 보존한 인용 ID | 줄바꿈 때문에 조건·서술부가 분리되는 빈도를 줄일 수 있음 | 문단 간 의존, 잘못된 단락 선택, 추가 주장·보류 실패는 남음 | **C2-P0 하나로 검토** |
| 검색된 청크 전체를 인용 ID로 사용 | 조각을 적게 선택해도 넓은 문맥을 인용할 수 있음 | 청크 경계 자체의 잘림은 남고, 관련 없는 문장까지 인용해 근거가 충분해 보일 수 있음 | 사용하지 않음 |
| 더 큰 무료 모델로 변경 | 다른 생성 능력을 시험할 수 있음 | 현재 메모리·속도·120초 적합성이 확인되지 않음. 모델과 구조 효과가 섞임 | 새 모델 다운로드·실행 없음 |
| 추가 자기검토·자동 수정 단계 | 오류를 찾아 고칠 가능성 | 이번 부분 실행에 완전 정답 개선 증거가 없고 호출 수·지연·실패 지점이 늘어남 | 추가하지 않음 |

문장 경계만으로 잘게 나누는 방식도 첫 후보에는 넣지 않는다. 약어, 코드, 목록, 인용문, 한국어 문장 부호를 정규식으로 판별하면 새로운 잘림이 생길 수 있다. 한 문단의 여러 문장을 함께 보존하는 쪽으로 후보를 좁히고, 문장 단위 분할과 문단 단위 분할을 동시에 탐색하지 않는다.

## C2-P0의 변경 범위

기존 로컬 가중치·양자화·runtime·GPU 적재·비추론 설정을 그대로 식별해 사용한다. 새 모델, 새 예시, 검색 정책 변경, 샘플링 탐색, 자기검토 호출을 추가하지 않는다. 완료된 C0/C1 소스와 계획에 묶인 파일은 편집하지 않고 새 진입점과 새 계획을 둔다.

Java가 인증·ACL·현재 리비전·검색 결과를 결정하고 마지막 인용 검증을 수행하는 경계를 유지한다. Python 어댑터의 요청별 근거 목록 생성만 바꾼다. 문서 DB 접근이나 핵심 검색을 Python으로 옮기지 않는다. 모델은 주장과 ID를 반환하고 어댑터가 원문·위치를 복사하는 기존 계약을 유지한다.

새 단위는 **Java가 권한·리비전을 검사해 전달한 단일 context의 범위 안**에서만 만든다. 같은 문서의 이웃 청크라도 좌표를 하나로 합치지 않으며, context 밖 원문을 다시 조회해 인용을 확장하지 않는다. 여러 청크가 필요하면 각 청크에 속한 별도 인용을 반환하고 Java의 기존 최종 범위·원문·접근권한·리비전 검사를 모두 통과해야 한다.

### 생성 전에 고정할 근거 단위

1. 입력 `contexts`의 순서와 원문 문자를 모두 보존한다. Unicode code point 위치, Markdown, 곡선 따옴표, 공백, 줄바꿈을 정규화하지 않는다. 질문이나 정답, 모델 출력으로 구간 경계를 바꾸지 않는다.
2. 일반 본문은 빈 줄로 구분한 문단을 기본 단위로 삼는다. **문단 내부의 물리적 줄바꿈은 ID 경계로 쓰지 않는다.** 마침표나 480 code points에 도달했다는 이유로 문장을 나누지 않는다.
3. 연속 목록과 그 들여쓴 이어지는 줄, 코드 fence, 표는 각각 한 구조 블록으로 보존한다. 바로 앞 문단이 콜론으로 끝나며 다음 목록·표·코드를 소개하는 경우에는 그 문단과 블록 사이의 원문까지 하나의 연속 구간으로 묶는다. 떨어진 위치의 문자열을 이어 붙인 quote는 만들지 않는다.
4. 제목·빈 구간도 원문 위치 보존에 포함한다. 공백만 있는 단위는 인용할 수 없다. 제목만으로 근거가 충분한지는 의미 검토 대상이며, 제목 ID가 있다는 이유로 본문의 조건이나 사건 상태를 추론하지 않는다.
5. 단위 최대 길이는 우선 **1,024 code points**로 제안한다. 큰 문단·목록·코드 블록을 맞추려고 다시 줄 또는 문자 수로 자르지 않는다. 초과하면 모델 호출 전 명시적 입력 오류로 멈춘다. 청크 전체 인용으로 조용히 전환하지 않는다.
6. 여러 구간이 필요한 주장에는 각각의 ID를 선택하게 한다. 한 청크 안의 단위들을 순서대로 복원하면 원문과 정확히 같아야 하며, 단위 간 문자 중복·누락을 금지한다. 기존 검색 청크 사이의 중복은 보존한다.

구조 블록의 세부 인식 규칙과 경계 우선순위는 구현 전 명세와 단위 검사로 확정해야 한다. 이 문서가 기존 parser가 그 규칙을 이미 만족한다고 보증하는 것은 아니다. 1,024도 실측 최적값이 아니며, 품질 응답을 본 뒤 길이를 바꾸는 탐색을 허용하지 않는다.

입력 청크 자체가 문장이나 단락 중간에서 시작·종료하는 문제는 이 변경으로 복원되지 않는다. 보이지 않는 앞뒤 문장을 가져오거나 완성하지 않는다. 청크 경계에서 완결 여부가 확인되지 않는 단위는 그 한계를 명시하고, 내부 문단처럼 완결이 확인됐다고 표시하지 않는다. 중간에서 잘린 단위를 이용해도 선택한 인용에 주장 전체가 없으면 의미 실패다. 경계가 불명확한 요청을 제외해 성공률을 높여서는 안 되며, 호출 전 거부도 평가의 시도 결과에 남겨야 한다.

### 원문 확대가 근거 부족을 가리지 않게 할 조건

- 단위는 **응답 생성 전에** 고정한다. 실패한 주장에 맞춰 이웃 문단을 사후 추가하거나 인용 ID를 바꾸지 않는다.
- 모든 추가 사실·원인·대상·시점·조건을 해당 주장에 연결된 인용만으로 확인한다. 같은 답변의 다른 주장이나 다른 컨텍스트에 근거가 있다는 이유로 통과시키지 않는다.
- 선택한 각 단위가 그 주장의 사실 또는 필요한 한정 조건을 실제로 지지하는지 검토한다. 관련 없는 단위를 추가한 것은 근거 보강으로 계산하지 않는다.
- 검토자는 넓은 인용 안에서 필수 근거를 이루는 최소 원문 부분을 짚고, 주장에 대응하지 않는 나머지가 많다는 사실을 별도로 기록한다. 인용 길이나 문서 개수를 의미 지지의 대리 지표로 쓰지 않는다.
- 단락이 여러 주제·상반된 상태를 포함하면 유리한 문장만 골라 해석하지 않는다. 취소·조건·예외까지 함께 반영해야 한다. 단락 보존은 논리적 완결성 보증이 아니다.
- 전달된 전체 source 문자 수, 단위 길이, 주장별 인용 문자 수, 답변 전체의 고유·중복 인용 문자 수, 불필요 인용 여부를 함께 보고한다. 인용 범위 비율의 분모와 집계 방식을 양쪽에 동일하게 고정하고, 넓어진 인용의 정확한 문자열 매칭만 좋아졌다는 결과로 채택하지 않는다. 이 길이 계측 때문에 원문이나 질문을 운영 로그에 남기지 않는다.
- UI나 후처리에서 답변을 고치거나 인용을 줄여 성공 결과를 만들지 않는다. 원문 발췌는 자연어 답변 성공과 구분한다.

## 120초 가정과 자원 게이트

추가 생성 단계는 없다. 요청당 모델 호출 1회, 재시도 0, 동시 생성 1개를 제안한다. 기존 768 출력 tokens는 전달받은 약 5 tokens/s만 적용해도 생성에 약 154초가 필요할 수 있어, 입력 처리·검증 시간을 포함한 120초 가정과 맞지 않는다. 이는 속도가 고정된다는 예측이 아니라 상한 설정의 문제를 보여주는 계산이다.

첫 구조 후보와 새 비교 기준에는 다음 동일한 예산을 적용하는 것을 제안한다.

| 항목 | 제안 상한 | 해석 |
|---|---:|---|
| 전달 청크 | 10개 | 원문 순서·내용을 조용히 축소하지 않음 |
| 근거 목록 | 160개 | 공백 단위도 보존 검사와 개수에 포함 |
| 입력 prompt | 4,096 tokens | 초과 시 호출 전 오류 |
| 출력 | 384 tokens | 6개 이하 주장, 주장당 1~4 ID 유지. 잘림은 실패 |
| 어댑터와 단일 생성 | 90초 | 취소·정리까지 제한 안에 들어야 함 |
| 서비스 전체 요청 | 120초 | 나머지 30초는 검색·권한·전달·검증 등을 위한 설계 여유이며 실측 보장이 아님 |

384 tokens도 약 5 tokens/s에서 생성만 약 77초다. 나머지 시간에 입력 처리를 마칠 수 있는지는 별도 실측이 필요하다. 384 tokens 때문에 필수 답변을 누락하면 완전성 실패이며, 질문을 줄이거나 oracle를 완화해 맞추지 않는다. timeout, OOM, 잘림, 형식 누락은 모두 실패로 남긴다. 자원 게이트를 통과하지 못하면 품질 자료를 새로 만들거나 길이·시간을 뒤늦게 확대하지 않고 이 후보를 멈춘다.

90초 어댑터 검사와 작은 중립 실행은 Java 120초 운영 검증을 대신하지 않는다. 최종 후보가 품질을 통과해도 실제 Java 경로의 요청 취소·모델 작업 종료·안전한 오류·이후 요청 복구를 별도로 확인해야 한다. 큰 모델의 다운로드나 native 실행은 이 문서 작성 범위에 없다.

## 새 품질 자료보다 먼저 할 검증

현재 문서에서는 아래 작업을 실행하지 않는다. 후속 구현자가 새 계획을 등록한 뒤 순서대로 수행할 조건이다.

1. **모델 없는 단위 검사:** 무작위 문자열과 새 인위적 구조 예제로 문단 내 줄바꿈, 문장 중간 줄바꿈, 조건/결론, 들여쓰기 목록, 소개 문단, 표, 코드 fence, Unicode, 반복 구절, 청크 경계 잘림을 검사한다. 옛 질문·응답·oracle 문구를 예제로 복사하지 않는다. 정확한 원문 복원, 위치, 중복·누락, 공백 ID, 최대 길이와 명시적 실패를 확인한다.
2. **모델 없는 계약·토큰 검사:** 동일 `contexts` 보존, 실제 tokenizer의 입력 길이, 기존 응답 복원과 Java 인용 경계 계약, 공개 오류에 원문·질문이 실리지 않는지 확인한다. 기존 실패 실험의 바인딩 파일 hash가 그대로인지 검사한다.
3. **중립 자원 검사 최대 2호출:** 새 인위적 입력으로 정상 계약 1회와 상한에 가까운 입력·출력 부하 1회를 사전 등록한다. 질문의 답을 고치는 실험이나 품질 성공 수에 포함하지 않는다. 실제 입력·출력 tokens, 전처리·입력 처리·생성·전체 시간, 종료 이유와 메모리를 기록한다.
4. 부하 검사가 실제로 긴 출력을 만들지 않았다면 최대 출력 지연을 검증했다고 하지 않는다. 관측 범위를 보고하고, 90초 안에서 완료·취소를 입증할 계획 조건이 충족되지 않으면 다음 단계로 가지 않는다. 중립 결과를 보고 의미 prompt를 튜닝하거나 중립 호출을 무제한 반복하지 않는다.
5. 이 검사를 통과한 **하나의 구조·정책·자원 설정**을 commit과 파일 hash로 동결한다. 그 다음에만 별도 자료 작성자가 신규 품질 자료를 만든다.

단위 검사에서 발견한 모델 없는 소프트웨어 결함은 품질 자료를 만들기 전에 고치고 새 hash로 등록할 수 있다. 모델 출력의 사실 선택을 보고 정책을 바꾸는 작업은 그 예외에 포함하지 않는다.

## 공정한 후속 평가 제안

아래 규모는 앞으로 등록할 상한 제안이며, 기존 실패 계획이나 oracle를 수정하는 내용이 아니다. 기존 C0 known4, prepared12, C1의 시도·미시도 자료, M5-B validation, 최종 test는 사용하지 않는다. 새 후보의 후보 수는 1개다.

- 새 calibration 8문항과 문서 계열이 분리된 신규 validation 12문항을 제안한다. 자료 수를 채우려고 기존 질문을 바꿔 쓰거나 같은 원문을 재활용하지 않는다. 두 분할의 언어·답변 가능/보류·복수 자료·시간/조건 구성과 필수 사실, 허용 대체 인용을 **첫 품질 호출 전에** 등록한다. 자료는 실제 작성 후 정확한 구성을 검증하며, 현재 존재한다고 주장하지 않는다.
- calibration에서 같은 입력을 고정된 직접 생성 기준과 C2-P0에 각각 한 번씩 전달한다. 직접 생성 기준은 기존 줄 단위 목록을 쓰되, 새 비교 실행기에서 위의 동일한 출력·시간 예산을 적용한다. 과거 D0 결과를 새 실행의 대조군으로 재사용하거나 동결 소스를 덮어쓰지 않는다.
- 모델·가중치·검색 결과·순서·질문·답변 schema·생성 설정·자원 상한은 양쪽이 같다. 차이는 생성 전 근거 단위와 그 표시를 설명하는 최소 계약 문구뿐이다. 비교 순서·캐시 조건·seed를 미리 정하고 기록한다. 자기검토 유무와 근거 단위 효과를 섞지 않는다.
- calibration 품질 호출은 최대 16회다. C2-P0가 8/8 완전 적합이고, 기준 대비 완전 정답 개선 1개 이상·퇴보 0이며 자원 게이트를 만족할 때만 validation으로 진행하는 것을 제안한다. 양쪽 8/8이면 개선이 입증됐다고 하지 않고 구조 변경 채택을 보류한다. 부분 실행이나 항목 제외로 이 선택 규칙을 통과시키지 않는다.
- validation은 격리된 custodian이 관리하고, 선택된 C2-P0만 12문항에 각 1회 실행한다. 12/12 완전 적합을 요구하며 오류·잘못된 보류·근거 없는 추가 사실은 0이어야 한다. 중립 2회를 포함한 전체 제안 상한은 **30 모델 호출**, 재시도 0이다. 이는 지금 실행하라는 명령이 아니다.
- 새 의미 검토자는 구현·정책 설계·자료 작성에 참여하지 않은 역할을 사용한다. 익명화한 질문·전체 컨텍스트·고정 oracle·실제 선택 인용·응답을 함께 제공하고, 판정과 SHA를 잠근 뒤 역할 대응표를 연다. 동일 출력이나 오류 모양이 역할을 드러낼 수 있다는 한계도 기록한다.
- 구조·정확한 인용·모든 주장 지지·모든 필수 질문 항목·언어·시간·대상·조건·올바른 답변/보류를 모두 충족해야 완전 적합이다. 기본 oracle의 허용 대체 인용을 존중하되, 선택 인용에 없는 근거를 전체 컨텍스트에서 빌려오지 않는다. `status:error`는 성공 보류가 아니다.
- parser/자원 오류 때문에 전체 실행을 멈추면 완료된 접두 부분만 사후 분석하고 선택 게이트는 실패로 남긴다. 남은 문항을 새 정책의 자료로 이어 붙이지 않는다. 실패한 품질 응답을 보고 oracle, 인용 범위, 출력 길이, 질문 수를 조정하지 않는다.

작은 신규 자료에서 전부 통과해도 넓은 운영 정확도나 인간 검수를 입증하지 않는다. Java·React 통합과 새 사용자 자료의 권한·리비전·오류 회귀는 별도 단계이며, 현재 Phase 1과 PR14는 미완료 상태다.

## 보존과 역할 변경

- C0/C1의 계획, bound source, 입력, raw 결과, 오류, 익명 검토 pack, 대응표, 잠긴 판정·요약을 그대로 보존한다. 현재 문서는 그 실패를 성공으로 바꾸지 않는다.
- C1은 원인 증거와 실패를 보고한 상태로 종료한다. 단일 생성 후보의 선행 조건으로 자기검토 응답 형식을 고치는 별도 패치를 만들 필요는 없다. 기존 실패 소스의 형식 패치와 재실행을 이번 제안에 포함하지 않는다.
- 이번 작업은 이 설계 문서 작성 하나다. 코드 변경 0, 새 질문 0, 모델 호출 0, native 실행 0, 모델 다운로드 0, 유료 사용 0, 인간 검수 0이다. 무료 로컬 경계와 별도의 공개 배포 승인 경계를 유지한다.
- 작성자는 앞서 C0와 C1 부분 calibration의 독립 의미 검토를 수행했다. C1의 네 질문·oracle·응답을 이미 보았다는 노출은 사라지지 않는다. **지금부터는 구조 설계 참여자이므로 후속 후보의 독립 의미 검토자로 사용하지 않는다.**
- 실제로 도구가 수락한 이 에이전트의 설정은 부모가 확인한 `gpt-6-astra / xhigh`다. 부모 채팅 모델이나 서비스 추론 모델을 변경했다는 뜻이 아니다.
- AI가 만든 자료·oracle와 AI 평가의 공통 편향이 남는다. 역할 분리나 익명화는 인간 검수의 대체 기록이 아니며, 후속 평가에서 작성자·설계자·검토자·custodian의 참여 이력을 함께 공개해야 한다.
