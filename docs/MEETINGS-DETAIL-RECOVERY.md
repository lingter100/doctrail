# 회의 상세 접근 거부와 결정 연결 충돌 복구

2026-10-16. 실제 Java 21/Spring Boot와 패키지된 React 화면의 로컬 검증이다. 답변 모델 품질 평가와 사용자 검수는 별개다.

회의를 공유에서 비공개로 바꾸면 독자의 상세 조회는 실제404를 반환한다. 수정 전에는 이 응답을 받아도 이전 작업 목록에 회의 제목·담당자·건수가 남았다. 이제 상세 또는 연결 조회에서 접근 거부가 확인되면 해당 화면의 상세·목록·작업·원문 패널과 이전 요청의 소유권을 무효화한다. 목록을 다시 읽기 전에는 확정된 빈 목록으로 표시하지 않으며, 사용자가 명시적으로 재조회할 수 있다. 작업공간 변경 후 도착한 이전 응답도 적용하지 않는다.

다른 문제는 결정 연결의 버전 충돌이었다. 연결 대상 회의의 담당자만 수정해도 분석 버전이 바뀐다. 기존 복구는 현재 회의만 새로 읽었으므로 연결 POST409 → 새로고침 → 다시 POST409가 반복됐다. 이제 현재 회의와 연결 대상들을 함께 확인하고, 양쪽 결정을 다시 선택해야 저장할 수 있다. 입력한 근거 구절은 유지한다. 자동 재전송은 하지 않으며 서버의 revision/version 조건도 그대로 유지한다.

현재 회의 접근 거부와 다른 작업공간의 대상 목록 접근 거부를 구분한다. 전자는 이전 정보 전체를 숨기지만 후자는 대상 후보만 숨기고 현재 회의와 근거 입력을 남긴다. 대상 목록503 같은 일시적 실패에서도 입력과 재확인 상태를 유지한다. 복구 중에는 제출을 막는다.

## 실제 재현과 검증 범위

- `web-e2e-vxznPS`: 실제 reader404 후 작업 정보가 남는 실패를 재현했다. 같은 실행의 연결 선택자 timeout은 테스트 문제로 따로 기록했다.
- `web-e2e-Wf1FpE`: 실제 대상 담당자 변경 후 POST409가 새로고침 뒤에도 반복되는 실패를 재현했다.
- `web-e2e-jjlPhM`: 수정 후8통과/1실패였다. 작업공간 변경 시 작업 화면이 유지된다는 잘못된 테스트 가정을 수정했고 표적1개가 통과했다.
- `web-e2e-jqnInv`: 부모 코드 검토의 후속으로 대상 목록403·현재 회의GET200 상황을 재현했다. 처음 수정에서는 입력 폼까지 사라졌다. 대상403은 명시적으로 주입한 합성 오류이며, 이 실패를 보존하고 오류 처리를 분리했다.
- 최종 `web-e2e-batch-ekRnes`는 새10 + 충돌5 + 연결 삭제4 + 기존 회의3 = **22통과/0실패/0skip/0flaky**다. 모든 실행은 패키지된 UI를 사용했고 서버가 종료됐다.
- 앞선 확장 검사 `web-e2e-batch-lZ29gZ`의 **42통과**는 마지막 대상 오류 분리 이전 결과다. 최종22와 합산하거나 최종 코드42통과로 표현하지 않는다.
- 최종 TypeScript·production build·Java `package -DskipTests`·공백 검사가 통과했다. 패키징은 전체 Java 단위 검사 실행을 의미하지 않는다.

실제 Java 인증·ACL·버전 충돌·저장 응답을 사용했다. 분석 전송과 대상403/503은 명시적 합성 fixture이며 실제 LLM 호출0·사용자 검수0이다. 현재 페이지 메모리만 보존하며 영구 초안 저장은 추가하지 않았다. 원본 로그·실패 trace·화면·코드 snapshot은 `.local/meeting-detail-recovery-v1/`에 남겼고 [공개 검증 영수증](../experiments/results/meetings-detail-recovery-v1.json)에 hash를 기록했다.

부모 AI는 데스크톱 접근 거부 화면과390px 결정 재선택 화면을 확인했다. 별도 읽기 검토에서 보조 재시도 버튼을 잘못 해석한 일도 보존했다. 실제 코드는 이미 `detail ? refresh() : load()`였고 결함이 아니었다. 이미 시작한 실제 Java 표적1개가 기존 버튼의 정상 재조회를 확인했으며 제품 코드와 최종 영수증은 바뀌지 않았다.
